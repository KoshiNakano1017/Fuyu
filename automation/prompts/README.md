# プロンプト

エージェント1体につき1ファイル。**10本**。

配置先は `automation/prompts/`。ワークフローからは次の形で読ませる。

```yaml
prompt: |
  automation/prompts/<名前>.md を読み、その指示に従うこと。
  対象 Issue 番号: ${{ github.event.issue.number }}
```

### 出力先に届かないエージェントがいる

`readonly.json`（レビュー 5a/5b/5c）は Bash を全面拒否し、`test.json`（テスト設計）は `gh` を許可していない。
**このためこの4体は、設計 §3 が定める出力先へ自力で到達できない。**

権限を緩めて解決すると §3 の権限表が崩れるため、**転記はワークフローが行う**
（`automation/scripts/post_agent_output.sh`）。プロンプト側は「最終メッセージに書く」だけでよく、
どのプロンプトにも「`gh` を実行できないので転記はワークフローが行う」と明記してある。

### マーカーの一覧（ワークフローが読む）

| マーカー | 出す人 | ワークフローの挙動 |
| --- | --- | --- |
| `<!--risk:high/mid/low-->` | pm-define / pm-plan | ゲート数を決める（auto-01・auto-03） |
| `<!--blocked-->` | 全エージェント | `auto:blocked` へ遷移して停止 |
| `<!--tests:designed-->` | test-design | 正常終了の確認 |
| `<!--implemented-->` | coding | 正常終了の確認 |
| `<!--review kind=quality/spec/privacy result=pass-->` | レビュー3種 | **[必須] 指摘がゼロ**。低リスク自動通過の条件② |
| `<!--review kind=... result=findings-->` | レビュー3種 | 修正エージェントを起動 |
| `<!--reject phase=review kind=privacy-->` | review-privacy | **停止**。実在の個人情報の疑いは自動修正に渡さない |
| `<!--fixed-->` | fix | 正常終了の確認 |
| `<!--reported-->` | pm-report | 正常終了の確認 |
| `<!--retry-->` | **ワークフロー**（機械が置く） | 5回に達したら停止（設計 §4.3・§6.2） |

**マーカーが読めないときは、ワークフローが安全側（指摘あり・高リスク）へ倒す。**

## 書くときの規律

### 1. 計画側3本には「質問の作法」を転記する

`pm-define` / `research` / `pm-plan` には、
[設計 §3.2 質問の作法](../../docs/自律開発ループ設計.md)の内容を**そのまま転記する**。

- 実質的な曖昧さの6軸
- 選択肢は最大3つ・推奨案とその理由を1つ・1回に1問
- **推奨は述べるが、採否は決めない**
- 出力の形（テンプレート）

> [!IMPORTANT]
> 「曖昧なら止まれ」とだけ書いたプロンプトは、**止まるが選択肢を出さない**。
> これでは人間が論点を一から再構成することになり、ループの価値が半減する。

### 2. 実装側には質問させない

`coding` / `fix` には質問の作法を入れない。
段取りが承認済みである以上、そこで聞くのは手戻りになる。

**実装中に曖昧さを見つけたら、質問ではなく停止**（`auto:blocked`）が正しい。
段取りの前提が崩れているということなので、ゲート2からやり直すべき状況である。

### 3. 強調を書きすぎない

`CRITICAL` `必ず` `絶対に` を多用しない。
現行モデルは指示を素直に追うため、**過剰な強調は的外れな指摘や過剰な発火を招く**。

| 悪い | 良い |
| --- | --- |
| `CRITICAL: 必ずこのツールを使うこと` | `〜のときにこのツールを使う` |
| `絶対に〜してはならない`（多数） | 本当に守るべき1〜2点だけを、理由つきで書く |

### 4. 一般論を書かない

コーディング規約・命名規則・テストの書き方といった一般論は、
リポジトリの規範ファイル（[`CLAUDE.md`](../../CLAUDE.md)）が既に持っている。
プロンプトに重複させると、**推論コストだけが増えて成功率は上がらない**。

**プロンプトに書くのは、そのエージェント固有の責務と境界だけ。**

### 5. 出力先を明示する

各エージェントが「どこに何を書くか」を1行で示す。
曖昧だと、Issue コメントに書くべきものをファイルに書いたりする。

## テンプレート

```markdown
# <エージェント名>

## あなたの責務
<1〜2文。何をする人か>

## やること
- <箇条書き>

## やらないこと
- <箇条書き。境界を明示する>

## 出力先
<Issue コメント / 特定のファイル / PR レビューコメント>

## 手順
1. <順序が意味を持つ場合のみ番号を振る>

## 停止条件
<どういうときに実装せず止まるか>
<計画側3本なら、ここに「質問の作法」を転記する>
```
