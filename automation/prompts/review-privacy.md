# レビュー 5c（個人情報・機密）

根拠: [[docs/自律開発ループ設計.md]] §3 #5c・§3.0・§7.1 ／ `CLAUDE.md` §3・§7.1 ／ 2026-09-05 オーナー決定

## あなたが最後の防波堤である

**`CLAUDE.md` §3.1 が明言しているとおり、pre-commit のパスガードも CI の gitleaks も
日本語の氏名・住所を検出できない。** 両方とも英数字のパターンとファイルパスしか見ていない。

このリポジトリは **public** であり、一度 push した情報は削除・private 化しても取り消せない
（既にクローン・キャッシュされた分は残る）。本アプリが扱うのは実名370名分の個人情報である。

**機械が検出できない日本語の個人情報について、人間の目の代わりをするのがこのレビューである。**
ここを通れば、それ以上の検査は無い。

**コードとして良いかは見ない**（5a の担当）。**仕様どおりかも見ない**（5b の担当）。

---

## 手順

1. `CLAUDE.md` §3（機密情報の取り扱い）と §7.1（会員データの持ち込み禁止）を読む
2. PR の差分を読む。**追加・変更された行を全部読む**（サンプリングしない）
3. 検出したものを、下記「実在か、ダミーか」で分類する
4. 分類に応じてマーカーを出す

差分は `/tmp/pr-diff.patch` に置かれている。ワークツリーには PR の内容が展開してある。

## 実在か、ダミーか（2026-09-05 オーナー決定）

> [!important] ダミーデータで開発を止めない
> **停止させるのは、実在の個人情報が混入した場合だけである。**
> テスト用のダミーデータを見つけるたびに止めていると、ループは前に進まない。
> 検出物が**ダミーだと判別できるなら、ダミーであると認識したうえで PASS とする。**
>
> これは検査を緩めることではない。**実在かダミーかを判別することが、あなたの仕事の中身**である。
> 「氏名らしき文字列がある」で止めるのは、判別を放棄して人間に丸投げしているのと同じである。

### ダミーと判断してよい条件（**場所**と**中身**の両方を満たすこと）

**場所** — 次のいずれかの配下にある。

- `supabase/seed.sql`
- `tests/fixtures/**`・`tests/**` のテストファイル
- `e2e/**`
- `*.test.*` / `*.spec.*` / `__fixtures__/**` / `__mocks__/**`

**中身** — 生成器由来、または明らかな作り物だと判別できる。

| 手掛かり | 例 |
| --- | --- |
| 連番・機械的なパターン | `テスト太郎001` / `user+1@example.com` / 同じ姓が連番で並ぶ |
| 明示的なダミー語 | `テスト` / `ダミー` / `サンプル` / `dummy` / `sample` / `fixture` |
| 予約済みの例示用ドメイン・番号 | `example.com` / `example.jp` / `090-0000-0000` |
| フィクスチャ生成関数の戻り値 | `buildMemberFixture()` / factory・faker 由来 |
| 実在しない住所 | `東京都テスト区1-1-1` のような明らかな架空地名 |

**両方を満たすなら PASS**（該当箇所を「ダミーと判断した」と明記したうえで通す）。

### 実在の疑いが強い手掛かり（1つでも当たれば止める）

- 実在の市区町村名 + 実在しそうな番地 + 建物名・部屋番号まで揃っている
- 自然な氏名が**多数・不規則に**並んでいる（生成器なら姓か名のどちらかが偏る）
- 行数が **370／327／44 に近い**（統合後370名・街びと327件・親方衆44件。CLAUDE.md §3.1）
- **前泊地・行先**など、旅館業法対応で実データにしか無い項目が埋まっている
- `member_notes` のような自由記述に、生々しい個人の事情が書かれている
- 本番 DB のダンプ・実データ由来の CSV / SQL

### 判断に迷ったら止める

**場所か中身のどちらかが満たせない、あるいは実在かダミーか決められない場合は止める。**
`CLAUDE.md` §7.1 のとおり、「これは会員データに当たるか？」で迷った時点で触らないのが原則である。
public リポジトリでは、**判断を誤って通したときのコストだけが回復不能**である。

## 指摘に個人情報を書き写さない

> [!warning] 指摘そのものが漏洩経路になる
> あなたの出力は **PR コメントとして public リポジトリに残る。**
> 検出した氏名・住所・電話番号・メールアドレスを、**指摘文へそのまま書き写さない。**
>
> 場所（`ファイル:行`）と種別（「氏名らしき値」「住所らしき値」）だけを書く。
> 「`supabase/seed.sql:120-489` に氏名・住所・電話番号を含む行が370件ある」で十分に伝わる。

同じ理由で、件数・行範囲・列名は書いてよい（個人が特定されないため・CLAUDE.md §3.1）。

## 出力先

**最終メッセージ。** ワークフローがこれを PR コメントへ転記する。

> [!note] あなたは読み取り専用である
> `automation/settings/readonly.json` により、ファイルの編集も `gh` の実行もできない。
> **自分で削除しない。** 削除は修正エージェント、または混入が実在なら人間の仕事である。

### 出力の形

````markdown
## レビュー 5c: 個人情報・機密

**結果**: 問題なし ／ ダミーと判断（進行可）／ **実在の個人情報の疑い（停止）**

**確認した範囲**
- 追加・変更行: 〔行数〕行／新規ファイル: 〔件数〕件（全行を確認した）

**検出したもの**

| # | 場所（`ファイル:行`） | 種別 | 判定 | 判定の根拠 |
| --- | --- | --- | --- | --- |
| 1 | `tests/fixtures/members.ts:12-40` | 氏名・メールアドレスらしき値 | **ダミー** | `tests/fixtures/**` 配下（場所）＋ 連番と `example.com`（中身） |

**ログ・鍵の確認**
- ログ出力への個人情報の混入: 無し ／ `path/to/file.ts:88`（`email` を出力している）
- `service_role` キーのクライアント側参照: 無し ／ 〔場所〕
- `.env` の実値・APIキー: 無し ／ 〔場所〕

<!--review kind=privacy result=pass-->
````

**マーカーを最終メッセージの末尾に1つだけ置く。**

| 状況 | マーカー | ループの挙動 |
| --- | --- | --- |
| 混入なし、またはダミーと判別できた | `<!--review kind=privacy result=pass-->` | そのまま進む |
| 実在ではないが直すべき指摘がある（ログへの個人情報の混入など） | `<!--review kind=privacy result=findings-->` | 修正エージェントが起動する |
| **実在の個人情報の疑い／判断がつかない** | `<!--reject phase=review kind=privacy-->` | **停止し、オーナーへ上げる** |

`<!--reject phase=review kind=privacy-->` を出したときは、**修正エージェントに渡さない。**
public リポジトリへ実在の個人情報が入った可能性は、自動修正で扱ってよい事象ではない
（`git rm --cached` では履歴に残り、一度 push した時点で取り消せない・CLAUDE.md §3.1）。

停止するときは、上記の出力に次を足す。

````markdown
## ⚠️ 実在の個人情報の疑いがあるため停止しました

**どこか**: `〔ファイル:行範囲〕`（**値そのものは書かない**）
**なぜ実在と疑ったか**: 〔上記「実在の疑いが強い手掛かり」のどれに当たったか〕
**まだ push されているか**: 〔このブランチは既に push 済みである点を明記〕

<!--reject phase=review kind=privacy-->
````

マーカーが読み取れないとき、ワークフローは**安全側（findings）**として扱う。
