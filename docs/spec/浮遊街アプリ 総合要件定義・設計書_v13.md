## 1. プロジェクト概要

### 1.1 背景

自給自足コミュニティ「浮遊街」におけるクエスト運営、会員管理、顧客管理、地域通貨「Uii（ウイ）」運用およびFAQ対応について、現在は人手による運営負荷が高い。本システムは、これらの運営業務をデジタル化し、AIを活用した運営支援を実現することを目的とする。

また、従来分散していた「浮遊街クエストボード」を本アプリへ一元集約し、日本円などの既存通貨を介さず「腐る経済」を軸とした特異なコミュニティの持続可能性を高める。

さらに、毎朝行われる朝会の音声録音から文字起こし・議事録を自動生成し、発言内容から「今日やるべきクエスト」をAIが自動抽出・起案する仕組みを **Phase 1から導入** する。併せて、コミュニティ内に存在する暗黙知（ゆうきさんのまかないレシピ、左官、草刈り、農作業ルーティン等）を行動の文脈に合わせて引き出せるよう形式知化（ケースベース推論）する。

### 1.2 システム目的

#### 業務効率化とワンオペ負荷の極小化

- 朝会音声のワンタップ録音、AIによる議事録自動生成、および議事録からの「クエスト候補自動抽出・起案」による朝のオペレーション負荷極小化（**Phase 1前倒し**）
- クエスト管理のデジタル化と既存クエストボードのアトリビューション統合（事前申請・指示・目視承認・Before/After写真検証・Eumo送付リンク案内）
- 顧客管理の統合化（宿泊・注文・クエスト・未会計請求情報の一元把握および一括精算）
- 朝会・日次オペレーションサマリーによる現場状況の即時把握
- カフェメニューの即時売り切れ（SOLDOUT）制御や、代理注文時の人間系エラー（誤注文・誤請求）防止策による現場摩擦ゼロ化
- FAQ自動回答と暗黙知のデータベース化（AI未回答時のLINE即時通知 ＆ 代理返信機能）

#### 利用者体験向上と摩擦ゼロのUI ＆ 透明性の確保

- チェックイン/チェックアウトのワンタップ・QR化と自動ウェルカムメッセージ
- 宿泊法（旅館業法等）に準拠した属性収集と現行宿泊フォームとの同期
- ユーザー本人（街人・ゲスト）が自身の注文・決済・クエスト履歴をいつでも確認できるログ透明化UI
- 獲得XPや貢献バッジ表示によるモチベーション・ゲーム性の提供

#### 将来展望とテクノロジー連携

- 複数コミュニティ展開（マルチテナント基盤構築）
- FEL（Favorite Earth Life）との共通データ連携およびIoT遠隔監視（Phase 3）

## 2. システム概要

**システム名称**: 浮遊街アプリ

### 利用者分類

| 分類 | ロール識別子（`role`） | 説明 |
| --- | --- | --- |
| 管理者 | `admin` | 運営統括（PC/タブレットから顧客管理・全体統括・店舗オペレーション・朝会録音/議事録作成・クエスト審査・会員データ一括インポートを実施） |
| コアメンバー | `core_member` | 現場の管理権限を持つスタッフ・コミュニティリーダー（店舗オペレーション、クエスト査定、ナレッジ登録。顧客管理は自拠点に限定） |
| 会員（街人） | `member` | 一般コミュニティメンバー、ボランティアスタッフ（マイページ、宿泊チケット保持、履歴ログ閲覧可能） |
| ゲスト / 長期滞在者 | `guest` | 初回来訪者または長期宿泊者（※宿泊チケット機能は除外。クエストは限定範囲で閲覧・受注申請が可能） |
| カスタム権限 | `custom` | 出資者・VIP等の特殊権限設定 |

> [!note] v1.10 変更点
> 従来「管理者」の説明文に同居していた**コアメンバーを独立ロールとして分離**した。ロール別UI表示制御（§5.9）とナレッジの公開範囲設定（§5.7）が `admin` と `core_member` を区別する前提で成立するため、ロール識別子を本章で確定させる。

#### ★ コミュニティ内の立場（`member_type`）— v1.12.0 追加

`role`（システム権限）とは**別軸**として、コミュニティ内での立場を保持する。2026-08-14 受領の実データに「親方衆」という区分が存在したため、正式に定義する。

| `member_type` | 説明 | 対応する `role` |
| --- | --- | --- |
| **親方** | 出資者・コミュニティの中核を担う立場（受領リスト44名） | **`member`（街人と同等の権限）** |
| 街人（コア） | コアメンバーとして現場運営を担う会員 | `core_member` |
| 街人（一般） | 一般会員（受領リスト327名） | `member` |
| ゲスト | 短期滞在者・初回来訪者 | `guest` |

> [!important] 「親方」は権限ではなく立場である
> 親方衆44名の**権限は街人（`member`）と同等**とする（2026-08-14 決定）。`member_type` は画面上のバッジ表示・再訪アラート（§5.8.4）・運営の呼称に用いるものであり、**アクセス制御には一切使用しない**。
> `member_type = 親方` を認可条件に混ぜると、「立場が上だから管理画面も見えるはず」という暗黙の期待が実装に紛れ込み、顧客の氏名・連絡先・運営メモが44名へ開放される事故につながる。認可は `role` のみで判定すること（§5.9.3）。

#### アカウント状態（`account_status`）

| 状態 | 説明 |
| --- | --- |
| `pre_registered` | 「親方・街人リスト」等から事前投入済みで、本人の初回認証が未了の状態（§5.8） |
| `active` | 本人認証・名寄せが完了し、通常利用中 |
| `withdrawn` | 退会処理済み（論理削除。30日後匿名化） |

## 3. 開発方針

1. **MVPの早期構築 ＆ 現場摩擦ゼロ**: 最小限の機能で短期間構築し、現場で運用しながら高速に改善する。操作マニュアルも同時準備・提出する。
2. **朝会録音・議事録自動生成 ＆ クエスト自動抽出（Phase 1前倒し）**: 朝会時にスマホ/タブレットからワンタップで音声録音。Whisper/Gemini API等を活用して高精度文字起こしと要約議事録を作成し、会話の中から「本日必要なタスク（作業内容・担当者・募集人数）」を抽出してクエスト登録案を自動作成する。
3. **クエストボードの完全集約 ＆ 承認・指示プロセスの厳格化**: 従来の紙/チャット等のクエストボードをアプリに一元化。受注申請 → 運営による業務指示（日時・場所・内容）→ Before/After写真付き完了報告 → 1日おき（日次）の承認/差戻し判定サイクルを確立する。
4. **Phase 1におけるUii管理の「会計管理特化」**: 開発スピード向上および現場運用の混乱防止のため、Phase 1におけるUii機能は「円2割引換算による請求額計算」「一括精算時のUii表示」「クエスト承認時の給付予定Uii確定」といった会計・精算管理のみに絞り込む。ユーザー個別のリアルタイム残高管理・有効期限（失効）管理・EUMO直接参照等の高度な通貨機能はPhase 2以降へ移行する。
5. **代理注文の間違い防止 ＆ ログの相互確認**: 代理注文時は「現在チェックイン中のユーザー」のみを選択肢に表示して誤請求を回避。万一の打ち間違いも管理画面から修正可能とし、ユーザー自身もスマホから自身の利用ログを常時確認可能とする。
6. **宿泊法対応 ＆ リピーター名寄せ・アカウント確定**: 宿泊法に基づく「住所」「前泊地」等の取得項目を現行の宿泊フォームと連動。再訪時に履歴が引き継げるようアカウント確定ロジックを整理する。

## 4. スコープ

### Phase 1（MVP：2026年7月〜8月）

#### 認証・アカウント・チェックイン / アウト

- 現行宿泊予約フォーム連動による予約情報の空枠作成（宿泊法必須項目：住所・前泊地含む）
- ニックネーム・誕生年月・属性・初回/リピーターアカウント確定処理
- ワンタップ/QRチェックイン・チェックアウト機能 ＆ AIウェルカムメッセージ送信
- ゲスト（非会員）向けの宿泊チケット表示除外処理

#### ★ 朝会録音・議事録自動生成 ＆ クエスト自動起案

- 音声録音インターフェース（管理者タブレット/PC）
- 音声テキスト化（文字起こし）＋ AI要約議事録の自動生成
- 会話内容からの「クエスト立案候補（タスク名、予定時間、推奨担当/人数）」AI自動抽出機能
- 抽出されたクエスト候補のワンタップ登録・修正機能

#### 顧客管理 ＆ 一括精算機能 ＆ マイログ閲覧

- ゲスト・街人の通算宿泊日数・保持チケット（会員のみ）管理
- 注文履歴・未会計ステータスおよび未会計分の一括精算用QRコード/URL発行
- **★ 顧客管理画面上での注文履歴の直接編集（明細・注文者・キャンセル・手動調整）と、請求精算額のリアルタイム自動再計算**
- **★ 未会計額の「円 ＋ Uii」併記表示**
- ユーザー本人が自身の注文・決済・クエスト履歴を閲覧できる個人ログ画面

#### クエスト管理（クエストボード集約） ＆ モチベーション

- クエスト一覧（ボード集約）、受注申請（ステータス：「申請中」）
- 運営による審査・実行指示（いつ・どこで・何を任せるか）
- 完了報告時の Before / After 写真添付 および作業時間入力
- 1日おき（日次サイクル）の運営による承認/差戻し審査画面
- 承認完了時の支払Uii額表示およびEumo送付用リンク発行・送付フロー
- マイページへの獲得XP・貢献バッジ表示

#### 注文管理・店舗オペレーション

- セルフ注文（スマホ）＋ 店員タブレット代理注文（チェックイン者限定選択 ＋ 管理画面補正機能）
- 店舗端末からの「売り切れ（SOLDOUT）」即時トグルスイッチ

#### Uii機能（会計管理限定）

- 円価格ベースの2割引換算表示（Uii = JPY × 0.8相当ロジック）
- 伝票・注文におけるUii請求額算定およびクエスト達成時の付与Uii額確定

#### FAQ・暗黙知AIコンシェルジュ ＆ ゆうきさんナレッジ

- RAG対応（まかないレシピ、左官、草刈り、しばかり/枝払い、農作業ルーティン等）
- AI未回答時の運営LINEグループ即時通知 ＆ LINE代理返信・自動学習
- **★ 管理者・コアメンバー向けナレッジ登録画面**（4ステップのガイド付きフォーム。詳細は §5.7）

#### ★ 既存街人の事前データ登録・名寄せ ＆ 宿泊日数管理（2026-08-13 レビュー追加）

- 「親方・街人リスト（CSV/Excel）」の一括インポートによる `pre_registered` アカウント生成
- 初回アクセス時の自動名寄せ ＆ ステータス引き継ぎ確認画面
- 再訪チェックイン時の運営向け再訪アラート（街人ステータス・残チケット・運営メモの即時表示）
- 顧客登録時の宿泊日数の初期入力 ＆ 運営による宿泊日数の手動増減（§5.8）

#### ★ ロール別UI表示制御・アクセス制御（2026-08-13 レビュー追加）

- ロールに応じたタブ・メニューの動的表示制御（権限外メニューはDOMごと非描画）
- ロール切替プレビュー機能自体を通常ユーザー画面から完全非表示
- 権限外URLへの直接アクセス時のアクセス制限画面（コンテンツ・プレビューを一切レンダリングしない）＋ サーバサイド認可（§5.9）

#### ★ ゲスト → 街人（会員）アップグレード導線（2026-08-13 レビュー追加）

- ロック中クエストの施錠表示（`🔒 街人登録で解放`）からの街人登録モーダル起動（§5.10.6）
- 2段階モーダル（入力 → 確認）による**申請**の受付。アプリ内では決済情報を入力させない
- **管理者による決済QRの発行・送付 → 入金確認 → 承認**をもって `guest` から `member` へ昇格し、**宿泊券4枚（4泊分）＋ コインCB 5,000 を付与**（§5.10.4）
- ※既存会員は本導線を通らず、名寄せによりステータスを引き継ぐ（§5.8）

#### 管理者画面・運用ドキュメント

- PC/タブレット最適化WebUI（「今日の浮遊街サマリー」ダッシュボード、朝会録音・議事録モジュール）
- アプリ初期操作マニュアルの提出

### Phase 2（2026年9月以降予定）

- **★ メディア（画像・動画）ストレージ ＆ おすすめ表示（2026-08-15 に Phase 1 から移送）**: Cloud Storage for Firebase への直接アップロード、カスタムメタデータ付与、用途タグに基づく「おすすめ画像・動画」の提示（§5.11）
- **★ 会員権の有効期間・期限表示・一斉失効（2026-08-15 に Phase 1 から移送）**: 有効期限のUI表示、満了時の一括失効バッチ（§5.8.6）。**最初の満了は 2027/4/30** のため Phase 1 では発生しない

- **スキルツリー機能**: スキルレベルLv1〜5の可視化、熟練度連動の報酬動的算出、推薦機能

#### 5.2.1 ★ 部屋割当（`rooms` / `room_assignments`）（2026-08-15 決定 ／ §9 #28）

**「誰がどの部屋に泊まったか」を記録するエンティティを新設する。** 宿泊者名簿（氏名・住所・前泊地等）と宿泊券の泊数管理（§5.8.6）だけでは、部屋単位の割当・移動・稼働状況が管理できないため。

| 要件 | 内容 |
| --- | --- |
| 部屋台帳（`rooms`） | 部屋（またはベッド単位の枠）をマスタとして保持する。ドミトリー・個室いずれの運用にも対応できるよう、**1部屋＝1収容枠とは限らない**（`capacity` を持つ）構造とする |
| 部屋割当（`room_assignments`） | チェックインごとに、どの部屋（枠）へ何日から何日まで割り当てたかを記録する。**1回のチェックインに対して複数の割当履歴を許容**し、部屋移動（A-07）にも対応する |
| チェックイン時の割当 | チェックイン操作の一部として部屋（枠）を選択する。**満室の部屋・メンテナンス中の部屋は選択肢に出さない**（`rooms.status` で制御） |
| 部屋移動 | 滞在中に部屋を変更する場合、既存の割当を終了（`ended_at` を設定）し、新しい割当を追加する。**物理的な上書きは行わない**（履歴として残す） |
| 表示 | 顧客管理画面の顧客サマリーヘッダー（§5.6.1①）に**現在の割当部屋**を表示する |
| 権限 | 部屋割当の登録・変更は **管理者・コアメンバーのみ**（§6 権限マトリクス） |

> [!note] `Place`（拠点・施設マスタ）との違い
> [[ER図_概念データモデル]] の `Place` はFELとの共通語彙で、気候・土壌・地形等の**環境プロファイル**を持つ大きな単位（畑・建物等）を指す。`rooms` はその内部にある**宿泊用の割当単位**であり、`Place` とは別エンティティとして分離する。`rooms.place_id` を任意項目として持たせ、建物（`Place`）に紐づけられる場合は参照できるようにする。
>
> `Place` に宿泊法の属性まで持たせると、FEL側と共有する環境プロファイルのスキーマに浮遊街固有の宿泊管理ロジックが混入し、[[システムアーキテクチャ]] のクリーンアーキテクチャ制約（FEL連携を見据えた共通語彙とドメイン固有拡張の分離）に反するため、意図的に分離している。

#### 5.2.2 ★ 予約のキャンセル・ノーショー（2026-08-15 決定 ／ §9 #27）

**顧客管理画面から該当の予約を削除する**運用とする。専用のキャンセル料計算や宿泊券の返却処理は Phase 1 では設けない。

| 項目 | 仕様 |
| --- | --- |
| 操作場所 | **顧客管理画面**（管理者・コアメンバーのみ。§6 権限マトリクス） |
| 対象 | 外部宿泊フォームから自動反映された予約（§9 #3）、およびチェックイン前の滞在予定 |
| 削除方式 | **論理削除**（`cancelled_at` ＋ `cancel_reason` ＋ 操作者IDを記録）。**物理削除は行わない** |
| 理由入力 | **必須**。「会員都合キャンセル」「ノーショー」「運営都合」等を選択＋自由記述（§5.6.4 の編集理由必須ルールに準拠） |
| **部屋割当の解放** | 予約削除と同時に、紐づく `room_assignments` を終了（`ended_at` を設定）し、**部屋を空き枠に戻す**（§5.2.1） |
| 本人への表示 | マイログの宿泊履歴に「運営によりキャンセル（日時・理由）」と表示し、相互確認できる状態にする |

> [!important] 宿泊券は「返却」する必要がない
> 宿泊券の消費（`stay_ticket_transactions` の `consume`）は**チェックアウト時に発生**する（§5.8.5）。したがって**チェックイン前のキャンセル・ノーショーでは、そもそも消費が起きていない**。
> 「消費されるのか返却されるのか」という当初の論点は、**消費のタイミングを後ろに置いた設計によって自動的に解消**されている。予約を削除するだけでよく、宿泊券に対する補正処理は不要。

> [!note] ノーショーにペナルティを課さない前提
> 上記のとおり、**ノーショーでも宿泊券は減りません**。予約だけ入れて来訪しない会員がいても、現状の仕様では宿泊券の損失が発生しない設計です。
> 部屋を押さえていた分の機会損失を会員側に負担させたい場合は、キャンセル料（`staff_adjust` による宿泊券の減算、または未会計としての金額計上）を別途定義する必要があります。**Phase 1 では設定しない**方針としますが、運用してみて無断キャンセルが問題化した場合は再検討の余地があります。

### 5.3 クエスト管理・受注承認・完了報告フロー

1. **クエストボードのアプリ集約**: 手動登録および朝会から自動抽出された全クエストを統合表示。
2. **受注申請 ＆ ステータス管理**: ユーザーが「参加申請」を行うと、ステータスは「申請中」となる。
   - **実行形態（execution_mode）**: onsite（現地必須）／remote（遠隔可能）／hybrid をクエスト属性として持ち、遠隔クエストは独立カテゴリではなくフィルタ抽出として扱う。
   - **資格要件（required_certification）の安全ゲート**: ユンボ・重機、チェーンソー（間伐）、食品衛生等の業務は、会員マスタの `certifications` と照合し、未保有者は受注申請できないバリデーションを設ける（スキルLv要件とは独立）。詳細は [[業務カテゴリ体系とAIエージェント設計]]。
3. **運営による審査・指示出し**: 運営側が「いつ・どこで・何を任せるか」の指示を出して承認（マッチング成立）。
4. **完了報告（Before / After 写真 mandatory）**: 作業前の写真（Before）、作業後の写真（After）、実施時間を添付して提出。
5. **日次承認サイクル（1日おき）**: 運営管理者が1日1回報告を確認し、「承認」または「差戻し」を行う。
6. **承認完了 ＆ Uii支払い案内**: 承認完了時、支払うべき確定Uii額とEumo送付用リンクを発行。

> [!note] クエストの反復実行・複数人按分・スキル連動報酬（2026-08-15 決定）
> 構想段階のbackground資料では「同一クエストの反復実行」「複数人での同時参加・貢献度按分」「スキル熟練度に応じた報酬変動」が言及されていたが、**いずれもPhase 1では実装せず、Phase2「スキルツリー機能」と合わせて整理する**。Phase 1では「1クエスト＝運営が指定した募集人数の範囲で受注可・報酬は均等割り・反復実行は運営の再登録ベース」というシンプルな運用とする。

### 5.4 注文管理・代理注文・間違い防止機能

- **★ 注文可能条件（チェックイン中限定）**: Phase 1では**カフェ・直売所ともに「現在チェックイン中のユーザー」のみ**が注文可能とする。未チェックインのユーザーには商品の購入導線を表示せず（「要チェックイン」表示）、カート投入・注文確定を禁止する。セルフ注文・代理注文の双方に適用する。
- **代理注文の誤選択防止**: 店員タブレットでの代理注文対象を「現在チェックイン中のユーザー（滞在中）」のみに制限。
- **間違え・打ち直し補正**: 管理者画面から該当伝票の注文者切り替えやキャンセル・金額補正が可能。
- **ユーザー個人のログ確認**: 会員・ゲストが自身のスマホから「注文履歴」「未会計額」「クエスト実績」を常時閲覧可能。

### 5.5 Uii機能・経済圏会計ロジック（Phase 1：会計管理）

- **円換算2割引ロジック**: システム内部では「円価格の2割引（20%オフ）」相当の数値をUii標準換算レートとして自動算定・表示する。
- **★ 通貨併記の原則**: 金額を表示する全画面（顧客管理・注文履歴・未会計額・一括精算・マイログ）において、**円を主・Uiiを副として併記**する。表記例：`¥3,000（2,400 Uii）`。
- **★ 換算の適用単位と端数処理（確定）**: Uii換算は伝票合計に対してではなく、**単品（商品1点の単価）ごと**に行う。
  - 単品Uii ＝ `floor(単価（円） × 0.8)`
  - 明細行Uii ＝ 単品Uii × 数量
  - 伝票Uii ＝ 明細行Uiiの合算（＋手動調整のUii換算）
  - 未会計Uii ＝ 未精算伝票のUii ＋ 宿泊費等の請求項目のUii
  - **理由**: 商品カードに表示される単品Uiiを足した値と、伝票・未会計合計のUiiが必ず一致する。合計に0.8を掛ける方式では表示と合計がずれ、現場で「計算が合わない」問題が起きるため。

#### 5.5.1 ★ 決済方式の統一（2026-08-14 決定 ／ §9 #24）

**即時決済・後払いのどちらも可能とする。ただし Uii による直接決済は行わず、すべて精算QRを経由して清算する。**

| 論点 | 確定内容 |
| --- | --- |
| 即時決済 | 可。注文直後にその場で精算QRを発行して清算する |
| 後払い | 可。「未会計」として計上し、退去時等に一括精算QRで清算する（§5.6.1④） |
| **Uiiによる直接決済** | **不可**。アプリ内でUii残高から引き落とす決済は実装しない |
| Uiiの役割 | **価格換算・併記の表示のみ**（`floor(単価×0.8)`／§5.5）。支払手段ではない |
| 精算の共通経路 | **精算QR**。即時・後払いのいずれも同一のQR発行・失効基盤（§5.6.3-5）を用いる |

> [!note] 即時と後払いは「QRをいつ出すか」の違いでしかない
> 両者を別々の決済フローとして実装しないこと。内部的にはどちらも「伝票を起票 → 未会計 → 精算QR発行 → 清算完了」という同一の状態遷移をたどり、**即時決済は起票直後にQRを発行するだけ**です。分岐を作ると、片方だけ伝票編集（§5.6.2）や差額繰越（§5.6.6）に対応していない、といった穴が生まれます。

### 5.6 ★ 顧客管理画面（画面デザイン要件）

**対象ロール**: 管理者・コアメンバー（PC / タブレット最適化）

#### 5.6.1 画面構成

| 領域 | 内容 |
| --- | --- |
| ① 顧客サマリーヘッダー | ニックネーム／氏名、会員種別（会員/ゲスト）、**チェックイン状態バッジ（滞在中/滞在外）**、**現在の割当部屋**（§5.2.1）、通算宿泊数、保持宿泊チケット数（会員のみ）、獲得XP・バッジ、**未会計額（円 ＋ Uii併記）を最も大きく強調表示** |
| ② タブ切替 | 「注文履歴」／「宿泊」／「クエスト」／「プロフィール（宿泊法項目）」 |
| ③ 注文履歴タブ（主機能） | 伝票一覧テーブル：伝票番号・日時・注文区分（セルフ/代理）・商品明細・金額（円）・**換算Uii**・決済ステータス（未会計/会計済み）・操作ボタン |
| ④ 請求精算パネル（右サイド固定） | 未会計伝票の選択合計（円／Uii）、**一括精算QRコード/URL発行**ボタン、精算済みマーク処理 |

#### 5.6.2 注文履歴の編集機能（管理者・コアメンバーのみ）

伝票行の「編集」から、以下をインライン編集できる。

| 編集操作 | 内容 |
| --- | --- |
| 商品明細の修正 | 品目の追加／削除、数量変更 |
| 単価の上書き | 特例値引き・イベント価格等に対応（上書き時は理由入力必須） |
| 注文者の付け替え | 代理注文の誤選択を救済。付替候補は原則「当日チェックイン中だったユーザー」を既定表示し、必要時に全顧客検索へ切替可能 |
| 伝票のキャンセル | 物理削除は行わず**論理削除（取消フラグ＋取消理由）**とし、一覧では取消線表示で残す |
| 決済ステータス変更 | 未会計 ⇄ 会計済み の手動切替（現金・Eumo手渡し等の場外精算に対応） |
| 手動調整行の追加 | 「まかない補助」「割引」等の任意調整額（プラス／マイナス）を1行として追加 |

#### 5.6.3 請求精算額の自動再計算

1. 明細を編集 → **行小計（円）**を再計算
2. 伝票合計（円）＝ 行小計の合計 ＋ 手動調整額
3. **伝票Uii ＝ 各行の「`floor(単価 × 0.8)` × 数量」の合算**（5.5の単品換算に準拠）
4. **未会計合計（円／Uii）**および請求精算パネルの選択合計に**即時反映**（保存後にリロード不要）
5. 既に精算QR/URLを発行済みの伝票を編集した場合は、**旧QR/URLを自動失効**させ、再発行を促す警告を表示する

#### 5.6.4 誤操作防止・透明性の担保

- **保存前の差分プレビュー**: 「変更前 → 変更後」（金額・Uii・明細）を確認ダイアログに表示し、確定ボタンで初めて反映。
- **編集理由の必須入力**: 単価上書き・注文者付替・キャンセル・ステータス手動変更は理由の入力を必須とする。
- **編集履歴ログ**: 誰が・いつ・どの伝票の何を・なぜ変更したかを全件保存し、伝票詳細から閲覧可能とする。
- **ユーザー側への反映**: 修正された伝票は、本人のマイログにも「運営により修正（日時）」と表示し、相互確認できる状態にする。

#### 5.6.5 ★ 会計済み伝票の遡及修正（確定仕様）

精算後に判明した誤り（品目間違い・数量違い・注文者違い等）を救済するため、**「会計済み」の伝票も編集可能**とする。ただし実収額と帳簿の乖離を防ぐため、以下を必須とする。

1. **警告表示**: 編集画面の冒頭に「この伝票は精算済みです。修正すると差額が生じます」と明示する。
2. **差額の明示**: 確定時に `修正後金額 − 精算済み金額` を算出し、**プラスなら「追加請求」、マイナスなら「返金」**として表示する。円・Uiiの両方を表示する。
3. **差額の残置**: 算出した差額は顧客管理画面の請求・精算パネルに「未処理の差額」として残り、運営が現金または Eumo で精算した時点で解消する。
4. **監査ログ**: 遡及修正は通常の編集ログとは別に警告レベルで記録し、「誰が・いつ・どの精算済み伝票を・いくら・なぜ」変更したかを保持する。
5. **取消の扱い**: 精算済み伝票の取消も可能。物理削除せず「取消」ステータスとし、精算額全額を返金差額として計上する。

#### 5.6.6 ★ 差額の次回繰越 ＆ 再訪時精算（2026-08-14 決定 ／ §9 #7）

§5.6.5 の遡及修正で生じた差額は、その場で回収・返金しようとせず、**未収金／未返金として繰り越し、次回チェックイン時に現地で精算する**。精算が退去後に判明することが多く、少額の差額を遠隔で回収する運用コストが金額を上回るため。

| 項目 | 仕様 |
| --- | --- |
| 差額の保持 | `settlement_adjustments` レコードとして保持（伝票番号・差額円／Uii・区分・発生理由・ステータス・発生日時） |
| 区分 | **追加請求**（会員→運営）／**返金**（運営→会員） |
| ステータス | `未処理` → `精算済み` ／ `免除` |
| **再訪アラート** | 未処理の差額を持つ会員がチェックインした瞬間、**管理者PC・店員タブレットへアラート表示**（§5.8.4 の再訪アラートと同一の通知枠に相乗り） |
| 現地精算 | アラートから当該差額を開き、**現金受領／QR決済／返金**のいずれかで消し込む。追加請求は §5.10 の決済QR基盤を流用可能 |
| 本人への表示 | マイログに「運営により修正（日時）」＋**未処理差額**を常時表示し、来訪前に本人が把握できる状態にする |
| 滞留アラート | 未処理のまま**90日**を超えた差額を管理画面に一覧表示し、運営が免除・督促を判断する |

> [!important] 「繰越」は消込ではなく先送りである
> 繰越を選んでも差額は**未処理のまま残り続けます**。実際に消えるのは次回来訪時の現地精算か、運営による免除操作の時点です。ダッシュボードの「未会計額」には繰越差額を**含めて**表示し、繰越を選んだ瞬間に画面から消える設計にしないでください。見えなくなった未収金は回収されません。

> [!warning] 返金差額を繰越にする場合の注意
> 追加請求（会員が払う側）の繰越は妥当ですが、**返金（運営が返す側）を無期限に繰り越すのは会員の不利益**になります。「二度と来なければ返金されない」状態になるためです。返金区分については、次のいずれかの運用を推奨します。
> - 金額が一定額（例：3,000円）を超える返金は、繰越せず**運営から連絡して速やかに返す**
> - 繰越する場合も、**マイログに明示**し本人が請求できる状態にする
> - 具体的な閾値・運用は §9 #17 で要確認

### 5.7 FAQ・暗黙知AIコンシェルジュ ＆ ★ ナレッジ登録画面（2026-08-13 レビュー反映）

- **属人化ナレッジの形式知化**: ゆうきさんの「まかないレシピ」「左官」「草刈り・しばかり」「農作業ルーティン」をRAGデータベースへ登録。

#### 5.7.1 設計方針（なぜ自由記述にしないか）

ナレッジ登録を「自由記述テキストボックス」または「ファイルアップロードのみ」で実装すると、**表記ゆれ・分類漏れ・文脈欠落**が発生し、RAG検索のヒット率低下とハルシネーションを招く。そのため**選択式（ガイド付き）フォーム**として設計し、入力者が「論点」と「格納先」を意識せずとも、システム側で適切なメタデータが自動付与される構造とする。

| 方針 | 内容 |
| --- | --- |
| 入力者に思考させないステップ設計 | 「これは誰向け？」「どのジャンル？」を順に選ぶだけで、メタデータ・カテゴリ・タグが内部付与される |
| 暗黙知の形式知化（Situated Action） | 「いつ・どこで・何をする時」という**行動の文脈**を選択式で必ず取得する（[[RAGシステム仕様]] の現場ナレッジカードに準拠） |
| 前提とする入力者像 | システム・AIの仕様を知らない運営メンバー、現場スタッフ（ボラスタ・リーダー）、および運営コアメンバー |

**対象ロール**: 管理者（`admin`）・コアメンバー（`core_member`）のみ。一般会員・ゲストには登録導線を表示しない（§5.9）。

#### 5.7.2 入力フォーム構成（4ステップ）

| STEP | 論点 | 入力形式 | 付与されるメタデータ |
| --- | --- | --- | --- |
| ① 対象者 | 誰に向けた情報か（＝公開範囲） | ラジオボタン（単一選択） | `target_role` |
| ② 格納先カテゴリ | どの領域の情報か | プルダウン（単一選択） | `category_id`（業務カテゴリマスタ準拠） |
| ③ 行動文脈・キーワード | どんな場面で使うか | チェックボックス（複数）＋タグ入力 | `usage_scene[]` ／ `keywords[]` |
| ④ ナレッジ本文 | 実際の内容 | FAQ形式／マニュアル形式の択一 | `question` ／ `answer` ／ `body` ／ `attachments[]` |

**【STEP 1】対象者（`target_role`）**

| 選択肢 | 値 | 想定内容 |
| --- | --- | --- |
| ゲスト（短期滞在者）向け | `guest` | 滞在ルール、カフェの注文方法、温泉・施設案内 |
| 一般会員（街人）向け | `member` | Uiiの使い方、クエストの報告手順、草刈機など機材の使い方 |
| 運営・コアメンバー向け（内部専用） | `core_member` | 受付オペレーション、緊急時対応、査定基準、未会計・精算処理 |

> [!important] `target_role` はアクセス制御キーを兼ねる
> `target_role` は表示上の「対象者」であると同時に、**AI回答時の検索フィルタ**として機能する。ゲストからの問い合わせには `target_role = 'guest'` のナレッジのみを検索対象とし、内部専用ナレッジ（査定基準・緊急時対応等）が外部へ漏出しないことをシステムとして保証する（§5.7.5）。**プロンプト指示による抑制ではなく、検索段階でのメタデータフィルタで担保すること。**

**【STEP 2】格納先カテゴリ（`category_id`）**

業務カテゴリマスタ（15ドメイン）に準拠しつつ、入力者が迷わないよう**現場語彙のラベル**で提示する。

| 表示ラベル | 主な内容 | 表示条件 |
| --- | --- | --- |
| 施設・生活案内 | キッチンの使い方、ゴミ分別、Wi-Fi、近隣マップ | 全ロール |
| クエスト・業務運用 | 作業手順、草刈り・農作業、報告手順 | 全ロール |
| 地域通貨 Uii・eumo | チャージ・送金方法、受取手順、決済トラブル | 全ロール |
| スキル・コミュニティ | スキルレベル昇格条件、イベント企画、推薦ルール | 全ロール |
| 場所づくり・環境データ | 畑の作付け、修繕記録、道具の保管場所 | 全ロール |
| 運営・業務オペレーション | 朝会、チェックイン受付、未会計対応、トラブルシューティング | `core_member` 選択時のみ |
| Uii / eumo 帳簿運用 | 決済トラブル、手動補正、一括精算処理 | `core_member` 選択時のみ |
| クエスト査定・推薦ルール | XP付与基準、査定不承認の基準、昇格推薦の確認 | `core_member` 選択時のみ |
| 施設・設備・道具マニュアル | 草刈機・農機具・キッチンの管理／保守 | `core_member` 選択時のみ |

※STEP 1 で `core_member` を選択した場合のみ、運営系カテゴリを追加表示する（誤って内部情報を一般公開カテゴリへ入れる事故を構造的に防ぐ）。

**【STEP 3】行動文脈（`usage_scene[]`）・キーワード（`keywords[]`）**

| 対象 | 利用シーン選択肢（チェックボックス・複数可） |
| --- | --- |
| 共通 | 朝会・受付時／作業・現場直前／カフェ・決済時／夜・自由時間／トラブル・困りごと |
| コア向け追加 | 朝会・朝の準備／チェックイン・受付時／現場作業・クエスト査定／会計・精算時／トラブル・緊急時 |

関連キーワードはタグ入力（カンマ区切り／タグチップ追加）とする。
入力例：`草刈機, 混合ガソリン, 始動方法` ／ `未会計, 一括精算, 離脱処理`

**【STEP 4】ナレッジ本文**

形式を択一で選ばせ、それぞれプレースホルダーで書き方を提示する。

| 形式 | 入力項目 | プレースホルダー例 |
| --- | --- | --- |
| **A. 一問一答（FAQ）形式**（推奨） | 想定される質問 | 「草刈機はどうやって動かせばいいですか？」 |
| | 回答・案内手順（結論＋手順） | 「①赤色のスイッチをONにし、②チョークを引いてレバーを引っ張ります。※混合ガソリンを使用してください。」 |

#### 5.7.3 運営コアメンバー向けの拡張仕様

コアメンバーが登録するのは現場案内だけでなく「運営の裏側（判断基準・緊急対応・精算処理）」を含む。そのため同一フォームを以下の点で切り替える。

| 項目 | 一般ナレッジ登録 | コアメンバー向け |
| --- | --- | --- |
| STEP 1 の意味づけ | 「誰に向けた情報か」 | **「この情報の公開範囲」**（アクセス権限の宣言） |
| STEP 2 の選択肢 | 現場案内5カテゴリ | ＋運営系4カテゴリ（5.7.2 表参照） |

#### 5.7.7 ★ ナレッジ登録UIの拡張思想 — タイプ別構造化入力（2026-08-16 追加）

§5.7.2 の4ステップフォームは「対象者・カテゴリ・行動文脈・本文（FAQ or マニュアル）」という**入力の型**を確定させたが、STEP4の本文は実質「FAQ」と「フリーテキスト」の二択にとどまっていた。一方 [[RAGシステム仕様]] では既に **レシピ型（`Recipe`：手順配列）** と **`failure_patterns[]`（症状／原因／対処）** という2つの構造化データモデルが定義済みであり、これらに対応する登録UIが存在しなかった。本節は本文入力を**「Q&A形式」「手順（Step-by-Step）形式」「トラブル・事例形式」の3タイプ**に拡張し、既存のデータモデルと入力UIを一致させるための追加要件である。現場担当者が主語や背景を省略せずに入力できることを目的とし、生成される構造化データ（JSON＋メタデータ付きテキスト）でRAGの検索精度を高める。

> [!note] 既存モデルとの対応関係
>
> | 新タイプ | 対応する既存データモデル | 備考 |
> | --- | --- | --- |
> | Q&A形式 | `question` / `answer`（§5.7.2 STEP4-A） | 既存のFAQ形式をそのまま流用 |
> | 手順（Step-by-Step）形式 | `Recipe`（レシピマスタ／[[RAGシステム仕様]] 運営サポート機能①） | タイトル・前提条件・ステップ配列を登録UIとして具体化 |
> | トラブル・事例形式 | `failure_patterns[]`（[[RAGシステム仕様]] ③よくあるミス・失敗パターン） | 発生現象／原因／解決手順を症状／原因／対処に対応させる |

**① 登録タイプ選択タブ**

画面上部にタブを配置し、3タイプを切り替える。タイプ切替時は本文フォームのみが差し替わり、②メタデータ設定領域は共通で維持する。

| タブ | 想定される登録内容例 |
| --- | --- |
| Q&A形式（一問一答型） | 「Uiiの使い方は？」等、単発の質問への対応 |
| 手順（Step-by-Step）形式 | 草刈機の始動手順、まかない調理の手順 |
| トラブル・事例形式 | 「エンジンが止まった」等、現場トラブルの再現可能な対処記録 |

**② メタデータ設定領域（3タイプ共通）**

既存の `target_role`（§5.7.2 STEP1）・`category_id`（STEP2）を、現場担当者が迷わず入力できるよう以下の粒度で再構成する。

| 項目 | 入力形式 | 選択肢例 | 既存フィールドとの関係 |
| --- | --- | --- | --- |
| 業務領域（`domain`） | ドロップダウン（単一選択） | ホテル予約管理／飲食・接客／農業・機器操作／その他 | [[業務カテゴリ体系とAIエージェント設計]] の15業務ドメインへ正式マッピングする（UIの選択肢はラベルを平易化した簡略版） |
| 分類カテゴリ（`category`） | ドロップダウン（単一選択） | システム操作／クレーム・例外対応／機械トラブル・メンテナンス | 既存 `category_id`（STEP2）の下位分類として扱う |
| 対象者・権限（`target_audience`） | チェックボックス（複数選択） | 全員（新人含む）／店舗管理者のみ | §5.7.2 の `target_role`（ラジオ・単一値）と**選択方式が異なる**。下記 [!important] を参照 |
| 関連機器・ツール名 | テキスト入力 | 例：芝刈り機-GX200 | 既存 `keywords[]`（STEP3）へ自動追加する新規サブフィールド |

> [!important] `target_audience`（複数選択）と `target_role`（アクセス制御キー・単一値）の整合が必要
> §5.7.2 では `target_role` を**単一値のアクセス制御キー**と定義し、「プロンプト指示ではなく検索段階のメタデータフィルタで内部専用ナレッジの漏出を防ぐ」ことを必須要件とした（§5.7.5）。本節のUIは対象者を**チェックボックス（複数選択）**で受け付けるため、そのままでは「1件のナレッジが同時に複数ロールへ公開される」ケースを表現できない。
> 参照実装（[[ナレッジ登録UIコンポーネント_KnowledgeRegistrationForm]]）では、**`target_role` を配列化し（`target_role: string[]`）、検索時は配列包含判定（例：`target_role @> ARRAY[role]`）でフィルタする案**を暫定採用した。バックエンド未確定の設計案であり、正式決定は **§9 #29** で管理する。

**③ 本文入力領域（タイプ別可変フォーム）**

| タイプ | 入力項目 |
| --- | --- |
| Q&A形式 | 質問（Q）／回答（A） |
| 手順形式 | タイトル／前提条件／Step（**動的に追加・削除可能**な配列入力） |
| トラブル事例形式 | 発生現象／原因／解決手順 |

**④ UX・入力サポート機能**

- **リアルタイムヒントパネル**：入力中のタイプに応じて「⭕ 良い入力例」「❌ 悪い入力例」を画面右側に常時表示する。悪い例は「これ／それ」等の指示語や、主語（誰が・どの機材か）を欠いた記述を典型例として示し、§5.7.1 の設計方針（暗黙知の形式知化・Situated Actionの明示）を入力時点で体感させる。
- **「✨ AIで文章を整頓する」ボタン**：クリック時に文脈補完・整形サンプルを注入する。Phase 1では実際のAI API呼び出しは行わず、**疑似的な整形サンプルの注入（フロントエンドのみの挙動）**とする。実AI整形へ置き換える場合は、§5.7.4 の朝会パイプラインと同様に既存のGemini API呼び出しへ相乗りできないか検討する（呼び出し回数を増やさないため）。

**⑤ 送信・JSONプレビュー**

#### 5.8.2 STEP 1：Excelデータの一括事前登録（インポート）

1. 運営管理画面（PCダッシュボード）から「親方・街人リスト（CSV/Excel）」をアップロードする。
2. **列マッピング画面**でExcel列と会員マスタ項目を対応付ける（列順・列名の揺れを吸収するため固定フォーマットを前提としない）。
3. **取込プレビューと検証**：必須項目の欠落、`contact_info` の重複、既存会員との衝突を一覧表示し、**取込前に差し戻せる**ようにする。
4. 確定すると `account_status = 'pre_registered'`（初回ログイン待ちの空枠）として会員アカウントを生成する。
5. 取込結果（件数・成功／スキップ／エラー理由）をログとして保存する。

#### 5.8.3 STEP 2：予約・初回アクセス時の自動名寄せ

- **照合キー**：`contact_info`（メールアドレス／電話番号）を第1優先、次いで氏名＋誕生年月の組み合わせ。
- 外部宿泊予約フォーム連携時、または初回LINE連携時に、事前登録データと自動照合する。
- **一致した場合**：「〇〇さん、おかえりなさい！」と表示し、宿泊チケット数・Uii残高・XP・街人ステータスを引き継いだ状態で起動する。ユーザーは `[ このデータで連携して開始する ]` を押すだけで完了し、**再度30,000円の登録フローを通る必要はない**（§5.10）。
- 連携完了時に `account_status` を `active` へ更新する。

> [!success] 照合キーを持たない会員の扱い 確定（2026-08-14 ／ §9 #2・#16）
> 受領した実データでは、**街びとの61件（メール欠損）と親方衆44名（連絡先列そのものが無い）＝計105名が照合キーを持たない**。これらについては**事前の連絡先整備を行わず、次回チェックイン時に現地で電話番号を入力してもらう**方式で確定した。
> - 105名は取込時 `account_status = 'pre_registered'` のまま保持し、**来訪するまで連携しない**
> - チェックイン画面（店員タブレット）に「連絡先未登録」バッジを表示し、スタッフが本人の目の前で電話番号を入力する
> - 対面入力であるため、入力と同時に `is_verified = true` としてよい（スタッフが本人を認識しているため、リモート照合より確実）
> - **招待コードの事前一括配布は行わない。** そもそもメールを持たない会員へコードを届ける手段が郵送か対面しかなく、対面で渡すなら対面で登録した方が早い
> - 詳細な項目設計は [[会員データモデル_ユーザーテーブル定義]] §5.3・§6.3 を参照

> [!warning] 誤名寄せの防止（必須要件）
> 名寄せの成立は他人の宿泊チケット・Uii残高・XPの引き継ぎを意味するため、**照合一致のみで自動連携させてはならない**。以下を必須とする。
> - 同姓同名・家族間での連絡先共有を想定し、**候補が複数件ヒットした場合は自動連携せず運営承認キューへ回す**
> - 事前登録データへの初回紐付け時は、**招待コード（運営が個別配布）またはメール／SMSのワンタイム認証**による本人確認を必須とする
> - 名寄せの成立・解除は監査ログ（誰が・いつ・どのレコードを・どの根拠で）に記録する
> - 連絡先を持たないゲストの同定方式は §9 #2 の未決事項として継続

#### 5.8.4 STEP 3：再訪チェックイン時の現場アラート

宿泊者が予約完了、または現地でワンタップ／QRチェックインをした瞬間、店舗用タブレット・管理者PCのダッシュボードへリアルタイム（Supabase Realtime）で通知する。

```text
🔔 再訪アラート
「街人の〇〇（親方ステータス）さんがチェックインしました」
 ・通算滞在：〇回目 ／ 残チケット：〇泊
 ・得意スキル：農作業・左官
 ・運営メモ：〇〇の件で相談可能
```

これによりスタッフ間の情報共有、個別のおもてなし、スキルに応じたクエスト依頼が即座に行える。**表示先は管理者・コアメンバー画面に限定**する（運営メモ・氏名を含むため）。

#### 5.8.5 宿泊日数の運営制御（2026-08-13 レビュー追加）

宿泊日数は自動計算のみに委ねず、**運営が明示的に制御できる**ものとする。

| 要件 | 内容 |
| --- | --- |
| **初期入力** | 顧客情報の登録時（インポート時・新規登録時の双方）に、保有宿泊日数／チケット数を**初期値として入力**する |
| **運営による手動増減** | 管理者・コアメンバーが顧客管理画面から宿泊日数・チケット数を加算／減算できる（出資追加、特例付与、誤登録の訂正、イベント招待枠等） |
| **理由入力の必須化** | 増減操作時は理由の入力を必須とする（§5.6.4 の編集理由必須ルールに準拠） |
| **調整ログ** | 誰が・いつ・誰の宿泊日数を・いくつからいくつへ・なぜ変更したかを監査ログに保存し、顧客詳細から閲覧可能とする |
| **本人への反映** | 変更はマイログの宿泊履歴に「運営により調整（日時）」として表示し、相互確認できる状態にする |
| **消費との整合** | チェックアウト時の自動消費（滞在日数分の減算）と手動調整の2系統が同一残高に作用するため、**残高は取引履歴の積み上げ（イベントソーシング）で算出**し、直接上書きしない |

#### 5.8.6 ★ 会員権の満了・失効処理（2026-08-15 決定 ／ §9 #21）【Phase 2 以降】

> [!info] 本節は Phase 2 以降の実装範囲（2026-08-15 決定）
> **最初の満了は 2027/4/30**（第一弾237名）であり、Phase 1（2026年7〜8月）の稼働期間中に失効イベントは発生しない。そのため**有効期限のUI表示・一括失効バッチはいずれも Phase 2 以降**とする。
> ただし `memberships.expires_on` / `status` の**スキーマは Phase 1 で用意する**（後からカラムを追加するとデータ全件の見直しになるため）。以下は Phase 2 着手時の仕様として記載する。

**会員権が満了した時点で、未使用の宿泊券も併せて失効させる。**（会員との合意済み）

| 項目 | 仕様 |
| --- | --- |
| 権利期間 | 第一弾は**満了日 2027/4/30 固定**（期中加入者も同日）。第二弾は**開始日＋24ヶ月** |
| 満了時の会員権 | `memberships.status` を `権利期間中` → **`失効`** へ更新 |
| 満了時の宿泊券 | 未使用残を **`expiry`（失効）トランザクション（−）** として計上し、残高を 0 にする。**行の削除・残高の直接上書きは行わない**（§7 の集計キャッシュ方針に準拠） |
| 実行方式 | 日次バッチで満了日到来分を検出して一括処理。**2027/4/30 に237名分が一斉に満了する**ため、件数に耐える設計とすること |
| 監査 | 失効処理は対象会員ID・失効泊数・実行日時をログに残し、後から「いつ・何泊消えたか」を追跡できるようにする |
| 例外 | 運営が個別に延長する場合は `memberships.expires_on` を更新し、理由を記録する（§5.8.5 の調整ログと同様） |

> [!important] 失効させるなら、有効期限を必ず見せること
> 会員との合意が取れていても、**本人が「いつまでに何泊使えるか」を確認できない状態で失効させると現場で必ず揉めます。** 以下をUI要件とする。
> - マイページ・マイログに**残泊数と併せて有効期限を常時表示**する
> - 顧客管理画面の顧客サマリーヘッダーにも有効期限を表示する（§5.6.1①）
> - 失効後は「失効済み（日付）」と履歴に残し、残高が黙って消えたように見せない
>
> 満了前の事前通知（リマインド送付）の要否は運用判断だが、**237名が同日に失効する**ため、通知しない場合の問い合わせ集中は想定しておくこと。

通常ユーザー（一般会員・ゲスト）の画面からは、無関係なメニュー・タブを**完全に排除（非表示化）**し、「摩擦ゼロ」で直感的に操作できるUIを実現する。

| マイページ（XP・バッジ・滞在履歴） | ◯ | ◯ | ◯ | ◯ |
| ~~AIコンシェルジュ（FAQチャット）~~ | — | — | — | — |
| 店員用タブレット（代理注文／SOLDOUT） | **非表示** | **非表示** | ◯ | ◯ |
| クエスト承認・査定画面 | **非表示** | **非表示** | ◯ | ◯ |
| ナレッジ登録フォーム（§5.7） | **非表示** | **非表示** | ◯ | ◯ |

| ロール切替プレビュー機能（デモ・検証用） | **非表示** | **非表示** | **非表示** | ◯ |

> [!note] 「AIコンシェルジュ（FAQチャット）」行は#31により無効（2026-08-16）
> 浮遊街アプリ本体はエンドユーザー向けAIチャットUI（アプリ内コンシェルジュ）を持たない。街人・ゲストへの
> AI案内はLINE（line-rag-bot）に一本化し、アプリ内タブとしては提供しない。

> ゲストのクエスト参加は §6 権限マトリクスの「〇（限定あり）」と同義。ゲスト・長期滞在者もクエストボードの閲覧・受注申請（限定範囲）が可能であり、街人登録により対象クエストの範囲が広がりXP・貢献バッジも貯まる（§5.10）。

#### 5.9.2 クライアントサイドの動的非表示（Next.js / React）

- ログインユーザーの `role`（`admin` / `core_member` / `member` / `guest`）を判定し、権限外のタブバー・ナビゲーション要素を**DOMから除外**する（`display:none` による視覚的非表示ではなく、要素自体を描画しない）。
- **ロール切替プレビュー用スイッチも、通常ユーザー画面ではコンポーネントごと描画しない。**
- **モックと本番の切り分け（2026-08-14 決定）**：HTMLモック／プロトタイプでは、検証の利便のため**滞在中／滞在外バッジがデモ用の切替スイッチを兼ねる**運用を継続してよい。**本番実装ではロール切替を管理者（`admin`）のみに限定**し、それ以外のロールでは要素ごと描画しない。

#### 5.9.3 サーバサイド認可（必須・二重防御）

> [!danger] DOM非表示は認可ではない
> クライアント側の非表示処理は**UXのための施策であり、セキュリティ境界ではない**。DOMからの除去だけでは、APIを直接叩く／JSを改変する経路で内部データ（運営メモ・氏名・査定基準・未会計情報）が取得できてしまう。以下を必須要件とする。
> - **Supabase Row Level Security（RLS）** により、テーブル単位・行単位で `role` に基づくアクセス制御をかける
> - ナレッジ検索は `target_role` によるメタデータフィルタを**サーバ側で強制**する（§5.7.5-④）
> - 画面ガードとAPI認可は**同一のロール定義（単一のソース・オブ・トゥルース）**を参照し、二重管理しない
> - Firebase Storage 側の認可も同じロール体系で揃える必要がある（§9 #9）

#### 5.9.4 アクセス制限画面（Guardコンポーネント）

権限のないユーザーが直リンク等で専用URLへアクセスした場合、**プレビュー・コンテンツを一切レンダリングせず**、以下の画面を表示する。

```text
+--------------------------------------------------+
|                                                  |
|                   🔒 アクセス制限                 |
|                                                  |
|       この画面は管理者・コアメンバー専用です。      |
|    お持ちのアカウントではこのページを閲覧できません。 |
|                                                  |
|               [ ホームへ戻る ]                    |
|                                                  |
+--------------------------------------------------+
```

実装上は、認可判定が完了するまで**中身をマウントしない**（ローディング中に一瞬コンテンツが見える「フラッシュ」を起こさない）こと。

#### 5.10.2 Step 1：インフォメーション ＆ 入力

| 項目 | 内容 |
| --- | --- |
| タイトル | 🌿 街人（メンバー）に登録して浮遊街をもっと楽しもう |
| 料金 | **30,000円** |
| 特典1 | **宿泊券4枚（4泊分）を登録時に付与**（街への滞在権利） |
| 特典2 | **コインキャッシュバック 5,000 を付与** |
| 特典3 | すべてのクエスト受注・申請が解禁（農作業、DIY、まかない補助など全領域） |
| 特典4 | XP（経験値）・貢献バッジ・Uii（地域通貨）が貯まる |
| 入力欄 | ニックネーム（アプリ内表示名）／メールアドレス・電話番号／誕生年月（概算） |
| アクション | `[ 登録内容を確認する ]` |

> 画面文言では「決済」ではなく**「申請」**と表現する。この時点では課金が発生せず、実際の決済は管理者からのQR送付後に行われるため。「申請したのに請求が来ない」「押した瞬間に課金された」という双方向の誤解を防ぐ。

#### 5.10.3 Step 2：確認 ＆ 申請確定

- メッセージ：「以下の内容で街人登録を**申請**します。よろしいですか？」
- 確認事項：登録種別（街人）／登録料 ¥30,000／付与内容（**宿泊券4枚 ＋ コインCB 5,000**・全クエスト解禁）
- 補足表示：「**お支払い方法は、運営から決済用QRコードをお送りします。**この画面ではお支払い情報の入力は不要です。」
- アクション：`[ 承認して申請する ]`
- **2段階（入力 → 再確認）とすることで、誤タップによる申請を防止する。**
- 申請確定時、`街人登録申込` レコードを `申込中` で作成し、**同一ユーザーの申込中レコードが既に存在する場合は新規作成せず既存を表示**する（二重申請の防止）。

#### 5.10.4 Step 3〜5：管理者によるQR送付・入金確認・承認

| Step | 操作者 | 内容 |
| --- | --- | --- |
| 3 | 管理者 | 管理画面の「街人登録 申請一覧」から対象を選び `[ 決済QRを発行・送付 ]`。送付経路はLINE／アプリ内通知／対面提示から選択。QRトークンは §5.6 の精算トークンと同一基盤で発行し、**有効期限と失効フラグ**を持つ |
| 4 | ユーザー | 受領したQRを読み取り決済する（決済処理自体はアプリ外＝eumo/既存決済経路で完結） |
| 5 | 管理者 | 入金を確認し `[ 決済を確認して街人登録を完了する ]` を押下。**この承認操作をもって登録成立**とする |

- 各Stepの遷移時刻・操作者を `街人登録申込` レコードに記録し、監査可能とする。
- 申請から一定期間（例：14日）承認されない申込は `保留` へ自動遷移し、管理画面にリマインド表示する（申請の滞留防止）。
- 却下する場合は理由を入力し、ユーザーへ通知する。

> [!note] なぜ「決済完了」ではなく「管理者の承認」を成立条件とするか
> 決済がアプリ外（QR経由）で完結するため、**システムは入金イベントを自動検知できない**。したがって権限昇格のトリガーは管理者の明示的な承認操作とする。将来 eumo API 等で入金通知を受け取れるようになれば、この承認を自動化できる余地を残す設計とする。

#### 5.10.5 完了処理 ＆ ロック解除

1. 管理者の承認をもって、バックエンドで `role` を `guest` → `member` へ更新する。
2. **宿泊券4枚（4泊分）を付与**し、宿泊日数調整ログへ種別「街人登録による付与」として記録する（§5.8.5）。付与数は `membership_plans` マスタから取得し、コードに直書きしない。
   - **コインCB 5,000 の付与は Phase 1 ではシステム化しない**（#22 により個人残高管理は Phase 2）。**運営が従来どおりExcelで付与記録を行う**。画面上は特典として表示するが、残高への反映は手動運用となる点に注意すること。
3. 画面上のロックアイコン（🔒）を全解除し、クエストが即時に閲覧・受注可能となる状態変化をアニメーションで提示する。
4. 既存会員（`pre_registered` から名寄せされたユーザー）は**本導線を通さない**。名寄せ完了時点で `member` として起動する（§5.8.3）。

#### 5.10.6 ★ ロッククエストによる登録導線（§9 #13 確定）

ゲストに開放するクエストは、クエストマスタの **`guest_allowed`（真偽値）** で運営が明示制御する。カテゴリや `execution_mode` からの導出は行わない（安全ゲートである `required_certification` と判定が混線し、資格が必要な作業をゲストに開放してしまう事故を防ぐため）。

| 条件 | ゲスト画面での表示 |
| --- | --- |
| `guest_allowed = true` | 通常表示。閲覧・受注申請が可能 |
| `guest_allowed = false` | **一覧には表示したうえで施錠表示**。カードに `🔒 街人登録で解放` バナーを重ね、申請ボタンは非活性 |
| `required_certification` 未保有 | `🚧 受注できません`（資格ゲート。街人登録では解放されないため、登録導線は出さない） |

- 施錠カードをタップすると §5.10.1 の Step 1 モーダルを起動する。
- クエスト一覧の上部に、解放されるクエスト件数を示す常設バナー（例：`🔒 あと12件のクエストが街人登録で解放されます`）を配置し、登録動機を可視化する。
- サーバ側でも `guest_allowed = false` のクエストに対するゲストの受注申請APIを拒否する（表示制御のみに依存しない）。

> [!important] §5.9 の「非表示」原則との使い分け
> §5.9 では権限外のメニューを**DOMごと非表示**とするが、本節はその**逆**で、権限外のクエストを**あえて見せて施錠する**。両者は目的が異なるため、実装時に混同しないこと。
> - **管理・運営機能（§5.9）** → 存在ごと隠す。目的は**セキュリティと画面のノイズ削減**。見せる価値がなく、見せること自体がリスク
> - **会員特典（本節）** → 見せて施錠する。目的は**登録への動機づけ**。「登録すると何ができるようになるか」が伝わることが導線の価値
> ただし施錠表示するクエストであっても、**詳細な内容（報酬額・指示内容・担当者情報）はゲストに返さない**。カード上はタイトル・カテゴリ・施錠状態までに留める。

### 5.11 ★ メディア（画像・動画）ストレージ ＆ おすすめ表示（2026-08-13 レビュー反映）【Phase 2 以降】

> [!info] 本節は Phase 2 以降の実装範囲（2026-08-15 決定）
> メディアのアップロード・おすすめ表示は **Phase 2 以降**へ移送した（§4 スコープ切り分け）。
> ただし **§5.11.2 の「認可を二重化しない」原則（Firebase Auth / Security Rules を使わない）は Phase 1 から適用**する。Phase 1 でも朝会音声の格納（§5.1②）でストレージを使うため、ここで認可方式を分岐させると後から統合できなくなる。

#### 5.11.1 選定：Cloud Storage for Firebase

画像（Before/After写真、施設・店舗写真、ナレッジ添付）および動画（作業アーカイブ等）の格納庫として **Cloud Storage for Firebase（バックエンドは Google Cloud Storage）** を採用する。

| 選定理由 | 内容 |
| --- | --- |
| **メタデータ付与の柔軟性** | アップロード時にカスタムメタデータ（`uploadedBy` / `questId` / `location` / `takenAt` / `contentType` 等）をKVで付与でき、ストレージ単体でもオブジェクト属性を判定・操作できる |
| **オートスケール** | 従量課金（Blazeプラン）のマネージドサービスであり、**容量追加設定やサーバ増設なしに、容量・転送量の増加に応じて自動的にスケールする** |
| **サーバ負荷の回避** | クライアントから直接アップロードするため、大容量の画像・動画でもAPI層のタイムアウト・負荷が発生しない |

#### 5.11.2 ★ 認可を二重化しないアーキテクチャ（§9 #9 確定）

**方針：格納は Firebase に一本化し、認可判定は Supabase に一元化する（署名付きURL方式）。**

Firebase Security Rules の `request.auth` は Firebase Authentication を前提とするため、素直に使うと「Supabase Auth と Firebase Auth」という**認証・認可の二系統**が生まれる。これを避けるため、以下を**設計上の不可侵ルール**とする。

| # | 不可侵ルール | 理由 |
| --- | --- | --- |
| 1 | **Firebase Authentication を導入しない** | ユーザー識別子とロールの所在を Supabase 1箇所に保つ |
| 2 | **Firebase Security Rules に認可ロジックを書かない** | ルールは「全拒否」のみとし、判定ロジックの二重管理を発生させない |
| 3 | **GCSバケットは公開アクセス全面禁止**（Uniform bucket-level access） | 署名付きURL以外の経路を物理的に塞ぐ |
| 4 | **ロール判定の実装箇所は Supabase（RLS ＋ Edge Function）のみ** | 単一のソース・オブ・トゥルース。§5.9.3 の認可方針と完全に同一 |

```text
[クライアント (App / Web)]
   │
   │ ①-a 「アップロードしたい」＋ Supabase JWT
   ├──────────────────────────► [Supabase Edge Function]
   │                                  │ ロール判定・用途タグ検証
   │                                  │ サイズ/contentType検証
   │ ①-b 署名付きURL(PUT/10分)         │ media_assets に pending 作成
   │ ◄────────────────────────────────┘
   │
   │ ② ファイル本体を直接PUT（API層を経由しない）
   ├──────────────────────────► [Cloud Storage (Firebase/GCS)]
   │                                  │
   │                                  │ ③ Object Finalize イベント
   │                                  ▼
   │                            [Cloud Functions]
   │                              ・サムネイル生成／トランスコード
   │                              ・Exif（撮影日時・GPS）抽出
   │                              ・Vision API タグ付け
   │                                  │ ④ 結果を書き戻し（pending → ready）
   │                                  ▼
   │                            [Supabase / PostgreSQL]
   │                              media_assets（メタデータの正）
   │
   │ ⑤ 「閲覧したい」＋ Supabase JWT
   ├──────────────────────────► [Supabase Edge Function]
   │                                  │ 公開範囲 × ロールを照合
   │ ⑥ 署名付きURL(GET/5分)            │
   │ ◄────────────────────────────────┘
   ▼
 直接ダウンロード ────────────► [Cloud Storage]
```

| # | 処理 | 内容 |
| --- | --- | --- |
| ① | アップロードURL発行 | Supabase Edge Function がロール・用途タグ・`contentType`・サイズ上限を検証し、**V4署名付きURL（PUT／有効期限10分／`contentType` 固定）**を発行。同時に `media_assets` へ `pending` レコードを先行作成 |
| ② | 直接アップロード | クライアントが署名付きURLへ直接PUT。**ファイル本体はAPI層を通らない**ため、大容量でもタイムアウト・サーバ負荷が発生しない |
| ③④ | 非同期後処理（Cloud Functions） | Object Finalize イベントで起動し、サムネイル生成、WebP/MP4変換・トランスコード、Exif抽出、Vision APIタグ付けを実行。結果を Supabase へ書き戻して `ready` に更新 |
| ⑤⑥ | 閲覧URL発行 | Edge Function が `media_assets` の公開範囲とユーザーロールを照合し、**短命（5分）の署名付きGET URL**を発行。内部専用ナレッジの添付は有効期限をさらに短く（2分）する |

> [!note] クライアントからの「完了通知」に依存しない理由
> アップロード完了の記録を**クライアントの完了通知ではなく、GCSのObject Finalizeイベント（③）を起点**とする。通信断やアプリ離脱で完了通知が届かないと、ストレージには実体があるのにDBに記録がない「孤児ファイル」が残り、課金だけが発生し続けるため。逆に `pending` のまま一定期間（例：24時間）実体が現れないレコードは、定期ジョブで自動削除する。

**この方式で満たされる要件**

| 要件 | 満たし方 |
| --- | --- |
| メタデータの仕込み | GCSカスタムメタデータ ＋ **Postgres の `media_assets` を正**とする二段構え。検索・集計はSQLで行えるため、おすすめ表示（§5.11.3）の実装が容易 |
| オートスケール | GCS（Blazeプラン）の従量課金でそのまま享受。§5.11.4 のライフサイクル・予算アラートも制約なく利用可 |
| セキュリティ | 認可は Supabase 側の単一実装。バケットは公開禁止で、署名付きURL以外の経路が存在しない |
| 認可基盤の非二重化 | Firebase Auth・Security Rules を**使わない**ことで達成 |

> [!warning] 本方式のトレードオフ（許容する）
> - **URL発行の往復が1回増える**（レイテンシ数十ms程度）。ただしファイル本体は経由しないため帯域・タイムアウトの問題は生じない。既存の非機能要件「画面応答3秒以内」に対して十分な余裕がある
> - **署名付きURLは失効までURLを知る者ならアクセスできる**。そのため有効期限を短く設定し（閲覧5分／内部専用2分）、URLをログや外部サービスへ残さない運用とする
> - **Cloud Functions から Supabase への書き戻しにサービスロールキーが必要**。キーは Secret Manager で管理し、Functions のみに権限を限定する
> - 公開画像（メニュー写真等）にCDNキャッシュを効かせたい場合は、**非公開バケットとは別に公開バケットを分離**する。混在させると署名付きURLの意味が失われるため

#### 5.11.3 用途タグと「おすすめ表示」（2026-08-13 レビュー追加）

アップロードした画像・動画を、**用途に合わせて自動的に推薦表示**する。

| 項目 | 内容 |
| --- | --- |
| 用途タグ（`media_purpose`） | アップロード時に選択（例：クエスト報告／施設紹介／作業手順の補足／メニュー写真／イベント記録／ナレッジ添付） |
| 紐付けキー | `category_id` ／ `quest_id` ／ `knowledge_id` ／ `place_id` ／ `usage_scene[]` |
| **おすすめ表示ロジック** | 表示中のコンテキスト（開いているクエスト・ナレッジ・カテゴリ・利用シーン）と、メディアの用途タグ・紐付けキーを突き合わせ、**一致度の高い順に候補を提示**する |
| 適用箇所 | ①ナレッジ登録時の添付候補サジェスト ②AI回答への画像・動画の自動添付 ③クエスト詳細の参考画像 ④施設・メニュー紹介 |
| Phase | メタデータ蓄積が前提のため、**アップロード＋タグ付与を Phase 1**、推薦ロジックを Phase 1.5 以降とする |

> 将来的には Vision API による自動タグ付け（②の後処理）と、テキスト埋め込みによる画像説明文のベクトル検索を組み合わせ、「〇〇のやり方」という質問に対して手順写真を自動添付する構成へ拡張できる。

#### 5.11.4 オートスケールとコスト制御

| 項目 | 内容 |
| --- | --- |
| **オートスケール** | 無料枠（5GB）超過後は従量課金（Blazeプラン）へ自動移行し、上限なくスケールする。運用側での容量追加作業は不要 |
| **予算アラート** | Google Cloud コンソールで月額予算（例：5,000円）を設定し、予測消費額の到達時に運営・管理者へ通知する |
| **ライフサイクルルール** | 動画・高解像度画像の蓄積によるコスト増を防ぐため、経過日数に応じてストレージクラスを自動転送する（30〜90日経過で Nearline / Coldline / Archive へ移動） |
| **一時ファイルの自動削除** | サムネイル生成前の一時ファイル、失敗したアップロードを一定期間後（例：7日）に自動削除する |

#### 5.11.5 セキュリティ・アクセス制御

認可判定はすべて Supabase Edge Function 側で行う（§5.11.2）。Firebase Security Rules には認可ロジックを置かない。

| 制御項目 | 実装箇所 | 内容 |
| --- | --- | --- |
| 認証済みユーザーのみ許可 | Edge Function | Supabase JWT の検証。未認証リクエストには署名付きURLを発行しない |
| ロール別のアップロード可否 | Edge Function | §6 権限マトリクスに準拠（会員・ゲストは自身のクエスト報告等に限定） |
| ファイルサイズ上限 | Edge Function ＋ 署名付きURL | 署名付きURL発行時に `x-goog-content-length-range` を指定し、**上限超過をストレージ側で拒否**する（クライアント側検証のみに依存しない） |
| `contentType` の制限 | Edge Function ＋ 署名付きURL | 署名に `contentType` を固定し、実行可能ファイル等の投入を防ぐ |
| **公開範囲の継承** | `media_assets` | 内部専用ナレッジの添付ファイルは、**ナレッジ本体の `target_role` を継承**する。本文は非公開なのに画像URLだけ辿れる、という穴を作らない |
| バケットの直接アクセス禁止 | GCS設定 | Uniform bucket-level access ＋ 公開アクセス全面禁止。署名付きURL以外の経路を残さない |

> [!important] 朝会音声も本基盤へ統合する
> §5.1 ② では音声ファイルの送信先を Supabase Storage としていたが、本決定に伴い**統一メディア基盤（Cloud Storage for Firebase）へ変更**する。ストレージが1系統に収まるうえ、Gemini（Vertex AI）は GCS URI を直接入力として扱えるため、音声処理の経路も短くなる（非機能要件「録音終了から60秒以内」に有利）。

> 本表は**機能・操作の可否（認可）**を定義し、§5.9.1 は**画面上のタブ・メニューの表示可否（UI）**を定義する。両者は同一のロール定義を参照する必要があるが、**「非表示」は「不許可」を意味しない**点に注意（表示していなくてもAPIが叩ければ操作できてしまう）。認可の実効性は §5.9.3 のサーバサイド制御で担保する。

## 8. 非機能要件

- **音声処理パフォーマンス**: 15分程度の朝会音声に対し、録音終了から文字起こし・議事録生成・クエスト抽出完了までを **60秒以内**（バックグラウンド処理）で完了させる。
- **操作マニュアルの整備・提出**: 一般ユーザー用および店舗・管理者用（朝会録音手順含む）の操作マニュアルを同梱。
- **UI/UX・マルチデバイス同期**: 代理注文時のチェックイン者フィルタリング、SOLDOUTトグルのリアルタイム反映。

**★ v1.10 追加（2026-08-13 レビュー反映）**

- **メディアストレージのオートスケール**: 画像・動画の格納には Cloud Storage for Firebase（Blazeプラン）を用い、**容量追加作業なしに自動拡張**されること。運用側での容量監視・手動拡張作業を発生させない（§5.11.4）。
- **ストレージのコスト制御**: 月額予算アラート（例：5,000円）を設定し、予測消費額の到達時に管理者へ通知。30〜90日経過した高解像度動画・過去ログのオリジナルデータは Nearline / Coldline / Archive へ自動転送。一時ファイルは7日で自動削除。
- **アップロード性能**: 画像・動画は**署名付きURLによりクライアントからストレージへ直接アップロード**し、ファイル本体がAPI層を経由しないこと。50MB程度のファイルでもAPIタイムアウト・サーバ負荷を発生させない（§5.11.2）。
- **ストレージ認可の単一化**: ロール判定の実装箇所を Supabase（RLS ＋ Edge Function）1箇所に限定する。**Firebase Authentication および Firebase Security Rules による認可判定を実装してはならない**（§5.11.2 の不可侵ルール）。
- **署名付きURLの有効期限**: アップロード用10分、閲覧用5分、内部専用ナレッジの添付は2分を上限とする。発行済みURLをログ・外部サービスへ残さないこと。
- **孤児ファイルの防止**: `pending` のまま24時間実体が確認できない `media_assets` レコード、およびDB未登録のストレージオブジェクトを定期ジョブで検出・削除すること（§5.11.2）。
- **認可の二重防御**: 画面上の非表示（クライアント）と、RLS・APIによるサーバサイド認可を**必ず両方**実装する。クライアント側の制御のみに依存した実装を禁止する（§5.9.3）。
- **ナレッジ検索の情報隔離**: `target_role` によるメタデータフィルタをサーバ側で強制し、内部専用ナレッジがゲスト・一般会員のAI回答に混入しないこと。**プロンプト指示による抑制を隔離手段としない**（§5.7.5）。
- **会員データインポートの再実行安全性**: 同一ファイルの二重取込が発生しても重複会員を生成しないこと（`contact_info` のユニーク制約と取込前プレビューで担保）。取込は原子的に実行し、途中失敗時は全件ロールバックする（§5.8.2）。
- **リアルタイム通知**: 再訪アラートは、チェックイン操作から**3秒以内**に管理者PC・店員タブレットへ反映されること（Supabase Realtime。既存の「画面応答3秒以内」に準拠）。
- **個人情報の表示制御**: 氏名・連絡先・運営メモは管理者・コアメンバー画面にのみ描画し、一般会員・ゲスト向けAPIのレスポンスに含めないこと。
- **★ 未使用宿泊券の集計（2026-08-15 追加）**: 任意時点（特に3/31・9/30）における**未使用宿泊券の総数および券面額換算の残高を集計・出力**できること。経営側が会計処理・資金決済法上の判断を行うための基礎データとなる（§9 #14）。**システムは判断を行わず、数値の提供に徹する。**
