# 要件定義書作成支援：浮遊街アプリ

### 🧑 User

添付の要件定義書を読んで下記を作成して 業務フローとシステム機能要件（As-Is / To-Be 比較） 業務フロー図・画面遷移図（テキスト構造定義） データモデル定義書（概念データモデル） 機能と権限のマトリクス リスク管理簿

### 🤖 Gemini

ご提示いただいた「浮遊街アプリ」および関連プロジェクトの構想資料に基づき、ご要望の5つの項目（要件定義・設計書を構成する主要要素）を作成いたしました。

##### 1\. 業務フローとシステム機能要件（As-Is / To-Be 比較）

**【As-Is（現状の業務と課題）】**

*

### 🤖 クエスト運営とUii管理

浮遊街におけるクエスト運営や、地域通貨「Uii」の運用は人手による運営負荷が高くなっています。
*

### 🤖 FAQ対応と情報案内

長期滞在者（メンバー）とゲスト（短期滞在者）に対する案内の階層構造が整理されておらず、手動でのコンテキスト切り替えが必要になっています。
*

### 🤖 リソースの偏り

誰がどのようなスキルを持っているかが可視化されておらず、特定のスキルを持った人が足りない時期（ボトルネック）が発生するリスクがあります。 **【To-Be（システム導入後と機能要件）】**
*

### 🤖 業務効率化とデジタル化

クエスト管理のデジタル化、FAQ自動回答、Uii運用支援をアプリ上で完結させ、運営の負荷を削減します。
*

### 🤖 スキルと貢献の可視化

スキルLv（1〜5）の可視化や職業ランク（称号）の付与を通じて、誰が何を得意としているかを明確にし、リソースの適切な配置とゲーム感覚の成長を促します。
*

### 🤖 AIによる自律支援

ユーザーの属性（メンバー・ゲストなど）を判定し、それぞれに応じた適切な解像度でFAQ案内や行動指針を自動応答します。

* * *

##### 2\. 業務フロー図・画面遷移図（テキスト構造定義）

**【クエスト実行・承認の業務フロー】**

1.

### 🤖 クエスト定義

運営管理者やコミュニティリーダーが、アプリ上でクエスト（内容、難易度、獲得XP、時期など）を新規登録します。
2.

### 🤖 クエストの受託・実行

一般会員がクエスト一覧からタスクを選択し、現地または遠隔で作業を行います。
3.

### 🤖 完了報告

実施者がアプリのフォーム経由で作業結果や資材のログを添付し、クエスト完了を報告します。
4.

### 🤖 承認・査定プロセス

コミュニティリーダーまたは査定員が報告を確認し、定量的な基準（作業時間や難易度）に基づいて承認を行います。
5.

### 🤖 情報更新

承認後、実施者の「マイページ」にUii残高や獲得XP、スキルレベルが反映され、新たな称号が付与される仕組みが回ります。 **【画面遷移の構成案】**

*   **\[認証・ログイン画面\]** （メール、Google、LINEログイン等）
    *   **\[マイページ\]**
        *   プロファイル情報（属性、スキルLv、職業ランク）
        *   自身のUii残高・獲得履歴の確認
        *   他会員への「推薦」送信機能
    *   **\[クエスト画面\]**
        *   クエスト一覧（季節やタスクカテゴリ別）
        *   クエスト詳細・受発注画面
        *   完了報告フォーム（作業内容、写真などの提出）
    *   **\[AIチャット画面\]**
        *   FAQ案内・質問（ユーザープロファイル判別による自動応答）
    *   **\[管理側ダッシュボード\]** （※運営・リーダー権限のみ）
        *   会員マスタ・Uii残高の一括管理
        *   クエストの新規登録・編集
        *   承認待ちクエストの査定、異常値検知時のエスカレーション対応

* * *

##### 3\. データモデル定義書（概念データモデル）

浮遊街AIおよび将来的なFEL（Favorite Earth Life）との連携を見据えた主要エンティティの構造定義です。

*

### 🤖 会員 (User/Member)

会員マスタID、氏名、入会日、基本属性、スキル・職業ランク。
*

### 🤖 拠点・施設 (Facility/Place)

拠点・施設マスタID、場所の静的プロファイル。
*

### 🤖 クエスト (Quest)

クエストマスタID、タスク定義、難易度、獲得XP、想定時期カレンダー。
*

### 🤖 作業ログ (WorkLog)

日時、作業内容、担当者、使用資材、進捗結果、FEL連携用メタデータ。
*

### 🤖 活動記録 (Activity/Interaction)

AI対話ログ、会員間での推薦・評価データ。
*

### 🤖 領域間参照テーブル

「会員 × スキル」「会員 × クエスト実績」「拠点 × 作業ログ」など、領域をまたいで紐付ける統合キー。

* * *

##### 主な追記・統合箇所

1.

### 🤖 業務フローと機能要件（As-Is/To-Be）

手動管理されていた「宿泊日数」や「滞在期間」のアナログ管理を課題として定義し、Uii決済やキャパシティ管理と自動連動させる要件を追加しました。
2.

### 🤖 フローおよび画面遷移

新たに「宿泊予約・滞在履歴確認フロー」を定義。会員用マイページからの予約遷移や、管理者ダッシュボードでの「滞在スケジュール・チェックイン承認タブ」の追加を構造化しています。
3.

### 🤖 データモデル定義（概念データモデル）

会員エンティティに 総保有宿泊日数 を付与し、拠点と会員を繋ぐ核心エンティティとして 宿泊・滞在ログ (StayLog / Reservation) を新規設計に組み込みました。
4.

### 🤖 機能と権限のマトリクス

「施設の宿泊・滞在状況一括管理・承認」および個人の「申請・履歴閲覧」に関する権限レベルを明文化しました。
5.

### 🤖 リスク管理簿

実滞在数との「データの不整合」リスクや、イベント期における「施設・キャパ管理」のダブルブッキングリスクを想定し、それぞれQRコード等を用いた実在確認や動的な制限バリデーションといった具体的な対応策をテーブルに追加しています。 上記リンクより詳細をご確認いただけます。システム設計の進展にぜひお役立てください。
