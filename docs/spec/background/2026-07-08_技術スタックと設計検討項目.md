ご提示いただいた技術要件の各項目について、現在までの浮遊街AIおよび関連プロジェクトの構想を整理し、検討すべき論点をまとめました。 \[cite\_start\]これらは「浮遊街AI」という特定のコミュニティ支援ツールから始まり、将来的には他コミュニティへ展開可能な「汎用サポートAI」を目指すという全体ロードマップに基づいています\[cite: 101, 132\]。

* * *

##### 技術スタックおよび設計検討項目

###### 1\. 技術スタック選定 (DB, ホスティング, フロント実装)

*   **方針:** 現時点では開発スピードと柔軟性を最優先します。
*   \[cite\_start\] **考え方:** 浮遊街の運用の変化に追従できるよう、構成要素を疎結合にし、コンポーネントの入れ替えが容易な設計が求められます。特に「場所づくり」に関連するデータ（気象、土壌、作業ログなど）は、将来的にFEL側の設計と共通の型（スキーマ）にすることで、後の連携コストを抑えることが肝要です\[cite: 132, 191\]。

###### 2\. MCP (Model Context Protocol) コネクタの判断

*   \[cite\_start\] **現状:** Claudeを基盤とした対話エンジンを軸としているため、外部ツールやデータベースとの接続においてMCPの活用は非常に有効です\[cite: 101, 132\]。
*   **検討点:** 既存のコネクタでコミュニティの特殊なデータ（Uii残高、クエスト進捗など）を扱えない場合、カスタムMCPサーバーを構築する必要があります。まずは既存の汎用コネクタでプロトタイプを作り、独自ロジックが必要な箇所を順次切り出すアプローチを推奨します。

###### 3\. 権限・認証・セキュリティの設計

*   \[cite\_start\] **属性管理:** 会員（長期滞在者）とゲスト（短期・初回来訪者）で提供すべき情報の解像度が全く異なるため、ログイン処理や属性フラグを用いたアクセス制御が必須です\[cite: 151\]。
*   \[cite\_start\] **データ保護:** コミュニティ内の貢献度やスキル情報は個人資産であるため、特に推薦機能やXP付与といった信頼に関わるデータは、権限設定と合わせて監査可能な形での保存が求められます\[cite: 151\]。

###### 4\. Agent SDKによる自律実行範囲の設計

*   \[cite\_start\] **自律実行の制御:** AIが「運営」に代わって判断するクエスト承認やリソース配置において、人間が最終承認を行う「閾値（しきいち）」を定量的に設ける設計が必要です\[cite: 151\]。
*   \[cite\_start\] **監査基盤:** 「なぜその判断がAIによってなされたか」というプロセスを記録するログ基盤は、コミュニティ内の納得感を醸成するためにも極めて重要です\[cite: 151\]。

###### 5\. 将来のマルチテナント化を見据えた設計

*   \[cite\_start\] **抽象化:** 浮遊街固有のロジック（Uii通貨や特定の施設案内など）と、汎用的な機能（作業ログ管理、スキル可視化など）を最初から分離してコード化しておく必要があります\[cite: 101\]。
*   \[cite\_start\] **データモデル:** 土地や場所を「パラメータの組み合わせ」として抽象化（場所のDNAデータ定義）することで、浮遊街以外の場所でも同じシステムを適用できるように設計します\[cite: 179\]。

* * *

##### 今後のアクションへの推奨

\[cite\_start\]開発着手のフェーズにおいて、特に\*\*「データモデルの共通化」**は優先度を高く設定すべきです。データが溜まり始めた後に構造を変更するのはコストが非常に大きいため、今回のPhase0（要件定義・データ整備）の段階で、浮遊街の要件と将来の汎用化・FEL連携を見据えた項目の洗い出しを行うことを強く推奨いたします\[cite: 132\]。 ご提示いただいた各項目の詳細な設計書（構成図など）の作成や、より具体的な技術選定のシミュレーションが必要な場合は、いつでもお知らせください。 User : 1,2,5についてクリーンアーキテクチャで実装するだけじゃ甘い？ Gemini : 結論から申し上げますと、ご認識の通り**「クリーンアーキテクチャで実装するだけ」では、今回のプロジェクトの目的（特に将来のマルチテナント化やFELとの連携）を達成するには甘い（不十分である）可能性が高い**です。 クリーンアーキテクチャはあくまで「コードの依存関係を制御し、変更に対する耐性を高めるための 構造 」に過ぎません。今回のプロジェクトが抱える真の難所は、構造そのものよりも**「意味（セマンティクス）の共通化」と「マルチテナントを見越したメタデータ設計」\*\*にあります。 なぜ「クリーンアーキテクチャだけでは甘いのか」、補足すべき視点を整理しました。

##### 1\. クリーンアーキテクチャの限界と「補うべき設計」

クリーンアーキテクチャは「UIやDBを入れ替え可能にする」には最適ですが、今回の要件には以下の要素が欠けています。

*   **「意味（語彙）」の共通化（ドメインの境界）:** 浮遊街の「場所」とFELの「場所」を同じコードで処理する場合、単にレイヤーを分けるだけでなく、 **「場所」というエンティティそのものを、異なるコンテキスト（マルチテナント）でどう解釈するか** というセマンティックな設計が必要です。
*   **メタデータによる動的構成（マルチテナント対策）:** マルチテナント化では、ハードコードされたロジックを減らし、DBや設定ファイルでコミュニティ固有のルールを定義する「メタデータ駆動型設計」が求められます。クリーンアーキテクチャの範疇を超えて、 **「システムの設定値（設定情報）」と「システムが扱う対象（データ）」を分離する設計** が必要です。

##### 2\. 1, 2, 5に対するより踏み込んだアプローチ

クリーンアーキテクチャに加えて、以下の設計思想を注入することを強く推奨します。

###### ① 技術スタック選定 (1)

*   **甘いアプローチ:** フレームワークに依存したクリーンアーキテクチャ実装。
*   **深めるアプローチ:** **「データ転送形式（スキーマ）」の独立性確保。** 具体的には、JSON SchemaやProtocol Buffersなどを用いて、システムの内外でやり取りする「場所のデータ構造」を言語仕様から独立させます。これができていれば、将来別のサービスと統合する際、コンバータを一つ挟むだけで済みます。

###### ② MCPコネクタ判断 (2)

*   **甘いアプローチ:** 単純にMCPコネクタをインターフェースとして使う。
*   **深めるアプローチ:** **「MCPサーバーをコミュニティのゲートウェイとして設計する」。** MCPサーバーの中に、抽象化された「浮遊街API（MCPサーバー）」を作成し、実態（DBなど）を隠蔽します。これにより、マルチテナント化の際、テナントごとにMCPサーバーを切り替えるだけで済む設計にします。

###### ③ マルチテナント化を見据えた設計 (5)

*   **甘いアプローチ:** データベースのテーブルに tenant\_id を入れるだけ。
*   **深めるアプローチ:** **「場所のDNA定義」のモデル化。** 場所の特性（気候帯、土壌、地形など）を「コード」ではなく「メタデータ（構造化データ）」として扱い、AIがそのメタデータを読み込んで推論を実行する仕組みにします。これにより、AIのロジックを変更せずに、新しいコミュニティを追加（オンボーディング）できるようになります。

##### 3\. 今すぐやるべき「構造」以外の設計

クリーンアーキテクチャのコードを書く前に、以下のドキュメント（あるいは設計図）を整理することをお勧めします。

1.  **コンテキストマップ:** 浮遊街とFELのドメイン（場所、作業、コインなど）で、共通して扱う言葉と、別々で定義すべき言葉の境界線を引く。
2.  **メタデータスキーマ定義:** 「場所」という概念を表現するために必要な最小限のプロパティを、両者で合意しておく。（※これは「技術仕様書」ではなく「語彙の約束事」です）

##### まとめ

クリーンアーキテクチャは「土台（建物）」を作ることには優れていますが、今回のような「将来的に他所にも適用する（汎用化・マルチテナント）」という目的においては、\*\*「建物の中の家具（データ構造）をいかに共通規格にするか」**が鍵になります。 「コードのきれいさ」だけでなく、**「データのポータビリティ（持ち運びやすさ）」と「設定の外部化」**を設計の軸に追加してみてください。今の段階であれば、クリーンアーキテクチャを適用する前に「データ項目の型（語彙）の共通化」から着手するのが最も失敗の少ない順序です。 User : CursorやGithubアクションで記載、指定すべきルール Gemini : 「浮遊街AI」と将来の「FEL連携」を見据えたプロジェクトにおいて、Cursor（AIエディタ）やGitHub Actionsで設定すべきルールは、**「構造の純粋さの維持」と「ドメイン知識の言語化」**に焦点を当てる必要があります。 単に綺麗なコードを書くだけではなく、**「マルチテナント対応を見据えたメタデータ分離」\*\*を強制するルールを組み込むことが重要です。

* * *

##### 1\. Cursorへの指定ルール（.cursorrules）

CursorのAIが「将来の汎用化・マルチテナント化」を常に意識して回答するように、以下のルールを記述しておくことを推奨します。

*   **アーキテクチャ制約:**
    *   「すべてのドメインロジック（特に場所データやクエスト定義）は、UIやインフラ層から分離すること（クリーンアーキテクチャの徹底）。」
    *   「特定コミュニティ（浮遊街）固有のロジックは src/domains/floating\_city/ に隔離し、汎用的な src/domains/core/ に依存させないこと。」
*   **メタデータ設計の強制:**
    *   「新しいエンティティを作成する際は、必ず『設定値（メタデータ）』と『ロジック』を分離すること。ハードコーディングを避け、JSONやスキーマで制御できる構造にすること。」
*   **ドキュメント生成:**
    *   「コード変更時には、必ず該当するデータスキーマの定義を更新し、日本語でコメントを追記すること。」
*   **連携意識:**
    *   「『場所のDNAデータ』を扱う際は、常に『FEL連携構想』で定義された共通型スキーマとの互換性をチェックすること。」

* * *

##### 2\. GitHub Actionsへの指定ルール（自動ガードレール）

GitHub Actionsは、人間が忘れてしまいがちな「設計上の制約」を機械的に守らせるために使用します。

*   **アーキテクチャ境界の違反チェック:**
    *   archunit 等のライブラリ（またはシンプルなスクリプト）を用いて、core レイヤーが floating\_city レイヤーをインポートしていないかをチェックするタスクを走らせます。
*   **スキーマ定義の厳格化:**
    *   「データモデル（型定義ファイル）」が更新された際、以前のバージョンとの後方互換性が保たれているか（Breaking Changeがないか）を検証するタスクを組みます。
*   **ドキュメントの自動同期:**
    *   コード内のスキーマ定義（JSON Schemaなど）から、最新のデータ定義ドキュメントを自動生成し、レポジトリ内の docs/ にコミットさせる自動化を行うと、チーム間の仕様齟齬が減ります。

* * *

##### 3\. 具体的な .cursorrules 記載例（案）

以下のテキストを .cursorrules ファイルとしてプロジェクトルートに配置してください。

```markdown
# プロジェクト指針：浮遊街AI / FEL汎用プラットフォーム

- 原則：すべては「将来的な他コミュニティへの移植」を前提とする。
- 構造：クリーンアーキテクチャを厳守する。
  - domain層：ビジネスルールとエンティティのみ。フレームワーク依存禁止。
  - usecase層：アプリケーション固有のロジック。
  - interface層：コントローラーやMCPサーバー定義。
- コミュニティ分離ルール：
  - `src/core/`：汎用的なサポートAI機能。
  - `src/communities/`：特定のコミュニティ固有機能。
  - coreはcommunitiesを参照してはならない。
- データ設計：
  - 「場所のDNA（土地プロファイル）」はメタデータとして定義し、ロジックと分離すること。
  - 定数やコミュニティ固有のルールはハードコードせず、設定ファイル（YAML/JSON）から読み込むこと。
- 連携：
  - 「場所データ」を定義する際は、常にFELデータパートナー制度との互換性を考慮すること。

```

* * *

##### 次のアクションとしての推奨

これらのルールを導入することで、\*\*「浮遊街AIを作っている最中に、自然と汎用的なプラットフォームが出来上がっている」\*\*という状態を作れます。 もしよろしければ、\*\*現在想定しているフォルダ構成（ディレクトリ構造）\*\*をご提示いただければ、このルールに基づいた「具体的なフォルダ境界の設計」をレビュー・修正します。いかがでしょうか？
