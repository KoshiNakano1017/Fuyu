# EUMO連携の実現可能性と代替案

### 🧑 User

EUMOのAPIで連携できること

### 🤖 Gemini

浮遊街アプリにおける「ユーモ（eumo）」との連携について、現状の構想および技術的な観点から整理します。

##### 1\. eumo（ユーモ）のシステム基盤とAPI連携の前提

まず、eumoは独自のオープンなAPIを広く公開しているわけではなく、一般的には\*\*株式会社フィノバレーが提供する電子地域通貨プラットフォーム「MoneyEasy（マネーイージー）」\*\*を利用して構築されています。 そのため、「eumoのAPIと連携したい」という場合、単純に外部からREST APIを叩いて自由にデータをやり取りできるというよりは、以下のいずれかのパスを検討する必要があります。

*

### 🤖 プラットフォーム経由での連携

導入する地域通貨プロジェクトとして「MoneyEasy」側のシステム仕様に基づいた開発や連携を行う。
*

### 🤖 運営側との直接協議

eumo運営企業と提携・協業関係を結び、個別のシステム連携（Webhookの活用やデータ連携APIの開示など）について協議する。

##### 2\. ユーザーが想定している連携の実現可能性

ユーザーの構想資料およびチャット内容にある以下の連携ニーズは、技術的には「決済・送金データ」と「メタデータ」の突合になります。

*

### 🤖 クエスト完了データと送金の紐付け

浮遊街アプリ上のクエスト完了（報酬の発生）と、ユーモ上での送金をシステム的に突き合わせる必要があります。
*

### 🤖 消費メタデータの付与

「何のために使ったか（マッサージ、野菜など）」という情報を付与して決済するニーズですが、一般的な決済アプリの標準APIでメタデータを自由に埋め込めるケースは稀です。 **今後のステップとして推奨される検討事項：**

1.

### 🤖 「ユーモ連携」の定義を明確にする

*   ユーモ側を単なる「決済手段」として使うのか、それとも浮遊街アプリの「データ」とユーモの「通貨データ」を双方向で同期させたいのかを切り分ける必要があります。
    *   後者の場合、ユーモ運営（株式会社eumo）に対し、どの程度のデータ連携が許可されるかを確認する必要があります。
2.

### 🤖 代替案の検討（独自トークン運用との比較）

*   資料内で検討されている「独自通貨（Uii）」の運用とユーモをどう共存させるかです。独自通貨のシステムを自前で持つ（Supabase等のDBで管理）方が、ユーザーの要件（クエスト連動、詳細なメタデータ付与）を柔軟に実装できます。
    *   「3年後に独自通貨発行」という構想があるため、初期段階ではユーモとは「API連携」にこだわらず、ユーモでの決済完了画面のスクリーンショットをユーザーが浮遊街アプリにアップロードする（またはURLを貼る）といった\*\*「ローテクな連携」\*\*から始めてデータを蓄積し、必要に応じて将来的にシステム連携へ昇華させるのが、開発コストとリスクの観点から最も現実的です。

##### まとめ

EUMO（ユーモ）側に現時点で「自由に使用できる汎用API」があることを期待して設計するよりも、まずは\*\*「浮遊街アプリ内で完結するデータモデル（Uii管理）」を先行して作り込み、ユーモは決済手段の一つとして併用する**という運用フローを優先することをお勧めします。これにより、ユーモ側のAPI仕様に依存せず、アプリ開発のスピードを維持できます。 User : 浮遊街アプリの「データ」とユーモの「通貨データ」を双方向で同期させたい ユーモの残高を照会して浮遊街アプリに表示させたり、浮遊街アプリの操作の結果EUMOの残高を増やしたり減らしたり Gemini : ご提示いただいた「浮遊街アプリとeumoの通貨データ（残高）の双方向同期」という構想は、ユーザー体験としては非常に強力です。 しかし、技術的・運用的な観点から申し上げますと、 eumoのプラットフォーム（多くの場合、MoneyEasyという基盤システム）に対して、外部アプリから直接「残高を書き込む（増やす・減らす）」という操作をAPI経由で行うことは、セキュリティおよび金融規制の観点から非常に高い壁があります。 金融系プラットフォームは、外部アプリからの直接的な残高操作を許可すると、不正送金やデータ不整合のリスクが排除できないため、通常は厳格なクローズド環境に置かれます。 そのため、現在の構想を現実的に実現するためには、**「双方向同期」ではなく「非同期的な連携（決済ゲートウェイ方式）」\*\*に設計を切り替えることを強く推奨します。

##### 1\. 推奨するアーキテクチャ：「オペレーション帳簿」と「決済基盤」の分離

「浮遊街アプリ」側を「経済圏の帳簿（Ledger）」とし、eumoを「実資金の決済基盤」として切り分けて運用するモデルです。 この構成であれば、eumo側のAPI仕様に完全に依存せず、独自の経済圏を構築できます。

##### 2\. 具体的なデータ連携フロー（案）

「同期」させるのではなく、\*\*「イベント通知」と「照合」\*\*で解決するフローです。

1.

### 🤖 クエスト完了報告（アプリ側）

*   アプリ上でクエストを完了させ、報酬として「内部トークン（Uii）」を発生させます。これはアプリ内のDB（Supabase等）で管理します。
2.

### 🤖 送金リクエスト（アプリ側）

*   アプリ内に「eumoで受け取る」ボタンを配置します。
    *   アプリは「送金依頼（または送金リンクの生成）」を行い、ユーザーをeumoアプリへ遷移させます。
3.

### 🤖 決済実行（eumo側）

*   ユーザーはeumoアプリ上で実際の送金を行います。
4.

### 🤖 完了報告と同期（双方向・非同期）

*   eumoアプリでの決済完了後、ユーザーは浮遊街アプリに戻り「決済完了報告」を行います。
    *   あるいは、eumo側からWebhook（もし提供されていれば）で通知を受け取り、浮遊街アプリ側で「Uii」の残高ステータスを「確定済（Paid）」に更新します。

##### 3\. この方針をとるメリット

*

### 🤖 規制クリア

金融規制（資金決済法など）に関わる領域（実際の送金）はeumo側に任せ、浮遊街アプリはあくまで「コミュニティ管理・作業管理」に特化できるため、開発リスクが低いです。
*

### 🤖 柔軟性

将来的に独自通貨（Uii）を発行する際も、この「帳簿管理システム」がすでにあるため、移行がスムーズです。
*

### 🤖 拡張性

他の決済手段（現金、他の地域通貨）が増えた場合も、このアーキテクチャなら対応可能です。

##### 4\. 今後の検討ステップ

もし本気で「直接的な同期（APIでの残高操作）」を狙うのであれば、以下のプロセスが必要になります。

1.

### 🤖 MoneyEasy（基盤システム）のAPI調査

*   まずは、eumoのプラットフォームであるMoneyEasyが、APIでの「残高照会」や「送金指示」を開放しているかを確認してください（一般公開されていない場合、パートナーシップ契約が必要です）。
2.

### 🤖 法務・コンプライアンス相談

*   自前アプリで残高を直接操作することは、マネーロンダリング対策（AML）や本人確認（KYC）の責任をどう負うかという問題に直結します。ここをeumo側に代行してもらう（あるいは委託する）ための契約を要します。
3.

### 🤖 MVP開発

*   まずは「リンク遷移による決済フロー」から始め、データモデルを先に固めておき、将来的にAPI連携が解禁された際にシステムを差し替えられるよう、コードベースを疎結合（今の設計方針）にしておくのが最も合理的です。 「残高を直接操作したい」という熱意はプロジェクトにとって大きな推進力になりますが、システム構築においては\*\*「決済結果の同期（確認）」をゴールにする\*\*のが、開発を止めないための現実的な解となります。
