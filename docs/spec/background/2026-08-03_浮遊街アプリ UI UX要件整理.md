#### 浮遊街アプリ 総合要件定義・設計書\_v8Version 1.3更新日：2026年7月20日

1.  プロジェクト概要 1.1 背景 自給自足コミュニティ「浮遊街」におけるクエスト運営、会員管理、地域通貨「Uii（ウイ）」運用およびFAQ対応について、現在は人手による運営負荷が高い。 本システムは、これらの運営業務をデジタル化し、AIを活用した運営支援を実現することを目的とする。また、日本円などの既存通貨を介さず「腐る経済」を軸とした特異なコミュニティの持続可能性を高めるとともに、将来的には複数コミュニティへの展開（マルチテナント化）およびFEL（Favorite Earth Life）とのデータ連携を見据えた基盤として構築する。 1.2 システム目的 業務効率化 クエスト管理のデジタル化（手動運用の自動化・効率化） FAQ自動回答（AIコンシェルジュによる問い合わせ削減） Uii運用・決済支援（EUMO連携による帳簿・残高管理） 利用者体験向上 情報へのアクセス性向上 クエスト参加促進・貢献の可視化 コミュニティ参加促進およびゲーム性の提供 将来展望 AIによる自律支援（朝の会議録音からのクエスト自動作成等） 複数コミュニティ展開（マルチテナント基盤構築） FEL（Favorite Earth Life）との共通データ連携

* * *

2.  システム概要 システム名称 浮遊街アプリ 利用者分類 管理者：運営スタッフ・コミュニティリーダー 会員：一般コミュニティメンバー ゲスト / 長期滞在者：初回来訪者または長期宿泊者（※ゲストおよび長期滞在者は基本同一権限とする） カスタム権限：出資者・VIP等の特殊権限設定

* * *

3.  開発方針

#### MVPの早期構築：最小限の機能で短期間構築し、現場で運用しながら高速に改善する。AIの活用：AI（Claude API）は人間の運営業務を補助・支援する位置付けとする。マルチテナント・疎結合設計：浮遊街固有のロジックと共通基盤を分離したアーキテクチャ（Shared Schema等）を採用する。EUMOとの連携：地域通貨「Uii」の残高管理の正（SSOT）は外部基盤（EUMO）とし、アプリ側は非同期参照・キャッシュを行う。

4.  スコープ Phase 1（MVP：2026年7月〜8月） 認証機能（メール / Google / LINE） クエスト管理（登録・編集・削除・閲覧・参加申請・完了報告） クエスト承認・査定（管理者/リーダーによる手動目視承認・Uii/XP付与） 会計管理・注文管理・売上分析（POS伝票デジタル化、顧客注文履歴、日次/月次売上集計・傾向分析） メニュー内容、価格 宿泊データと合わせて決済もできるように Uii残高表示・失効管理（EUMO残高参照、3ヶ月有効期限一括失効） 宿泊管理機能（宿泊申込フォーム連携、滞在日数自動計算・毎日0時自動減算、宿泊延長処理） Googleカレンダーに入れて誰がいつ泊るか、混雑状況を確認して誰がいるかその日（ニックネームで登録） 施設・フィールドマップおよび品目案内（P2Pマーケット前段としての案内表示） FAQ・AIコンシェルジュ（RAG対応）（プロファイル判別応答、信頼度低下時の未回答エスカレーション） 気候・環境データ・施設情報管理（FEL連携を見据えたバッチ収集および構造化保存） 次に持ち越しかな⭐️ データの集め方、Firebase、クラウド上にファイルを作成して、テキストだったらVectorの方がいいかな？、気象データの取り方（） 数字はJsonで格納 数字化できない文字とかはPDFにする FELはFELでやる 写真・データの共有・検索（ベクトル検索による素材共有・SNS運用自動化基盤） Phase 2（2026年9月以降予定） スキルツリー機能（スキルレベルLv1〜5の可視化、熟練度連動の報酬動的算出、上級職・称号付与、推薦機能） P2Pマーケット（スキル・物品の売ります/買いますマッチング、情緒的メタデータを伴うUii送金） Phase 3（将来検討） AIによるクエスト自動生成（朝会録音・議事録解析による自動作成・承認フロー） FEL連携強化（気象・土壌データ共有、Shared Schemaの完全活用） マルチテナント化（他コミュニティ展開へのマルチテナントプラットフォーム化）

5.  業務要件 5.1 認証 メール認証、Google OAuth、LINE OAuthによるログイン／ログアウトを提供する。 ※MFA（多要素認証）はPhase 1では非対象とする。 5.2 クエスト管理 管理者：クエスト新規登録、編集、削除、募集人数設定、Uii報酬・難易度設定。朝会録音からの自動起草承認（将来機能）。 会員 / ゲスト：クエスト一覧閲覧、詳細確認、参加申請、複数人パーティー参加、完了報告（写真・資材・コメント添付）。 反復実行：クエストは繰り返し実行可能とし、熟練度や担当スキルに応じて報酬を調整可能とする。 5.3 クエスト承認 管理者 / リーダー：完了報告の内容を目視確認し、承認・差戻し（理由添え）を実施。 承認処理：承認完了時に自動でUii付与（EUMO連携）および獲得XP加算、スキルレベル更新を行う。 ※MVPではAI自動承認・閾値アラートは行わず、手動目視を原則とする。 5.4 注文管理・会計売上分析 伝票入力・POSデジタル化：店舗・施設スタッフが品目を選択して注文データを即時入力。手書き伝票の削減。 注文履歴：会員・ゲストごとに注文履歴を蓄積し、マイページで過去の履歴を閲覧可能とする。 売上集計・傾向分析：日次・月次の自動集計、個人の利用傾向・パーソナリティ分析（適切なプライバシー保護を実施）。 5.5 宿泊管理機能 宿泊申込：事前の申込フォーム連携による予約データの自動登録。宿泊権の他者譲渡は禁止。 滞在期間管理：チェックイン・アウト日保持、現在の滞在日数自動計算、宿泊予定一覧表示。 宿泊残日数減算：毎日0時に宿泊残日数を自動減算処理。 宿泊延長：既存予約変更ではなく新規フォーム申請による再予約処理とする。

*   概要・用語: 宿泊券＝1泊分の権利、保有数（残高）の考え方
*   アクター: 管理者/運営（付与）、ユーザー（消費）
*   機能要件: 付与、保有数確認、消費、履歴管理
*   データ項目案: user\_id, balance, transaction\_type, nights, related\_reservation\_idなど
*   今後の検討事項: 有効期限、クエスト報酬としての自動付与、キャンセル時の返却フロー

#### 5.6 クエストキャンセル機能会員キャンセル：クエスト開始前まで任意でキャンセル可能。未承認のキャンセルはUii/XP付与なし。管理者キャンセル：天候・災害・運営都合による中止可能。キャンセル理由・日時・実施者をログとして保管。5.7 Uii機能・経済圏設計（腐る経済）SSOT（信頼できる唯一の情報源）：残高管理の正はEUMOとする。アプリ側は非同期同期および一時キャッシュを保持。有効期限（3ヶ月失効）：3ヶ月の有効期限（価値逓減）を設定し、期限到達時は対象残高を一括失効。失効履歴を保管する。マイナス残高の禁止：送金・決済時に残高不足の場合はエラーを返し取引を中止する。5.8 FAQ・AIコンシェルジュ機能（RAG）コンテキスト切り替え：ログイン属性（メンバー/ゲスト）を判別し、適切な解像度でFAQ回答を自動生成。知識ベース更新：管理画面での直接編集およびPDFアップロードによるRAGナレッジ更新。エスカレーション：信頼度が閾値未満の場合や根拠データ不備の場合は自動回答を中止し、管理画面の「未回答問い合わせ一覧」へエスカレーション、運営へ通知。5.9 気候・環境データおよび施設情報管理環境情報：FEL・クエスト用の気候データ、地形・広さ等のデータを収集・保管。データ読み込みは月1回のバッチ処理等でトークン・運用負荷を最適化。施設情報：カフェの平米数、宿舎受入人数、床素材、アースバッグ構造等の項目定義と修繕履歴の蓄積。

##### 3\. UI/UX設計における重要ポイント（チコさんレビュー＆ヒアリングの反映）

画面を作る上で、デザイナーが意識すべき具体的な要件です。

###### ① 「摩擦ゼロ」のアカウント開設と個人情報保護

*

### 🤖 設計方針

宿泊予約フォーム（外部）に入力された段階で裏側でアカウント（空枠）を作成しておきます。
*

### 🤖 UIへの落とし込み

ユーザーには「招待リンク」を送り、初回アクセス時は\*\*「ニックネーム」と「誕生年月（概算）」\*\*だけを入力させます。本名やクレジットカード情報（円情報）はUUMO側で処理するため、アプリ内では一切入力させないミニマルなUIにします。

###### ② 注文管理の「セルフ・代理」ハイブリッドUI

*

### 🤖 設計方針

ユーザーの自己手配と、現場の柔軟な対応を両立します。
*

### 🤖 UIへの落とし込み

*   客のスマホからはシンプルに「カートに入れて注文」するだけのUI。
    *   店員のタブレットには「〇〇さん：コーヒー2杯」とリアルタイム表示。もし売り切れの場合や、客がスマホを持たずに注文しに来た場合は、店員がタブレット上で「〇〇さんの代理で注文」できる切り替えボタンを配置します。

###### ③ 暗黙知の形式知化（Situated Action / ケースベース推論の体現）

*

### 🤖 設計方針

「キッチンの配置がわからない」「重い荷物の運び方がわからない」といったボラスタの課題や、コミュニティ特有のナレッジ（暗黙知）を、行動の文脈（Situated Action）に合わせて引き出せるようにします。
*

### 🤖 UIへの落とし込み

*   AIチャット画面に、 **「いま自分がいる場所（例：キッチン、畑）」のコンテキストタグ** をワンタップで付与できるボタンを配置します。
    *   「キッチン」タグを選択して質問すれば、ベクトルDB（Obsidian/MDワールド参照）から関連するメタデータ（配置図やルール）が即座に提示されるチャットUIにします。
    *   クエスト完了報告時に、「どんな工夫をしたか？（ナレッジ）」を任意で一言残せるフィールドを設け、それを次のAIの回答データ（ケースベース）へと循環させます。

###### ④ IoTや将来拡張を見据えた「余白」の設計

*

### 🤖 設計方針

蜂の巣チェックのIoT化や、FELとのデータ連携（気象・土壌）など、将来的に多様なデータが入ってくることを想定します。
*

### 🤖 UIへの落とし込み

ホーム画面や施設詳細画面の隅に、「環境データウィジェット（温度、湿度、センサーアラートなど）」を追加できるモジュール型のカードUI設計（FigmaでのAuto Layout活用）にしておきます。

* * *

##### 次のアクション（Figmaへの移行に向けて）

これらの整理を元に、まずは以下の3つの「コア体験（Core User Journey）」のワイヤーフレームからFigmaで作成することをお勧めします。

1.  **予約完了後の初回ログイン 〜 自分のステータス（Uii/日数）確認**
2.  **クエスト受注 〜 現場作業 〜 完了報告（暗黙知のログ化）**
3.  **カフェでの注文（ユーザーのスマホ） 〜 提供（スタッフのタブレット）** エンジニアの視点から見ても、DB構造（Supabase）やコンポーネント設計（Next.js）に綺麗に落とし込める要件に整理されています。この内容でデザイナーと認識を合わせ、画面レイアウトの作成に進めて問題ありません。他に深掘りしたい画面遷移はありますか？
