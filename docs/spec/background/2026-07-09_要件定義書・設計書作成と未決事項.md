# 要件定義書・設計書作成と未決事項

### 🧑 User

下記を作成、ただし作成できない箇所や確認事項があれば未決で、何を検討すれば決められるかも併せて ① 要件定義書 プロジェクト全体の要約です。以下の内容を包括します。 プロジェクトの背景・目的 業務フロー図（As-Is / To-Be） 機能一覧・機能詳細定義 非機能要件定義 ② 業務フロー図・画面遷移図 現状の業務（As-Is）と、システム導入後の業務（To-Be）のプロセスを可視化 ③データモデル定義書（概念データモデル） システムで扱うデータの関連性を整理します。システム全体の構造を定義する基盤となります。 ④機能と権限のマトリクス

### 🤖 Gemini

ご提示いただいた「浮遊街AI」および「クエストアプリ」に関する各種構想資料（構築ロードマップ、収集データ項目、連携構想、技術スタック等）の蓄積データを統合・整理し、ご指定のドキュメントを作成しました。 作成したGoogleドキュメントは以下のリンクよりご確認いただけます。 [浮遊街AI\_クエストアプリ\_総合要件定義・設計書\_v1](https://docs.google.com/document/d/1ksxQVGoFKh0D9lm_OD4FZbBET9Dtr2RoCVLb6bDa4Lg/edit?usp=drive_web) \[file-tag: drive-uploaded-file-1ksxQVGoFKh0D9lm\_OD4FZbBET9Dtr2RoCVLb6bDa4Lg\] ドキュメントの構成、および現時点で情報が不足している「未決・確認事項」と「それを決めるための検討方法」の要約は以下の通りです。

##### 📄 ドキュメントに含まれる内容

1.  **要件定義書**
    *   **プロジェクトの背景・目的:** 「独自の経済圏（Uii、腐る経済、クエスト制、通い型）」という浮遊街の特性と課題、および将来的な汎用コミュニティサポートAI（FEL連携含む）への展開目的を明文化。
    *   **機能一覧・機能詳細定義:** 4つの中心領域（運営サポート、会員・ゲスト案内、スキルツリー、場所づくり支援）の機能を網羅。
    *   **非機能要件定義:** 疎結合なクリーンアーキテクチャ方針、FELとの共通データスキーマ（Shared Schema）、セキュリティ、データ利用のガバナンス等を定義。
2.  **業務フロー図・画面遷移図（テキスト構造定義）**
    *   導入前後（As-Is / To-Be）のプロセス比較表。
    *   クエスト運用、プロファイル判別（メンバー/ゲスト）による案内フローのプロセス。
    *   マイページ、クエスト一覧・報告、AIチャット、管理側ダッシュボード等の画面遷移構成案。
3.  **データモデル定義書（概念データモデル）**
    *   会員、クエスト、作業ログ、拠点・施設、会員スキル、AI対話ログの主要エンティティの関係性と基本属性を整理（物理ER図への橋渡しとなる基盤構造）。
4.  **機能と権限のマトリクス**
    *   4つのロール（運営管理者、コミュニティリーダー/査定員、一般会員、ゲスト）における操作・閲覧権限の分離定義。

* * *

##### ⚠️ 現時点での未決・確認事項と、検討の進め方

本格的なデータベースの物理設計（物理ER図）や、Next.js・Supabase等によるシステム実装へ進む前に、以下の仕様を確定させる必要があります。ドキュメントの「5. 現時点での未決事項・確認事項」にも詳細を記載しています。

1.  **関連性の多重度（Cardinality）と業務仕様の定義**
    *   **未決内容:** 同一クエストを何度も繰り返し実施可能とするか。また、一つのクエストに複数人で同時に取り組み、貢献度（XPやUii）を按分・分配する仕様（パーティー機能等）にするか。
    *   **検討方法:** 実際の現場オペレーション（例：複数人で行う農作業や修繕など）の運用ルールをヒアリング・策定する。
2.  **承認フローの閾値と自動化・エスカレーション基準**
    *   **未決内容:** クエスト完了を「リーダーが最終承認する」ための定量的な基準（作業時間や成果の乖離）。また、AIがイレギュラーを検知して人間にアラートを出す具体的な閾値。
    *   **検討方法:** 各作業の「平均的な所要時間」や「過去のトラブル事例」を洗い出し、システム判定用の閾値ルール（例：想定の2倍以上の時間がかかっている場合は要レビュー等）を明文化する。
3.  **地域通貨Uiiの不整合・残高不足対応**
    *   **未決内容:** クエスト完了後に「支払うコインプール（予算）が運営側にない」といった事態を防ぐための、予算（コインプール）と発行クエスト数の連動設計。また、Uiiが「腐る（価値が逓減する）」際の具体的なロジックと計算タイミング（日次、月次など）。
    *   **検討方法:** 浮遊街の経済圏設計（トークノミクス）のルールブックを参照、または経済設計担当者と協議し、価値逓減バッチ処理の仕様を確定させる。
4.  **ゲスト案内の範囲と、プロンプト・マニュアルの一元管理**
    *   **未決内容:** ゲストに「どこまでの内部情報開示を許容するか」のセキュリティライン。また、コミュニティのルールが変更された際に「AI用プロンプト/RAG用ナレッジ」をどこで一元管理（マニュアルとAI設定の同期）するか。
    *   **検討方法:** ゲスト向け規約や案内ガイドラインを整理。また、管理者がエンジニアを介さずに知識ベースを更新できる仕組み（Notion連携やSupabaseの管理画面など）の運用コストを比較検討する。 こちらのドキュメントをベースに、上記の未決事項についてチーム内やクライアントとディカッションを進めていただくのがスムーズです。必要に応じて、特定のセクションの深掘りやプロトタイプ用プロンプトの作成などもサポートいたしますので、いつでもお申し付けください。
