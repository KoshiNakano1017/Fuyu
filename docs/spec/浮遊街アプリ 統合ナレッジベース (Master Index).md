## 1. プロジェクト概要 [[プロジェクトの背景と目的]]
- **対象**: 1,000人限定の通い型自給自足コミュニティ「浮遊街」
- **コアコンセプト**:
  - **クエスト制**: コミュニティ内の作業（農作業、広報、メンター等）をクエスト化し、ゲーム感覚で貢献を可視化。
  - **Uii（ウイ）**: 日本円を介さない「腐る経済」を体現する独自の地域通貨。
  - **暗黙知の形式知化**: 現場の文脈（Situated Action）に応じたAIファシリテーション。
- **将来展望**: 単一コミュニティの支援から、複数コミュニティへのマルチテナント展開、およびメタバース連携（職業に応じたマイショップ機能など）への拡張。

## 2. 主要機能要件（ドメイン） [[機能要件定義]]

> **業務ドメインの全体地図**: 浮遊街で想定される全業務（15ドメイン）と、それを担う8種のAIエージェント構想は [[業務カテゴリ体系とAIエージェント設計]] に整理。クエストカテゴリ／スキルツリー／RAGカテゴリタグの共通基盤となる。

### A. クエスト・スキル管理 [[クエストシステム仕様]]
- **スキルと職業**: Lv.1（見習い）〜Lv.5（師匠）のスキルレベル。レベルに応じてタスクの想定工数（生産性）が変動。
- **職業（ジョブ）**: スキルの掛け合わせによる自動付与（例：農業Lv3＋料理Lv2＝『里のシェフ』）。
- **転職クエスト**: 単なるスキル数値だけでなく、メンバーからの「推薦」や「イベント企画」等のコミュニティ体験（信頼・実績）を上位職への昇格要件とする。

### B. Uii経済圏・決済連携 [[Uii経済圏とeumo連携]]
- **eumo連携のアーキテクチャ**: APIの完全同期（双方向同期）は仕様上困難なため、**「非同期的な連携（決済ゲートウェイ方式）」**を採用。
- **役割分担**: 浮遊街アプリ側を「オペレーション帳簿（メタデータ・残高記録）」とし、eumoを「実資金の決済基盤」として分離。
- **消費メタデータ**: 単なる送金ではなく、「何に消費したか（マッサージ、野菜など）」を記録し経済循環を可視化。

### C. UI/UX・顧客管理 [[UI_UX設計指針]]
- **客用スマホ画面**: 摩擦ゼロのUI。招待リンクから「ニックネーム・誕生年月」のみでアカウント枠を作成。
- **店員用タブレット画面**: 注文一覧、売り切れ即時反映（SOLDOUTトグル）、客がスマホを持たない場合の「代理注文機能」を備えたハイブリッド仕様。
- **管理者PC画面**: 今日のサマリー、未会計アラート、一括精算QR、朝会・議事録の音声文字起こし＆クエスト自動生成。
- **HTMLモック（動くプロトタイプ）**: [[HTMLモック_v13]] … 要件定義v13準拠の全8画面インタラクティブモック（Tailwind + Alpine.js 単一HTML）。

### ★ E. 会員データ・アクセス制御（2026-08-14 追加） [[会員データモデル_ユーザーテーブル定義]]
- **既存会員の移行**: 街びと327件・親方衆44件を `members` / `member_identifiers` / `membership_plans` / `memberships` / `stay_ticket_transactions` / `member_notes` の6テーブルへ正規化。
- **残高の扱い**: 会員マスタの `stay_tickets`・`total_stay_days`・`uii_balance` は**集計キャッシュ**。**正本は取引明細**で、直接UPDATEは禁止（実データで15件の不整合が発生していたため）。
- **ロール別UI制御**: 権限外メニューはDOMごと非描画。ただし**DOM非表示は認可ではない**ため、Supabase RLS を必ず併用する。
- **ゲスト→街人導線**: 施錠クエスト（`guest_allowed=false`）を**あえて見せて施錠**し、登録の動機づけとする（管理機能を「隠す」原則とは逆方向）。

## 3. FEL（Favorite Earth Life）連携構想 [[FEL連携アーキテクチャ]]

FELは「お気に入りの場所を10年以上の視点で育てるランドスケープ教育事業」であり、浮遊街AIの「④場所づくり支援」とドメインが重なる。

- **連携の最重要方針**: インフラ（アプリ・DB）は**完全分離（疎結合）**とするが、**「データモデル（語彙・スキーマ）」のみ先行して共通化**する。
- **データ収集方式**:
  - FEL側は通信環境の悪い山林等を想定し、USB/Bluetoothによる「手動エクスポート方式（3ヶ月に1回）」を採用。
  - **多様性マトリクス**: 気候帯 × 土地タイプのセルを埋めるように意図的にデータを収集（各セル5〜10件）。
- **共通スキーマ定義**: 
  - `Place`（場所プロファイル：気候、土壌、地形）
  - `PlaceLog`（作業・変化の時系列ログ）
  - `Member`（会員情報）

## 4. システム構成・技術スタック [[システムアーキテクチャ]]

無料枠の制限（Supabaseのプロジェクト数上限やDB容量500MBの壁）と将来のマルチテナント化を見据えた設計。

- **フロントエンド**: Next.js (Vercel) / Tailwind CSS (HTMLモックはClaude Artifactsで最速生成)
- **バックエンド/DB**: Supabase (PostgreSQL, 認証, Realtime, RLS) — **認証・認可の単一のソース・オブ・トゥルース**
- **メディアストレージ**: Cloud Storage for Firebase（GCS）＋ Cloud Functions（サムネイル・トランスコード・Exif抽出）
  - **Firebase Authentication / Security Rules は使用しない。** 署名付きURLで配布し、**認可判定はすべて Supabase 側**で行うことで基盤の二重化を避ける。
- **AI基盤**: Claude API / Agent SDK
- **RAG/ベクトル検索**: ~~pgvector (Supabase内) または OpenSearch~~ → **2026-08-16確定：浮遊街コンシェルジュ（line-rag-bot、Firestore）に統合**。浮遊街アプリ本体は独自のベクトル検索基盤を持たず、エンドユーザー向けAIチャットUIも持たない（案内はLINEに一本化。v13 §9 #31、詳細は[[浮遊街アプリ 総合要件定義・設計書_v13]] 詳細設計 `外部連携設計.md` 参照）
- **API/連携層**: MCP (Model Context Protocol) 
  - **MCP Gateway**を用いて、分離された各テナントのデータやAIログをセキュアかつ疎結合にルーティングする。
- **共通スキーマ管理**: Shared Schema Repository (TypeScript Package / OpenAPIとしてGitHub等で管理)

## 5. データベース構想 (概念データモデル) [[ER図_概念データモデル]]

本格的な物理ER図への橋渡しとなるエンティティ群：
1. **会員マスタ (Member)**: ID、属性、宿泊日数、スキルLv、職業ランク
2. **拠点・施設マスタ (Place)**: 静的プロファイル（緯度経度、気候帯、土壌タイプ等）
3. **クエストマスタ (Quest)**: 業務定義、付与XP、Uii報酬設定
4. **作業ログ (WorkLog)**: 実行日時、担当者、Before/After写真、成果
5. **活動・対話ログ (Activity)**: AIとの会話履歴、推薦・評価データ
6. **レシピマスタ (Recipe)**: クエスト作業・調理の手順書（材料・使用道具・ステップ・よくあるミス）
7. **道具・資機材マスタ (Tool)**: 農機具・調理器具等の使用手順・注意点（例：芝刈り機の混合油投入〜エンジン始動手順）
8. **業務カテゴリマスタ (WorkCategory)**: 15業務ドメインの階層定義、担当AIエージェント種別、RAG構造化タイプ（[[業務カテゴリ体系とAIエージェント設計]]）
9. **★ 会員まわり（2026-08-14 実データ準拠）**: `MembershipPlan` / `Membership` / `MemberIdentifier` / `StayTicketTransaction` / `MemberNote` — 物理スキーマは [[会員データモデル_ユーザーテーブル定義]] を正とする
10. **★ メディアアセット・街人登録申込・差額精算**: [[ER図_概念データモデル]] を参照

## 6. Claude（開発用AI）へのプロンプト記述ルール 🤖

Claudeにコード生成や設計を依頼する際は、`.cursorrules` やシステムプロンプトに以下を指定してください。

```text
【アーキテクチャ制約】
・すべてのドメインロジック（特に場所データやクエスト定義）は、UIやインフラ層から分離すること（クリーンアーキテクチャの徹底）。
・特定コミュニティ（浮遊街）固有のロジックは `src/domains/floating_city/` に隔離し、汎用的な `src/domains/core/` に依存させないこと。

【メタデータ設計とインフラ分離】
・新しいエンティティを作成する際は、ロジックのハードコーディングを避け、JSONやスキーマで制御できる構造にすること。
・FEL連携を見据え、「場所データ（Place/PlaceLog）」を扱う際は、共通語彙（Shared Schema）との互換性を維持したスキーマ設計を行うこと。
・インフラは浮遊街とFELで分離するため、データベース接続は直接ではなく、MCP（Model Context Protocol）を介した疎結合な連携を前提としたコードを出力すること。

【UIモックアップ生成】
・UIを生成する際は Tailwind CSS を使用し、「客用スマホ画面」と「店員用タブレット画面」をトグル等で切り替えてプレビューできるHTMLを出力すること。
```
