# RAGシステム仕様

> [[浮遊街アプリ 統合ナレッジベース (Master Index)]] の子ノート（2-D）

> [!warning] 2026-08-16 正本により一部無効化（v13 §9 #31、同日再確定あり）
> ナレッジ・RAG基盤はline-rag-bot（Firestore）へ統合することが確定した。本ノート中の
> pgvector・ベクトルDB関連の記述は実体としてline-rag-bot側の設計に置き換わっている。あわせて
> 浮遊街アプリ本体はエンドユーザー向けAIチャットUI（アプリ内コンシェルジュ）自体を持たない。
> **2026-08-16再確定：浮遊街アプリ本体とline-rag-botの間にAPI連携は一切実装しない**（読み取り
> 専用APIも含む）。本ノート中の「ナレッジ登録画面」「4ステップフォーム」「line-rag-bot APIへ送信」
> といった記述はいずれも無効で、ナレッジ登録・編集・エスカレーション対応は全てline-rag-bot
> Streamlit管理画面で行い、浮遊街アプリ側は同画面への外部リンクを配置するのみ。`target_role`は
> 4値（guest/member/core_member/admin）の単一値で確定。詳細は正本v13 §9 #31、
> `docs/spec/detailed-design/外部連携設計.md`を参照。本ノート自体は経緯を追跡できるよう原文の
> まま残す（正本と食い違う場合は正本を優先する、というMaster Indexの既存ルールに従う）。

## 構成
- **フロントエンド**: LINE Messaging API
- **AIエンジン**: Gemini / Claude
- **ベクトル検索基盤**: pgvector（Supabase内）または OpenSearch

## ナレッジ管理方針
- 既存マニュアル（PDF）の読み込みだけに頼らず、検索精度を上げるために「草刈機の使い方」「Uiiの登録方法」等をQ&A（一問一答）形式でベクトル化して登録する。
- 管理画面での直接編集およびPDFアップロードによるナレッジ更新に対応。

## ★ ナレッジ登録画面（2026-08-14 追加 ／ 正本 §5.7）

**自由記述テキストボックスやファイルアップロードのみで実装しない。** 表記ゆれ・分類漏れ・文脈欠落が発生し、検索ヒット率の低下とハルシネーションを招くため、**選択式（ガイド付き）フォーム**として設計する。入力者が「論点」と「格納先」を意識せずとも、システム側でメタデータが自動付与される構造とする。

**対象ロール**：管理者（`admin`）・コアメンバー（`core_member`）のみ。一般会員・ゲストには登録導線を表示しない。

### 入力フォーム（4ステップ）

| STEP | 論点 | 入力形式 | 付与されるメタデータ |
| --- | --- | --- | --- |
| ① 対象者 | 誰に向けた情報か（＝公開範囲） | ラジオボタン | `target_role` |
| ② 格納先カテゴリ | どの領域の情報か | プルダウン | `category_id`（業務カテゴリマスタ準拠） |
| ③ 行動文脈・キーワード | どんな場面で使うか | チェックボックス＋タグ | `usage_scene[]` ／ `keywords[]` |
| ④ 本文 | FAQ形式／マニュアル形式の択一 | テキスト＋添付 | `question`/`answer`/`body`/`attachments[]` |

- **STEP 1 の `target_role`（`guest`／`member`／`core_member`）はアクセス制御キーを兼ねる。** ゲストからの問い合わせには `target_role='guest'` のナレッジのみを検索対象とし、内部専用ナレッジ（査定基準・緊急時対応・精算処理）が外部へ漏出しないことをシステムとして保証する
- **STEP 2 は STEP 1 で `core_member` を選んだ場合のみ運営系カテゴリを追加表示**する（内部情報を一般公開カテゴリへ誤って入れる事故を構造的に防ぐ）
- STEP 4 は**A. 一問一答（FAQ）形式を推奨**。Q&Aペアの方がベクトル検索のヒット率が高いため。B. マニュアル形式は既存資産の取り込み用とし、登録後にAIがQ&A候補へ分解して承認フローに載せる

### 入力負荷そのものを下げる3機構

画面を用意するだけでは登録は進まない。**入力の起点をシステム側から提示する**。

| # | 機構 | 内容 |
| --- | --- | --- |
| ① | **未回答ログからのワンタップ登録** | AIが回答できなかった質問を管理画面トップに「未登録論点」カードとして表示。ボタン1つで**質問文が入力済みの状態**でフォームが開く |
| ② | **朝会議事録からの自動抽出** | 朝会パイプラインと**同一のGemini API呼び出し**で「新しく決まったルール」「現場の注意点」を候補抽出。確認して「承認・登録」を押すだけ。※別呼び出しにすると非機能要件「60秒以内」を圧迫するため相乗りさせる |
| ③ | **スマホからの現場即時登録** | 音声入力／写真＋短文で登録。登録時点では `draft` とし、後からPCで構造化・公開する |

### 登録後の処理

| # | 処理 |
| --- | --- |
| ① | 本文のチャンク化・ベクトル化 |
| ② | **メタデータ付きで pgvector へ格納**（`target_role`/`category_id`/`usage_scene[]`/`keywords[]`/`agent_type`/`review_status`） |
| ③ | 添付メディアは Cloud Storage for Firebase へ格納し、DBにはパスとメタデータのみ保持（[[システムアーキテクチャ]]） |
| ④ | **検索時のメタデータ事前フィルタ**：質問者のロールで検索空間を絞ってからベクトル検索する |
| ⑤ | `review_status`（`draft`/`published`/`needs_review`）で公開制御。③のスマホ登録は `draft` で入る |

> [!danger] 情報隔離はプロンプトで行わない
> 内部専用ナレッジの隔離は、**検索段階のメタデータフィルタでサーバ側から強制**すること。「内部情報は答えないで」というプロンプト指示は隔離手段として機能しません。
- **ナレッジ登録UIの帰属先（2026-08-14 方針決定）**: 登録画面は最終的に浮遊街アプリ本体の**管理者権限UI**に統合する。あわせて運営者（ゆうきさん）が**スクリプトからも直接登録**できる経路を用意する。現状は line-rag-bot 単体の暫定管理画面（Streamlit）でのみ登録可能で、外部（浮遊街アプリ本体）から呼べるAPIは無い。実現には line-rag-bot 側にナレッジCRUD用REST APIを切り出す必要があり、浮遊街アプリ本体の技術スタック・管理者認証方式が固まってから着手する（未着手・詳細は line-rag-bot の `docs/08-浮遊街RAG詳細設計.md` 9-5）。

## 運営サポート機能（クライアント要望 2026-08-08反映）
RAGを単なる来訪者向けFAQ応答に留めず、**現場スタッフ・ボラスタ向けの運営サポート機能**として位置づける。具体的には以下2種の構造化データを登録・検索可能にする。

### ① レシピマスタ（クエスト・調理の手順書）
- クエスト作業（草刈り、農作業、左官等）や調理（まかない等）の「よくある手順」をレシピ形式で登録し、AIチャットから検索・提示できるようにする。
- データ項目案：レシピID、カテゴリ（調理／クエスト作業）、タイトル、材料・使用道具リスト（下記②の道具マスタと紐付け）、手順（ステップ配列）、所要時間、注意点・コツ、作成者ID、参照元（動画・写真URL）

### ② 道具・資機材マスタ（構造化された使い方情報）
- クエストや調理で使う道具・機材を独立したマスタとして構造化し、レシピや手順書から参照できるようにする。
- 例：**芝刈り機** → 「混合油（オイル＋ガソリン）をタンクに入れる」「リコイルスターター（エンジン始動ひも）を引いてエンジンをかける」といった操作手順・注意点（燃料混合比、始動手順、点検・保管方法、注意事項）を構造化データとして登録。
- データ項目案：道具ID、名称、カテゴリ（農機具／調理器具／建築工具等）、使用手順（ステップ配列）、必要な消耗品（燃料・油等の混合比含む）、安全上の注意点、保管場所、点検・メンテナンス頻度、関連レシピID
- レシピマスタ・道具マスタは共にRAGのベクトル化対象とし、「芝刈りのやり方を教えて」等の自然文検索から手順・道具情報の両方を横断的に提示できるようにする。
- 概念データモデルへの追加は [[ER図_概念データモデル]] を参照。

### ③ よくあるミス・失敗パターン（failure_patterns）
- `Recipe` に `failure_patterns[]`（症状／原因／対処／発生条件）を持たせ、**現場体験で得た「よくあるミス」を構造的に蓄積**する。
- 現行の `WorkLog`（作業ログ）は成果・評価のみを記録するため、失敗知見が残らない。`WorkLog` に `issue_flag` ＋ `issue_note` を追加し、報告された失敗事例を後から `Recipe` へ反映するフィードバックループを構築する。
- ケースベース推論において「成功事例」だけでなく「失敗ケース」を第3のケース種別として明示的に扱う。

### 現場ナレッジカード（登録テンプレート）
体験した業務を構造化する際の統一テンプレート。レシピ・道具・ミス・コツを分離して記録する。

| ブロック                | 項目                                                 |
| ------------------- | -------------------------------------------------- |
| 基本情報                | ナレッジID、レシピ/道具ID紐付け、カテゴリ（業務ドメイン）、タイトル、場所タグ（キッチン／畑等） |
| 状況（Situated Action） | 発生条件（時間帯・天候・混雑度）、対象者スキルLv要件                        |
| 手順                  | ステップ配列、使用道具・材料（`Tool`参照）、所要時間                      |
| **課題・よくあるミス**       | ミスのパターン（何を／なぜ間違えやすいか）、発生条件、実際に起きた結果                |
| 対処法・コツ              | リカバリー手順、熟練者の勘所の言語化                                 |
| Q&A化                | 想定質問（複数バリエーション）、回答本文                               |
| メタ情報                | 参照元（体験者ID・写真/動画URL）、レビュー状態、関連レシピ/道具ID              |

**登録フロー**: ①現場では音声/写真でラフメモ → ②テンプレートで構造化 → ③AIでQ&A文へ変換 → ④カテゴリ・ソース付与して登録 → ⑤問い合わせログ・エスカレーション履歴で精度検証し、ミス事例を随時追記。

## 業務ドメイン別のナレッジ設計
全業務ドメイン（15分類）と担当AIエージェントの定義は [[業務カテゴリ体系とAIエージェント設計]] を参照。ナレッジは構造化タイプごとに格納先を変える。

| 構造化タイプ | 対象業務例 | 格納先 |
| --- | --- | --- |
| **レシピ型**（手順が定型化できる） | 調理、清掃、ベッドメイク、草刈り、重機操作 | `Recipe` × `Tool` マスタ |
| **判断型**（状況依存・ケースバイケース） | 農作業の見極め、ファシリテーション、デザイン、イベント運営 | ケースベース推論ログ（`{状況}+{アクション}={結果}`） |
| **規程型**（ルール・法令・基準） | 宿泊法、食品衛生、安全管理、契約・保険 | 規程ドキュメント＋Q&Aペア |

### エージェント別ルーティング（将来構想）
ナレッジマスタに `agent_type` を持たせ、質問をまずエージェント判定してから該当ナレッジ空間に絞ってベクトル検索する。検索精度向上とトークン削減の両立を狙う。
- Phase 1では「ホスピタリティ（宿泊・飲食）」「ランド（施設・農業）」の2系統のみ実装。
- **ガバナンス系ナレッジ**（安全・資格・法令）のみ横断制約として全エージェントから参照可能にする（例：重機クエスト受注時の資格確認）。

## 暗黙知の形式知化（ゆうきさんナレッジ）
- 属人化した知識（まかないレシピ、左官、草刈り・しばかり、農作業ルーティン等）をRAGデータベースへ登録。
- 認知モデル：ケースベース推論。状況（Situated Action）とアクション・結果をセットで蓄積し、類似状況での再利用コストを下げる。
- ボラスタ向けには「キッチンの配置」「重い荷物の運び方」等の現場ナレッジを、行動の文脈（場所タグ：キッチン／畑など）に応じて即座に引き出せるようにする（UI詳細は [[UI_UX設計指針]]）。

## コンテキスト切り替え・エスカレーション
- ログイン属性（メンバー／ゲスト）を判別し、適切な解像度でFAQ回答を自動生成。
- 信頼度が閾値未満、または根拠データ不備の場合は自動回答を中止し、管理画面の「未回答問い合わせ一覧」へエスカレーション。運営LINEグループへ即時通知し、代理返信・自動学習につなげる。

## AIハルシネーション対策
- RAG構成の徹底、Temperature 0.1設定、根拠出典の表示、信頼度下限でのエスカレーションを組み合わせてリスクを低減する。

## 場所データとの連携（FEL連携を見据えて）
- 気象データ・地形データ・作業結果の時系列ログを蓄積し、単純な天候情報では捉えられない局所的な環境（マイクロクライメート）や「目の前の畑の状態」を反映した推論を可能にする。
- 因果ログの構造：`{気象条件} + {土地プロファイル} + {実施アクション} = {結果（収穫量・土壌改善度・状態変化）}`
- 過去の類似「土地プロファイル×気象パターン」ログを検索することで、ゼロからの推論よりも短い演算コストで最適アクション（クエスト）を提示する。
- 詳細な共通スキーマ設計は [[FEL連携アーキテクチャ]] を参照。

## Phase別スコープ
- **Phase 1**: RAG対応FAQ（プロファイル判別応答）、信頼度低下時のエスカレーション、PDF＋Q&A形式のナレッジ登録、運営サポート機能としてのレシピマスタ・道具マスタ登録＆検索、**★ ナレッジ登録画面（4ステップフォーム）＋ 未回答ログ起点・朝会抽出・スマホ現場登録の3機構（2026-08-14 追加）**
- **Phase 3**: 朝会録音・議事録解析によるクエスト自動生成の完全自動化、FEL連携強化（気象・土壌データ共有）
