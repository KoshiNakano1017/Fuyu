# FEL連携アーキテクチャ

> [[浮遊街アプリ 統合ナレッジベース (Master Index)]] の子ノート（セクション3）

## FELとは
「Favorite Earth Life（FEL）」は、お気に入りの場所を10年以上の視点で育てるランドスケープ教育事業。浮遊街AIの「④場所づくり支援」ドメインと重なる領域を持つ。

## 連携の最重要方針
- インフラ（アプリ・DB）は**完全分離（疎結合）**とする。
- 一方で、**「データモデル（語彙・スキーマ）」のみを先行して共通化**し、将来のデータ相互運用性を確保する。
- 理由：浮遊街とFELはそれぞれ通信環境・運用体制・優先順位が大きく異なるため、無理な密結合はどちらの開発速度も損なう。

## データ収集方式の違い
- **FEL側**: 通信環境の悪い山林等を想定し、USB/Bluetoothによる「手動エクスポート方式（3ヶ月に1回）」を採用。
- **浮遊街側**: アプリ経由でのリアルタイム〜バッチ収集（月1回程度のバッチ処理でトークン・運用負荷を最適化）。

## 多様性マトリクスによるデータ収集
- 気候帯 × 土地タイプのセルを埋めるように意図的にデータを収集する（各セル5〜10件）。
- 横展開（47都道府県 × 土地タイプ）を見据え、特定地域に寄りすぎない「メタモデル（抽象層）」と、個別の土地に適用する「インスタンス（具象層）」を分離する設計思想。
  - メタモデル：どの地域でも共通する「植物・菌・気象・日照の相互作用ロジック」
  - インスタンス：「瀬戸内紀行のこの谷間」「北海道の西向き斜面」等の個別ID

## 共通スキーマ定義（Shared Schema）
- **`Place`**（場所プロファイル）：気候帯、土壌タイプ、地形（緯度経度、標高、方角、傾斜角度、土壌特性、周囲の植生、微細地形）
- **`PlaceLog`**（作業・変化の時系列ログ）：気象条件（実測・予報）＋場所（地形特徴）＋作業（クエスト）＋結果（収穫量、土壌改善度、状態変化）をセットで記録
- **`Member`**（会員情報）：浮遊街側の会員マスタと連動する基本属性

## マイクロクライメートという考え方
- 広域的な気象データだけでは「目の前の畑の菌の繁殖状況」等の局所的な変化を捉えられない。
- 局所センサー値（温湿度、照度）による広域気象データの補正値、および状態ログ（菌の繁殖状況、作物の生育状況、土壌の乾燥具合）を定点観測として記録する。
- 因果ログ：`{気象条件} + {土地プロファイル} + {実施アクション} = {結果}` という形式で蓄積し、AIの推論コストを削減する（詳細は [[RAGシステム仕様]]）。

## 技術的な連携経路
- インフラ分離を維持しつつ、MCP（Model Context Protocol）を介した疎結合連携を前提とする（詳細は [[システムアーキテクチャ]]）。
- Shared Schema RepositoryをTypeScriptパッケージ／OpenAPIとしてGitHub等で管理し、双方のプロジェクトが同じ語彙でデータをやり取りできるようにする。

## Phase区分
- **Phase 1**: 気候・環境データ・施設情報の管理基盤（FEL連携を見据えたバッチ収集・構造化保存）
- **Phase 3**: FEL連携強化（気象・土壌データ共有、Shared Schemaの完全活用）、IoT遠隔監視との統合
