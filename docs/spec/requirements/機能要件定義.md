# 機能要件定義

> [[浮遊街アプリ 統合ナレッジベース (Master Index)]] の子ノート（セクション2）。詳細は [[浮遊街アプリ 総合要件定義・設計書_v13]] を正本とする。

主要機能を4つのドメインに整理する。

> **業務ドメインの全体像**: アプリが扱う対象業務（15ドメイン・現地/遠隔の実行形態・担当AIエージェント）の分類体系は [[業務カテゴリ体系とAIエージェント設計]] を参照。

> **業務ドメインの全体地図**: 浮遊街で想定される全業務（15ドメイン）とその分類軸、8種のAIエージェント構想は [[業務カテゴリ体系とAIエージェント設計]] を参照。クエストカテゴリ・スキルツリー・RAGカテゴリタグの共通基盤となる。

## A. クエスト・スキル管理 → [[クエストシステム仕様]]
- スキルレベル（Lv.1〜Lv.5）と職業（ジョブ）の自動付与ロジック
- 転職クエスト（推薦・実績ベースの昇格）
- クエストボードの一元集約、受注申請〜完了報告〜承認の運用フロー

## B. Uii経済圏・決済連携 → [[Uii経済圏とeumo連携]]
- eumoとの非同期連携（決済ゲートウェイ方式）
- 消費メタデータの記録（何に消費したか）
- Phase 1では会計管理（円建て価格の2割引換算・請求額算定）に機能を限定し、残高管理・失効処理等の高度機能はPhase 2以降

## C. UI/UX・顧客管理 → [[UI_UX設計指針]]
- 客用スマホ画面（摩擦ゼロオンボーディング）
- 店員用タブレット画面（SOLDOUTトグル、代理注文）
- 管理者PC画面（サマリー、未会計アラート、一括精算QR、朝会議事録＆クエスト自動生成）

## D. 浮遊街コンシェルジュ（RAG、旧称：AIコンシェルジュ） → [[RAGシステム仕様]]
- LINE Messaging APIをフロントエンドとした問い合わせ対応（**2026-08-16確定：唯一のフロントエンド**。浮遊街アプリ本体にはアプリ内チャットUIを設けない、v13 §9 #31）
- Gemini/Claudeを用いたRAG回答生成（浮遊街コンシェルジュ／line-rag-bot側で実施）
- ~~Q&A形式でのナレッジベクトル化（pgvector）~~ → **浮遊街コンシェルジュ（line-rag-bot、Firestore）へ統合**（2026-08-16、v13 §9 #31）
- ~~**★ ナレッジ登録画面**（4ステップのガイド付きフォーム）＋ 未回答ログ起点・朝会抽出・スマホ現場登録の3機構。送信先はline-rag-bot API~~ → **2026-08-16再確定**：この画面・API連携は浮遊街アプリ側に実装しない。ナレッジ登録・編集は浮遊街コンシェルジュのStreamlit管理画面で行い、浮遊街アプリ側は「浮遊街コンシェルジュ管理画面を開く」外部リンクのみ実装する（v13 §9 #31）
- **利用者ロール別アクセス制御（2026-08-16実装）**：guest/member/core_member/adminの4段階。LINEユーザー↔ロールの対応は運営者による手動マッピング（line-rag-bot側 `docs/08` §8-9参照）

## E. 会員データ・アクセス制御（2026-08-14 追加）→ [[会員データモデル_ユーザーテーブル定義]]
- ~~既存会員（街びと327件／親方衆44件）の一括インポートと名寄せ~~ → **初期移行はVault側スキーマで完了済み**。汎用の管理者向け一括インポートUIはPhase1では実装不要（2026-08-16、画面設計.md C6参照）
- ロール別UI表示制御 ＋ サーバサイド認可（RLS）
- ゲスト→街人アップグレード導線（申請 → 管理者QR送付 → 承認）

## F. メディアライブラリ（2026-08-16新設） → [[画面設計]]
- 各人（全ロール）が動画・写真をCloud Storage for Firebaseへ格納し、用途（インスタグラム投稿／資料作成等）を入力すると、AIが適合度順にソート＋キャプション案を自動生成
- 当初Phase2予定だった`media_assets`をPhase1へ前倒し（WBS §14、DB物理設計.md §3-7、API設計.md §2-10）
- メディア（画像・動画）ストレージと用途タグによる推薦

## フェーズ別スコープ（v13準拠 ＋ クライアント最優先要望 2026-08-08反映）

> **クライアントからの最優先指定（2026-08-08）**
> 1. **飲食管理**（注文・メニュー・調理レシピの標準化）
> 2. **宿泊管理**（チェックイン/アウト、宿泊日数）
> 3. **会計管理**（誰が・いつ・何に・いくら使ったかを常時可視化）
> 4. **朝会の議事録自動生成**（＋クエスト自動起案）
>
> 上記4本柱をPhase 1の中核（最優先実装対象）とし、他機能はこれらを支える前提条件・付随機能として位置づける。

### Phase 1（MVP：2026年7月〜8月）— 優先度順

**★最優先（クライアント指定コア）**
- 飲食管理・注文管理・店舗オペレーション（セルフ注文＋代理注文＋SOLDOUTトグル、調理レシピ登録）
- 宿泊管理（宿泊法対応、チェックイン/アウト、滞在日数管理、名寄せ）
- 会計管理（Uii/円の請求額算定、個人別・日次の利用状況を常時可視化するマイログ＆管理者ダッシュボード）
- 朝会録音・議事録自動生成＆クエスト自動起案

**★ 2026-08-13 レビューで追加（§5.7〜§5.11）**
- ナレッジ登録画面（管理者・コアメンバー向け4ステップフォーム）
- 既存街人の事前データ登録・名寄せ ＆ 宿泊日数の運営制御
- ロール別UI表示制御・アクセス制御
- ゲスト→街人アップグレード導線（QR送付方式）
- メディアストレージ（Cloud Storage for Firebase／認可はSupabaseに一元化）

> **スコープ影響**：上記5ブロックは当初見積の対象外。納期との関係は未合意（正本 §4 のスコープ影響を参照）。

**上記を支える前提・付随機能**
- 認証・アカウント作成（招待リンク・宿泊フォーム連動によるアカウント事前確定）
- 顧客管理＆一括精算＆未会計アラート
- クエスト管理（クエストボード集約）＆モチベーション（XP・バッジ）
- Uii機能（会計管理限定：円の2割引換算・確定支払額計算）
- FAQ・暗黙知AIコンシェルジュ（運営サポート機能。レシピ・道具の構造化登録を含む。詳細は [[RAGシステム仕様]]）
- 管理者画面・運用ドキュメント

### Phase 2（2026年9月以降予定）
- Uii高度機能（個人Wallet残高表示、3ヶ月有効期限一括失効、EUMO API直接同期）
- スキルツリー機能（可視化、報酬動的算出、推薦機能）
- P2Pマーケット（スキル・物品のマッチング）

### Phase 3（将来検討・IoT移行）
- IoT同期・環境データ収集（蜂の巣チェック等の遠隔監視）
- FEL連携強化・マルチテナント化

## ロール定義（2026-08-14 確定）

| ロール識別子 | 分類 | 備考 |
| --- | --- | --- |
| `admin` | 管理者 | 運営統括 |
| `core_member` | コアメンバー | 現場の管理権限を持つスタッフ・リーダー |
| `member` | 会員（街人） | 一般会員・ボラスタ |
| `guest` | ゲスト／長期滞在者 | 初回来訪者・長期宿泊者 |

**`member_type`（親方／街人／ゲスト）は `role` とは別軸**のコミュニティ内の立場であり、**認可には一切使用しない**。親方衆44名の権限は街人と同等（`role='member'`）。

## 権限マトリクス（概要）
| 機能 | 管理者 | コアメンバー | 会員（街人） | ゲスト |
| --- | :---: | :---: | :---: | :---: |
| ログイン/チェックイン | 〇 | 〇 | 〇 | 〇 |
| 朝会録音・議事録・クエスト自動抽出 | 〇 | 〇 | − | − |
| クエスト受注申請 | 〇 | 〇 | 〇 | 〇（`guest_allowed` のみ） |
| クエスト審査・承認 | 〇 | 〇 | − | − |
| 代理注文・修正 | 〇 | 〇 | − | − |
| 自身のログ閲覧 | 〇 | 〇 | 〇 | 〇 |
| 顧客管理・一括精算 | 〇 | 〇（自拠点） | − | − |
| **ナレッジ登録・公開範囲設定** | 〇 | 〇 | − | − |
| **会員データ一括インポート／名寄せ承認** | 〇 | − | − | − |
| **宿泊日数の手動増減** | 〇 | 〇（自拠点） | − | − |
| **街人登録の申請一覧・QR発行・承認** | 〇 | − | − | − |
| **ロール切替プレビュー（本番）** | 〇 | − | − | − |

> [!danger] DOM非表示は認可ではない
> 画面上の非表示はUXのための施策であり、セキュリティ境界ではない。**Supabase RLS によるサーバサイド認可を必ず併用**すること（正本 §5.9.3）。
