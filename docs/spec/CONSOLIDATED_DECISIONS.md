## 0. プロジェクトの位置づけ

- 対象: 1,000人限定の通い型自給自足コミュニティ「浮遊街」の運営支援アプリ。クエスト制・地域通貨「Uii」・暗黙知の形式知化（RAG）が三本柱。（出典: Master Index）
- 開発方針: MVPの早期構築、朝会録音・議事録・クエスト自動起案をPhase1へ前倒し、Uii機能はPhase1では「会計管理特化」に絞る。（出典: v13 §3）
- Phase区分は v13 §4 が確定版。2026-08-13レビューで追加された5ブロックのうち §5.11（メディアストレージ）と §5.8.6（会員権失効）は2026-08-15にPhase2へ再移送済み。（出典: v13 §4）

## 1. 技術スタック（確定・正式承認済み — 2026-08-15回答）

- フロントエンド: Next.js（Vercelホスティング）
- バックエンド/DB: Supabase（PostgreSQL・Auth・Realtime・RLS）— 認証・認可の単一ソース・オブ・トゥルース
- メディアストレージ: Cloud Storage for Firebase（GCS）+ Cloud Functions。Firebase Authentication / Security Rules は不採用（認可はSupabaseに一元化、署名付きURL方式）
- AI基盤: Claude API / Agent SDK。朝会音声はGemini APIへ直接投入（マルチモーダル、Whisper＋話者分離は不採用）
- RAG: ~~pgvector（Supabase内）~~ → **2026-08-16確定：line-rag-bot（Firestore）に統合**。浮遊街アプリ本体は独自のベクトル検索基盤を持たない（§10参照）
- 通知: LINE Messaging API
（出典: Master Index §4、v13 §5.1・§5.11.2、background 2026-07-09各種インフラ検討ログ）
- ✅解消済み（2026-08-15回答）: background の初期案（2026-07-06〜08、ノーコードBubble/Glide・独自EUMO直結）は不採用。後続の技術検討（2026-07-09）で収斂したVercel+Supabase+Claude/MCP構成が正式承認済み。テスト基盤（CI/単体・結合テスト方針）は依然未定のため、実装着手前に別途構築が必要（詳細: QUESTIONS.md）。

## 2. ロール・アクセス制御

- `role`: `admin` / `core_member` / `member` / `guest` / `custom`。コアメンバーはv1.10で独立ロール化。
- `member_type`（親方／街人コア／街人一般／ゲスト）は `role` と別軸のコミュニティ内の立場であり、**認可には一切使用しない**（親方44名の権限は`member`と同等）。
- `account_status`: `pre_registered` / `active` / `withdrawn`。
- UI非表示（DOM非描画）とサーバサイド認可（Supabase RLS + Edge Function）は両方必須。DOM非表示のみは認可ではない。
- ゲスト向け「ロック中クエスト」はDOMごと隠すのではなく**見せて施錠**し登録導線にする（§5.9の「隠す」原則とは逆方向、意図的な使い分け）。
（出典: v13 §2, §5.9, §5.10.6, §6）

## 4. クエスト管理

- クエストボード集約、受注申請→運営指示→Before/After写真付き完了報告→日次（1日おき）承認/差戻しサイクル。
- `execution_mode`（onsite/remote/hybrid）、`required_certification`（重機・チェーンソー・食品衛生等の安全ゲート）、`guest_allowed`フラグを保持。
- ゲスト開放判定は`guest_allowed`フラグのみで行い、カテゴリや`execution_mode`から自動導出しない（安全ゲートとの混線防止）。
- ✅解消済み（2026-08-15回答）: background（2026-07-06〜10）の「反復実行」「複数人パーティー参加・按分」「スキル連動の報酬変動」は**Phase2送りと決定**（スキルツリー機能と合わせて整理）。Phase1は「募集人数の範囲内で受注可・報酬均等割り」のシンプル運用。v13 §5.3に注記を追記済み（詳細: QUESTIONS.md）。
（出典: v13 §5.3, §5.10.6, §7）

## 5. 決済・Uii（地域通貨）

- **Phase1の扱い**: Uiiは「円価格2割引の換算表示専用」。個人のリアルタイム残高管理・失効処理・EUMO直接参照は全てPhase2以降。
- 換算式: 単品Uii = `floor(単価(円) × 0.8)`、明細行Uii = 単品Uii×数量、伝票Uii = 明細行Uiiの合算（単品ごとに丸め。伝票合計への一括掛け算は禁止）。
- 決済方式: 即時決済・後払いともに可。**Uiiによる直接決済は不可**。すべて精算QR（発行・失効基盤共通）を経由。
- ⚠️矛盾あり（v13内で明示的に無効化済み）: background（2026-07-10〜08-03のv9/v10ドラフト）では「Uii残高管理のSSOT（信頼できる唯一の情報源）はEUMO」「アプリはEUMOの非同期キャッシュ」「マイナス残高禁止でUii決済前提」という設計だった。v13 §9 #24 changelogが明示的に「[[UI_UX設計指針]]の『Uii決済前提・マイナス残高防止』は本決定により無効」と記載しており、**この矛盾は解消済み・v13が正**。[[UI_UX設計指針]] 等の子ノート自体は本リポジトリ（docs/spec/配下）にはコピーされていないが、v13 v1.12.0改訂履歴（2026-08-15）に「子ノート6本を正本へ追随させ乖離を解消」と明記されており、Obsidianボルト側では同期済みと判明（詳細: QUESTIONS.md）。
- Uiiの「3ヶ月で失効する腐る経済」概念、eumoとの非同期連携（決済ゲートウェイ方式、双方向同期はしない）という設計思想自体はbackground（2026-07-10）由来でv13のPhase2構想と整合。
（出典: v13 §5.5, §5.5.1, §9 #18・#22・#24, Master Index §2-B, background 2026-07-10各種・2026-08-03 v9/v10ドラフト）

## 6. 街人（会員）登録・アップグレード導線

- 決済フロー: アプリ内で決済情報は入力させない。「申請」→管理者が決済QRを発行・送付（LINE/アプリ内通知/対面）→ユーザーがQR決済→管理者が入金確認して承認、の5ステップ。承認操作が権限昇格のトリガー（システムは入金を自動検知できないため）。
- 特典: **宿泊券4枚（4泊分）＋ コインキャッシュバック5,000**（実データ準拠、確定値）。コインCB付与はPhase1ではシステム化せず運営がExcelで手動記録。
- ✅解消済み（2026-08-15修正）: v13 §7データ要件の「街人登録申込」エンティティ定義にあった「付与宿泊券枚数（既定3枚）」という更新漏れを「既定4枚」に修正済み（値の変更ではなく単純な表記統一）。実装時は`membership_plans`マスタを参照し、コードに直書きしないこと（この方針自体はv13で明記済み）。
（出典: v13 §5.10, §7, §9 #11・#15）

## 7. 宿泊・部屋・チェックイン

- 部屋台帳（`rooms`）と部屋割当（`room_assignments`）を新設。1部屋=1収容枠とは限らず`capacity`を持つ。割当は履歴として残し物理上書きしない。
- 予約キャンセル・ノーショーは顧客管理画面から論理削除（`cancelled_at`+理由必須）。宿泊券消費はチェックアウト時発生のため、チェックイン前キャンセルでは券の返却処理は不要。ペナルティ（キャンセル料）はPhase1では設定しない。
- 会員権の満了・宿泊券一斉失効処理は**Phase2以降**（最初の満了が2027/4/30のため、Phase1稼働期間中は発生しない）。ただしスキーマ（`memberships.expires_on`等）はPhase1で用意。
- **宿泊予約フォーム連携（2026-08-16追加）**: AS-IS＝「Googleフォーム『浮遊街 宿泊予約』→自動返信（ひかる作成）→予約担当者がTimeTreeへ手動転記」。TO-BE＝フォーム送信をトリガーに`pre_registered`予約を自動生成（イベント駆動、既定の#3方針を踏襲）し、**備考欄が空なら予約担当者の確認なしにシステムが自動確定**、備考欄に記載があれば「要確認」ステータスで担当者に通知する（現場要望を反映、確定方針）。
- **TimeTree連携は不採用（2026-08-16決定）**: 当初ICS（iCalendar）カレンダー購読による一方向同期案を検討したが、**「TimeTreeと連携するより浮遊街アプリの管理者画面で宿泊予定を確認したい」との判断により不採用**。代わりに**管理者画面に「宿泊予定カレンダー」を新設**（確定予約を日付・部屋タイプ・部屋・人数・要確認フラグで一覧化。権限は管理者・コアメンバー）し、TimeTreeは今後の宿泊予約フローで使用しない。
- ✅解消済み（2026-08-16回答、5/5点）: ①部屋タイプ選択肢は**運用中の6種（コテージA/B・アースバッグ・テント・車中泊・ゲストハウス・サロン）が正**。フォームを4種→6種へ修正する。②旅館業法必須項目（住所・前泊地・後泊地/行先）は**チェックイン時にアプリ側で収集**（Googleフォームへの項目追加はしない）。③「備考欄が空」の自動確定判定基準は**完全な空欄（無入力）のみ**（「特になし」等の定型文言は要確認扱い）。④自動返信メールの発信主体は**現状のApps Script継続**（アプリへの統合はしない）。⑤宿泊予定カレンダーのUIは**Googleカレンダーと同等の操作感**を目指す。
（出典: v13 §5.2.1, §5.2.2, §5.2.3, §5.8.6, §9 #21・#27・#28・#30）

## 8. 顧客管理・会計

- 顧客管理画面（管理者・コアメンバー専用）で伝票の明細編集・単価上書き・注文者付替・キャンセル・手動調整が可能。会計済み伝票も遡及修正可（差額を「追加請求/返金」として明示）。
- 差額の消込は「次回繰越」が基本方針（未処理のまま持ち越し、再訪時に現地精算）。
- ✅解消済み（2026-08-16回答）: 返金差額の無期限繰越は**Phase1では許可**（一定額超は運営から連絡する運用と併用）。免除操作の権限は**Phase1はコアメンバーにも許可**（管理者限定にしない）。90日滞留後は自動免除・督促は行わず**滞留フラグを立てるのみ**（運営が任意タイミングで目視対応）。
- 未会計額は円を主・Uiiを副として全画面で併記。
（出典: v13 §5.6, §9 #6・#7・#17）
