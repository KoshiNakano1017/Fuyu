## 2. ロール・アクセス制御

- `role`: `admin` / `core_member` / `member` / `guest` / `custom`。コアメンバーはv1.10で独立ロール化。
- `member_type`（親方／街人コア／街人一般／ゲスト）は `role` と別軸のコミュニティ内の立場であり、**認可には一切使用しない**（親方44名の権限は`member`と同等）。
- `account_status`: `pre_registered` / `active` / `withdrawn`。
- UI非表示（DOM非描画）とサーバサイド認可（Supabase RLS + Edge Function）は両方必須。DOM非表示のみは認可ではない。
- ゲスト向け「ロック中クエスト」はDOMごと隠すのではなく**見せて施錠**し登録導線にする（§5.9の「隠す」原則とは逆方向、意図的な使い分け）。
（出典: v13 §2, §5.9, §5.10.6, §6）

- **決定**: **`target_role` の正本は浮遊街アプリ側（正本 v13 §2）とする**
  - 決定日: 2026-08-22 / 決定者: プロジェクトオーナー（リスク回答 R4）
  - 理由: 2リポジトリに同じ4値が独立定義されており（二重管理）、片方だけ変更するとナレッジ漏洩に直結するため、
    正本の所在を1箇所に固定した。`line-rag-bot`（`app/roles.py`）は**追従側**とする。
  - 運用: ロール定義を変更するときは**必ず両リポジトリを同時に確認**する。
    `line-rag-bot` 側を先に変更してはならない。
  - 反映先: 正本 v13 §2、`Projects/line-rag-bot/app/roles.py`（追従側である旨をコメントに明記すること）

- **決定**: **LINEユーザーのロールは個別に分けず、初期メッセージの自己申告で「運営・待ち人」／「ゲスト」の2区分にする**
  - 決定日: 2026-08-22 / 決定者: プロジェクトオーナー（リスク回答 R6）
  - あわせて **`target_role` を4値（guest / member / core_member / admin）→ 2値（guest / member）へ統合**する。
  - 理由: LINE 側に会員情報を取得する API が無く、運営が手作業で `user_roles` に登録する運用が
    追いつかないため（登録漏れのユーザーが `guest` へフォールバックし、街人が必要なナレッジに到達できない）。
  - **詐称の扱い（2026-08-22 追加確定）: Phase 1 では見逃す。**
    根拠は「**LINE ボット経由で個人情報にアクセスできない**」こと。コード実査で妥当性を確認済み
    （RAG が返すのはナレッジチャンクのみ・会員データへの参照経路なし／会話履歴とエスカレーションは
    認証必須の Streamlit 管理画面からのみ閲覧可）。
    ⚠️ ただし**「個人情報ではない機微情報」（運営ノウハウ・鍵や設備の扱い・原価/単価）は到達しうる**ため、
    **その種の情報をナレッジに登録しない運用**を併せて徹底する。合言葉・招待コード照合は Phase 2 で再検討。
  - **非対称の扱い（2026-08-22 確定）: アプリは5値、LINE は2値のままでよい。**
    アプリ側（`admin`/`core_member`/`member`/`guest`/`custom`）は**画面認可**に使い、
    LINE 側（`member`/`guest`）は**ナレッジの公開範囲の出し分けのみ**に使う。用途が違うため揃える必要がない。
    マッピングは `admin`/`core_member`/`member`/`custom` → **`member`**、`guest` → **`guest`**。
    `custom` は LINE 側に対応値を作らず `member` として扱う。
    正本 v13 §2 に「アプリ5値 / LINE2値 の非対称」節として反映済み（v1.16.0）。
  - ⚠️ **共有デプロイへの注意**: `app/roles.py` を直接2値化すると、Cloud Run / Firestore を共有する
    **既存クライアントも巻き添えになる**。`feature_flags` によるテナント単位の切替が必須。
  - 反映先: `Projects/line-rag-bot/app/roles.py`・`app/line/user_roles.py`、正本 v13 §2・§6

## 5. 決済・Uii（地域通貨）

- **Phase1の扱い**: Uiiは「円価格2割引の換算表示専用」。個人のリアルタイム残高管理・失効処理・EUMO直接参照は全てPhase2以降。
- 換算式: 単品Uii = `floor(単価(円) × 0.8)`、明細行Uii = 単品Uii×数量、伝票Uii = 明細行Uiiの合算（単品ごとに丸め。伝票合計への一括掛け算は禁止）。
- 決済方式: 即時決済・後払いともに可。**Uiiによる直接決済は不可**。すべて精算QR（発行・失効基盤共通）を経由。
- ⚠️矛盾あり（v13内で明示的に無効化済み）: background（2026-07-10〜08-03のv9/v10ドラフト）では「Uii残高管理のSSOT（信頼できる唯一の情報源）はEUMO」「アプリはEUMOの非同期キャッシュ」「マイナス残高禁止でUii決済前提」という設計だった。v13 §9 #24 changelogが明示的に「[[UI_UX設計指針]]の『Uii決済前提・マイナス残高防止』は本決定により無効」と記載しており、**この矛盾は解消済み・v13が正**。[[UI_UX設計指針]] 等の子ノート自体は本リポジトリ（docs/spec/配下）にはコピーされていないが、v13 v1.12.0改訂履歴（2026-08-15）に「子ノート6本を正本へ追随させ乖離を解消」と明記されており、Obsidianボルト側では同期済みと判明（詳細: QUESTIONS.md）。
- Uiiの「3ヶ月で失効する腐る経済」概念、eumoとの非同期連携（決済ゲートウェイ方式、双方向同期はしない）という設計思想自体はbackground（2026-07-10）由来でv13のPhase2構想と整合。
（出典: v13 §5.5, §5.5.1, §9 #18・#22・#24, Master Index §2-B, background 2026-07-10各種・2026-08-03 v9/v10ドラフト）

## 6. 街人（会員）登録・アップグレード導線

  - 内容:
    1. ユーザーに**最初にカテゴリを UI から入力**してもらう
