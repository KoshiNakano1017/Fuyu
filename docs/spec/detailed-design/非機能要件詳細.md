## 2. セキュリティ

### 2-1. 認可の二重防御（最重要の不可侵ルール）

| 項目 | 内容 |
| --- | --- |
| 原則 | クライアント側のDOM非表示（画面設計.md §5）と、サーバサイド認可（Supabase RLS＋Edge Function／DB物理設計.md §6）を**必ず両方**実装する。クライアント制御のみへの依存を禁止（v13 §8, §5.9.3） |
| 認可の単一実装箇所 | ロール判定は`role`カラムのみで行い、実装箇所はSupabase（RLS＋Edge Function）に限定する。Firebase Authentication・Firebase Security Rulesでの認可判定は**禁止**（システムアーキテクチャ.mdの不可侵ルール） |
| API設計への反映 | API設計.mdの全エンドポイントで、リクエストのJWTからroleを取得し、DB物理設計.mdのRLSポリシーと同一の権限マトリクス（v13 §6）を適用する。フロント側のロール表示制御だけに依存するエンドポイントを作らない |

### 2-2. ストレージ・メディアの認可

| 項目 | 内容 |
| --- | --- |
| 格納先 | Cloud Storage for Firebase（GCS）に一本化。バケットは公開アクセス全面禁止（Uniform bucket-level access） |
| 署名付きURL有効期限 | アップロード10分／閲覧5分／**内部専用ナレッジの添付のみ2分**（より厳格） |
| アップロード完了の起点 | クライアントの完了通知ではなく、GCS Object Finalizeイベントを起点にDB（`media_assets`）へ書き戻す（通信断による孤児ファイル対策） |
| 孤児ファイル防止 | `pending`のまま24時間実体未確認の`media_assets`レコード、DB未登録のストレージオブジェクトを定期ジョブで検出・削除する（Cloud Scheduler等での日次バッチを想定） |

### 2-3. ナレッジ検索の情報隔離

**2026-08-16確定**：ナレッジ・RAG基盤はline-rag-bot（Firestore）へ統合されたため、`target_role`による
メタデータフィルタの実装責務もline-rag-bot側に移った（DB物理設計.md §4は参考記録のみ）。浮遊街アプリ
本体はエンドユーザー向け検索UIを持たないため、隔離ルールの適用対象はline-rag-bot側のWebhook応答のみと
なる。プロンプト指示（「内部情報は答えないで」等）を隔離手段として使わない、という原則自体は
line-rag-bot側の設計（docs/06-マルチテナント設計.md等）に引き継がれる想定。

### 2-4. 個人情報保護

| 項目 | 内容 |
| --- | --- |
| 認証方式 | メール認証、Google OAuth、LINE OAuth（システムアーキテクチャ.md） |
| 通信・保存時暗号化 | TLS 1.2以上、Supabase標準DB暗号化、Vercel暗号化基盤 |
| 表示制御 | 氏名・連絡先・運営メモは管理者・コアメンバー画面にのみ描画し、一般会員・ゲスト向けAPIレスポンスに**含めない**（v13 §8）。API設計.mdの各エンドポイントのレスポンススキーマ設計時、ロールに応じたフィールドマスキングを行う必要がある（本書での新規指摘。API設計.md側には未反映のため、実装時に反映すること） |
| 退会プロセス | ①論理削除 → ②30日後匿名化 → ③必要に応じ物理削除（システムアーキテクチャ.md） |
| データ最小化 | ニックネーム登録を推奨する一方、宿泊法対応のため氏名・住所等は正式保持（QUESTIONS.md「個人情報方針の大転換」で回答済み。利用規約反映は別途要確認） |

### 2-5. 会員データインポートの再実行安全性

同一ファイルの二重取込で重複会員を生成しないこと。`contact_info`のユニーク制約と取込前プレビューで担保し、
インポートは原子的に実行、途中失敗時は全件ロールバックする（v13 §8, API設計.md `/api/admin/members/import/*`）。

## 5. 本書で新規に発見した論点

DB物理設計.md・API設計.mdを非機能要件の観点で見直した結果、以下の未設計箇所を発見した。

1. **署名付きURL発行APIがAPI設計.mdに未掲載**。メディアアップロード（クエスト完了報告の写真、朝会音声、ナレッジ添付）は全て署名付きURL方式が前提（v13 §5.11.2）だが、API設計.mdのエンドポイント一覧に`POST /api/media/signed-upload-url`相当が抜けている。次回API設計.md改訂時に追加が必要。
2. **ロール別レスポンスマスキングの設計が未着手**。API設計.mdの各エンドポイントは「認可ロール」列でアクセス可否は示したが、レスポンスに含めるフィールド自体をロールで出し分ける設計（個人情報の表示制御）は反映されていない。
3. **10年監査ログの保存・アーカイブ方針が未確定**。テーブル自体は取引明細方式のため長期保存に適するが、10年経過後の扱い（アーカイブDB分離等）は未設計。
4. **孤児ファイル検出バッチ・インポート原子性の実装方式（DBトランザクションかアプリ層制御か）が未確定**。
