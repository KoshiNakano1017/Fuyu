## 2. セキュリティ

### 2-1. 認可の二重防御（最重要の不可侵ルール）

| 項目 | 内容 |
| --- | --- |
| 原則 | クライアント側のDOM非表示（画面設計.md §5）と、サーバサイド認可（Supabase RLS＋Edge Function／DB物理設計.md §6）を**必ず両方**実装する。クライアント制御のみへの依存を禁止（v13 §8, §5.9.3） |
| 認可の単一実装箇所 | ロール判定は`role`カラムのみで行い、実装箇所はSupabase（RLS＋Edge Function）に限定する。Firebase Authentication・Firebase Security Rulesでの認可判定は**禁止**（システムアーキテクチャ.mdの不可侵ルール） |
| API設計への反映 | API設計.mdの全エンドポイントで、リクエストのJWTからroleを取得し、DB物理設計.mdのRLSポリシーと同一の権限マトリクス（v13 §6）を適用する。フロント側のロール表示制御だけに依存するエンドポイントを作らない |

### 2-2. ストレージ・メディアの認可

| 項目 | 内容 |
| --- | --- |
| 格納先 | Cloud Storage for Firebase（GCS）に一本化。バケットは公開アクセス全面禁止（Uniform bucket-level access） |
| 署名付きURL有効期限 | アップロード10分／閲覧5分／**内部専用ナレッジの添付のみ2分**（より厳格） |
| アップロード完了の起点 | クライアントの完了通知ではなく、GCS Object Finalizeイベントを起点にDB（`media_assets`）へ書き戻す（通信断による孤児ファイル対策） |
| 孤児ファイル防止 | `pending`のまま24時間実体未確認の`media_assets`レコード、DB未登録のストレージオブジェクトを定期ジョブで検出・削除する（Cloud Scheduler等での日次バッチを想定） |

### 2-3. ナレッジ検索の情報隔離

**2026-08-16確定**：ナレッジ・RAG基盤はline-rag-bot（Firestore）へ統合されたため、`target_role`による
メタデータフィルタの実装責務もline-rag-bot側に移った（DB物理設計.md §4は参考記録のみ）。浮遊街アプリ
本体はエンドユーザー向け検索UIを持たないため、隔離ルールの適用対象はline-rag-bot側のWebhook応答のみと
なる。プロンプト指示（「内部情報は答えないで」等）を隔離手段として使わない、という原則自体は
line-rag-bot側の設計（docs/06-マルチテナント設計.md等）に引き継がれる想定。

| 表示制御 | 氏名・連絡先・運営メモは管理者・コアメンバー画面にのみ描画し、一般会員・ゲスト向けAPIレスポンスに**含めない**（v13 §8）。~~API設計.mdの各エンドポイントのレスポンススキーマ設計時、ロールに応じたフィールドマスキングを行う必要がある（本書での新規指摘。API設計.md側には未反映のため、実装時に反映すること。**2026-08-28 QUESTIONS.mdへ正式起票 → 本書§7 F-2**）~~ → **2026-09-05 確定：列単位のマスキングは行わない**（下記「保護方式」の行を参照） |

### 2-5. 会員データ投入の再実行安全性（2026-08-28 現行方針へ改訂）

同一データの二重投入で重複会員を生成しないこと。`contact_info`のユニーク制約で担保し、
投入は原子的に実行、途中失敗時は全件ロールバックする（v13 §8）。

なお、インポートAPI（`/api/admin/members/import/*`）は**2026-08-16に不要化済み**（API設計.md §2-7）。
実名を含む会員データは public リポジトリへ持ち込めないため（`CLAUDE.md` §3.1・§7.1）、
実データの投入は**リポジトリ外のローカル環境から直接行う**。本要件（ユニーク制約・原子性・全件ロールバック）は
そのローカル投入手順にも同様に適用する。

### 2-6. 公開エンドポイントの防御（2026-08-28 新設）

2026-08-23 の決定 #46（Googleフォーム廃止・公開予約ページ `/reserve` 新設）により、本アプリは初めて
**未認証で到達できる書き込み経路**を持つことになった。API設計.md §2-2b の防御要件を非機能要件として正式収録する。

| 項目 | 内容 | 出典 |
| --- | --- | --- |
| サーバ経由の強制 | `/api/public/*` はクライアントから Supabase へ直接 INSERT させない。Server Action / Route Handler 内部で `service_role` を用いサーバ側でのみ書き込む。**anonキーに `check_ins` 等のINSERT権限を与えない**（RLSの緩みがそのまま個人情報テーブルへの書き込み口になるため） | API設計.md §2-2b |
| ボット対策 | Cloudflare Turnstile を予約送信前に必須化（フォーム時代は検証手段が無く、架空予約で枠が埋まっても検知できなかった） | 同上 |
| レート制限 | OTP発行は同一メール24時間3件・同一IP単位で制限し、超過は429を返す | 同上 |
| OTP保護 | `code_hash` のみ保存（**平文の保存・ログ出力を禁止**）・TTLは数分・`attempt_count` 上限超過で無効化 | DB物理設計.md §3-6 |
| 名寄せの抑制 | OTPで本人性が確認できても既存会員アカウントへ自動連携しない。候補が複数ヒットした場合は運営承認キューへ回す（予約時点で確定させるのは宿泊枠であって人物の同定ではない） | v13 §5.8.3・API設計.md §3-4注記 |
| **ネットワーク層の防御**（2026-09-05 追加） | **`/api/public/*` に Vercel WAF の IP単位レート制限を設定する**（Hobby のカスタムルール3本のうち **R1**）。`/api/public/*` は**必ず Vercel を通る**（`service_role` はサーバ側のみ）ため、WAF が確実に効く数少ない経路である | [[システムアーキテクチャ]]「ネットワーク層の防御 → ★ 採用する構成」・**F-9** |
| **`anon` 権限ゼロ**（2026-09-05 追加） | 上記「サーバ経由の強制」を**INSERT 権限だけでなくテーブル権限全般へ拡張**する。**`anon` にテーブル・ビュー・関数の権限を与えない**（原則ゼロ）。`anon` キーは公開情報であるため、**読めるものを無くすこと自体が直アクセス経路の防御になる**。DDL 本体は `DB物理設計.md` §6 | API設計.md **§1-1**・**F-9** |

> [!success] 2026-09-05 更新: 本節の防御は「3前線」構成の**前線1・前線2の一部**として位置づけ直された
> ネットワーク層の防御の全体像（前線1 Vercel WAF ／ 前線2 `anon` 権限の削り込み＋RLS ／ 前線3 GCS の IAM）は
> [[システムアーキテクチャ]]「ネットワーク層の防御 → **★ 採用する構成**」を正とする。**F-9 を参照**。

> [!warning] ⚠️ **新規論点（2026-09-05 発見）: Supabase 既定SMTP の「2通/時」が本節の OTP 発行と衝突する**
> Supabase の**既定の組み込みSMTP は認証メールが 2通/時**に制限されている（無料枠・既定設定）。
> 本節は OTP 発行を「同一メール24時間3件」で制限する設計だが、**その手前でプラットフォーム側の上限に当たり、
> 公開予約ページが実運用に耐えない**。カスタムSMTP（Resend / SendGrid 等）を設定すると既定 30件/時となり、
> ダッシュボードの Authentication > Rate Limits で調整可能になる。
> **→ 「無料枠で開始する」決定（§7-4）の下でも、カスタムSMTP の用意は事実上の必須要件になる。**
> **⚠️ 要確認**: 採用するSMTPプロバイダと、その無料枠での1日あたり送信可能数（費用発生の有無）。`QUESTIONS.md` へ起票。

> [!note] Turnstile の適用箇所は2つある（混同しないこと）
> ① **予約フォーム**（本節の「ボット対策」）＝ `/reserve` の送信前チェック。
> ② **Supabase Auth**（新規／前線2）＝ **サインアップ・サインイン・パスワードリセット**に適用する。
> Supabase はダッシュボードの Authentication > Bot and Abuse Protection で hCaptcha / Turnstile を組み込みで有効化できる。
> ②は**攻撃者が正規のJWTを取得して RLS 越しに正当な範囲を読むこと**を防ぐ関門であり、①とは目的が異なる。
> **⚠️ 要確認**: サインアップ経路の一部で CAPTCHA が迂回される旨の公開Issue報告がある（supabase/supabase #29231・#35750）。
> 有効化しただけで満足せず、**CAPTCHAトークン無しのリクエストが拒否されることをテストで確認すること**。

### 2-7. 暗号化・鍵管理（2026-08-28 新設）

#### 経路の暗号化（通信）

| 区間 | 方式 | 備考 |
| --- | --- | --- |
| ブラウザ ⇄ Vercel | TLS 1.2以上（Vercel管理・証明書自動更新） | HSTS 等のセキュリティヘッダを Next.js の `headers` 設定で有効化する（§7 F-4） |
| Vercel ⇄ Supabase／外部API | TLS（各マネージドサービスの標準） | 平文HTTP接続を許可しない |
| クライアント ⇄ GCS | HTTPS（署名付きURLは V4 署名） | **URL自体が資格情報**のため、発行済みURLをログ・外部サービスへ残さない（v13 §5.11.2） |

#### 保存時の暗号化（at rest）

| 対象 | 方式 |
| --- | --- |
| Supabase PostgreSQL | プロバイダ管理の保存時暗号化（AES-256）。日次バックアップも同様に暗号化される（**⚠️ 2026-09-05：無料枠運用の決定により日次自動バックアップ自体が存在しない。後段は Pro 移行後の前提 → §7-4**） |
| Cloud Storage for Firebase | Google管理鍵によるデフォルト暗号化（全オブジェクト・追加設定不要） |
| 顧客管理鍵（CMEK） | **Phase 1 では不採用（★提案）**。鍵運用の負荷に対し、プロバイダ管理暗号化＋RLS＋署名付きURL＋バケット非公開で §7 の主要脅威経路は塞がるため |

#### アプリケーション層のハッシュ化・トークン

| 対象 | 設計 | 状態 |
| --- | --- | --- |
| `reservation_otps.code_hash` | **HMAC-SHA256＋サーバ側シークレット（ペッパー）を提案**。短命の数字コードは `attempt_count` 上限とTTLでオンライン総当たり面を閉じたうえで、DB流出時のオフライン辞書化をペッパーで防ぐ。bcrypt等の低速ハッシュは、コードが短命・使い捨てであることから過剰と判断 | ★提案（QUESTIONS.md 起票済み） |
| 精算QR・入金QRトークン（`orders.settlement_qr_token`／`membership_applications.qr_token`） | **暗号学的乱数128bit以上・TTL・単回使用（清算完了／承認時に失効）を提案**。現設計は平文 `text` 保存で、`settlement_qr_token` には有効期限カラムが無い（§7 F-1） | ★提案（QUESTIONS.md 起票済み。DB物理設計の変更を伴う） |
| パスワード | Supabase Auth の管理に委ねる（bcrypt）。アプリ側で独自にパスワードを保存しない | 確定（技術スタックに内包） |
| 予約セッショントークン | 暗号学的乱数・短命。OTP検証成功時のみ発行 | API設計.md §2-2b どおり |

#### 鍵・シークレット管理

| 項目 | 内容 |
| --- | --- |
| 保管場所 | Vercel 環境変数／GitHub Actions Secrets／Supabase secrets。Cloud Functions のサービスアカウント鍵は **Secret Manager**（v13 §5.11.2） |
| `service_role` キー | サーバサイド（Edge Function / Server Actions）のみで使用し、クライアントへ渡さない（`CLAUDE.md` §3.2・`.env.example` 注記） |
| ローテーション | 漏えい（コミット混入含む）時は該当キーを**必ず即時ローテーション**（`CLAUDE.md` §3.3）。定期ローテーションの周期は運用開始時に定める |
| ログのマスキング | トークン・個人情報をログへ出力しない。`user_id` は可・`email` は不可（`CLAUDE.md` §3.2） |

#### カラムレベル暗号化の採否（★提案）

**Phase 1 では不採用を提案**する（QUESTIONS.md 起票済み・承認までは確定扱いしない）。

1. `contact_info` は名寄せの第1優先キーでユニーク制約が必要（v13 §5.8.3）。検索可能なまま暗号化するには決定的暗号化が必要になり、実装・鍵運用の複雑度が保護効果に見合わない
2. 保存時暗号化＋RLS＋ロール別マスキング（§7 F-2）＋バケット非公開で、脅威モデル上の主要な漏えい経路は塞がる
3. Supabase Vault / pgsodium によるカラム暗号化は **Phase 2 以降の再評価事項**とする

> 「A6 の10年蓄積は **DB 500MB 上限**と正面から衝突する」問題が解消する。
>
> | 論点 | 決定 |
> | --- | --- |
> | 正本の置き場所 | **GCS の監査専用バケット**（メディア用バケットとは**必ず分離**する。メディア側の「一時ファイル7日削除」ライフサイクルと削除不可設定が正面衝突するため） |
> | 改ざん耐性 | **Retention Policy ＋ Bucket Lock**。ロック後は**管理者でも削除・改ざんできない**。あわせて書き込み用SAを**「作成のみ」**権限に絞る（IAM で消す権限を渡さない／Bucket Lock で権限があっても消せなくする、の二重防御） |
> | ストレージクラス | **Nearline → Archive の自動遷移**（削除するライフサイクルは設定しない） |
> | Postgres 側の保持期間 | **★提案**: 理由必須操作の監査ログ **90日** ／ ログイン履歴 **30日** ／ AI対話履歴は**置かない**。根拠と要確認事項は下記 |
> | **⚠️ アクセス制御** | **Postgres の外に出た時点で RLS が効かなくなる**。GCS 上の監査ログのアクセス制御は **GCP IAM へ移る**（§7-1 の S 格付け情報を含みうるため、IAM を RLS と同等の厳格さで設計すること） |
> | **⚠️ 依存** | **日次エクスポートは「非同期ジョブ実行基盤の未決（`WBS_Phase1.md` §16-1 の真のブロッカー）」に依存する**。基盤が決まるまで実装に着手できない。§7-4 の `pg_dump` 日次エクスポートと**同じジョブレーンに相乗り可能** |
> | 🚫 **禁止事項** | **監査ログと AI対話履歴を `line-rag-bot` のナレッジ空間へ投入してはならない**（v13 §9 #61 の個人情報ガードが未決。監査ログは氏名・連絡先・金額・運営メモを構造的に含み、LINE 側ロールは自己申告のため `target_role` はガードにならない） |
>

### ⚠️ 「全面無料枠」は GCP には当てはまらない（2026-09-05 確定）

> [!warning] 正確には「**Supabase と Vercel は無料枠、GCP は従量課金**」である
> `CONSOLIDATED_DECISIONS.md` §1 の 2026-09-05 決定は「コストは全面的に無料枠で開始する」と記録しているが、
> これは **Vercel と Supabase について正しく、GCP については正しくない**。
> 上表の **Blaze プランは従量課金であり、請求先アカウントの紐付けが前提**である。

| プラットフォーム | 課金モデル | 超過時の挙動 |
| --- | --- | --- |
| **Vercel** | **Hobby（無料）** | 制限に当たると**止まる**。非商用利用限定（§7-4） |
| **Supabase** | **無料枠**（dev / prod とも） | 上限に当たると**止まる**（DB 500MB・プロジェクト2つ） |
| **GCP**（Cloud Storage / Cloud Functions / Cloud Scheduler） | **⚠️ Blaze（従量課金）** | **⚠️ 止まらず課金され続ける**（上限のない従量課金） |

**なぜ区別が必要か**: Vercel Hobby / Supabase 無料枠が「**超えたら止まる**」のに対し、
**GCP は「超えたら課金され続ける」**。したがって **GCP だけは、コスト暴走に対する能動的な監視が必要**になる。
**上表の予算アラート（月5,000円）が、その監視の役割を担う。**
これは**コスト管理であると同時に、§7-2 の D（サービス妨害）に対する検知手段**でもある（大量アップロードによる課金増を検知する）。

- 本設計で **Blaze が必須になる要素**: メディア用 GCS バケット、**監査ログ用 GCS バケット（§3 A6）**、
  ライフサイクル管理、メディア後処理の Cloud Functions、日次バッチの Cloud Scheduler、
  および §7-4 の緩和策である `pg_dump` の GCS 日次エクスポート
- **⚠️ 要確認**: **監査ログの GCS 保管を追加したことで、月5,000円という予算アラート水準が妥当かを再確認する**必要がある。
  Nearline / Archive の単価は低いものの、**10年間 削除されずに積み上がる**性質のデータが新たに加わったためである。
  費用試算は**未実施**（§6 #2 の試算に含める）
- **⚠️ 要確認**: Archive クラスは**取り出し時の費用と最低保存期間の課金**が発生するため、
  遷移までの日数（例: 90日で Nearline、365日で Archive）は費用試算のうえ確定すること
