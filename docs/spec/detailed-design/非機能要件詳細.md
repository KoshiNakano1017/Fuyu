## 2. セキュリティ

### 2-1. 認可の二重防御（最重要の不可侵ルール）

| 項目 | 内容 |
| --- | --- |
| 原則 | クライアント側のDOM非表示（画面設計.md §5）と、サーバサイド認可（Supabase RLS＋Edge Function／DB物理設計.md §6）を**必ず両方**実装する。クライアント制御のみへの依存を禁止（v13 §8, §5.9.3） |
| 認可の単一実装箇所 | ロール判定は`role`カラムのみで行い、実装箇所はSupabase（RLS＋Edge Function）に限定する。Firebase Authentication・Firebase Security Rulesでの認可判定は**禁止**（システムアーキテクチャ.mdの不可侵ルール） |
| API設計への反映 | API設計.mdの全エンドポイントで、リクエストのJWTからroleを取得し、DB物理設計.mdのRLSポリシーと同一の権限マトリクス（v13 §6）を適用する。フロント側のロール表示制御だけに依存するエンドポイントを作らない |

### 2-2. ストレージ・メディアの認可

| 項目 | 内容 |
| --- | --- |
| 格納先 | Cloud Storage for Firebase（GCS）に一本化。バケットは公開アクセス全面禁止（Uniform bucket-level access） |
| 署名付きURL有効期限 | アップロード10分／閲覧5分／**内部専用ナレッジの添付のみ2分**（より厳格） |
| アップロード完了の起点 | クライアントの完了通知ではなく、GCS Object Finalizeイベントを起点にDB（`media_assets`）へ書き戻す（通信断による孤児ファイル対策） |
| 孤児ファイル防止 | `pending`のまま24時間実体未確認の`media_assets`レコード、DB未登録のストレージオブジェクトを定期ジョブで検出・削除する（Cloud Scheduler等での日次バッチを想定） |

### 2-3. ナレッジ検索の情報隔離

**2026-08-16確定**：ナレッジ・RAG基盤はline-rag-bot（Firestore）へ統合されたため、`target_role`による
メタデータフィルタの実装責務もline-rag-bot側に移った（DB物理設計.md §4は参考記録のみ）。浮遊街アプリ
本体はエンドユーザー向け検索UIを持たないため、隔離ルールの適用対象はline-rag-bot側のWebhook応答のみと
なる。プロンプト指示（「内部情報は答えないで」等）を隔離手段として使わない、という原則自体は
line-rag-bot側の設計（docs/06-マルチテナント設計.md等）に引き継がれる想定。

### 2-5. 会員データ投入の再実行安全性（2026-08-28 現行方針へ改訂）

同一データの二重投入で重複会員を生成しないこと。`contact_info`のユニーク制約で担保し、
投入は原子的に実行、途中失敗時は全件ロールバックする（v13 §8）。

なお、インポートAPI（`/api/admin/members/import/*`）は**2026-08-16に不要化済み**（API設計.md §2-7）。
実名を含む会員データは public リポジトリへ持ち込めないため（`CLAUDE.md` §3.1・§7.1）、
実データの投入は**リポジトリ外のローカル環境から直接行う**。本要件（ユニーク制約・原子性・全件ロールバック）は
そのローカル投入手順にも同様に適用する。

**未認証で到達できる書き込み経路**を持つことになった。API設計.md §2-2b の防御要件を非機能要件として正式収録する。

| 項目 | 内容 | 出典 |
| --- | --- | --- |
| サーバ経由の強制 | `/api/public/*` はクライアントから Supabase へ直接 INSERT させない。Server Action / Route Handler 内部で `service_role` を用いサーバ側でのみ書き込む。**anonキーに `check_ins` 等のINSERT権限を与えない**（RLSの緩みがそのまま個人情報テーブルへの書き込み口になるため） | API設計.md §2-2b |
| ボット対策 | Cloudflare Turnstile を予約送信前に必須化（フォーム時代は検証手段が無く、架空予約で枠が埋まっても検知できなかった） | 同上 |
| レート制限 | OTP発行は同一メール24時間3件・同一IP単位で制限し、超過は429を返す。**確定値は §2-6a（2026-09-22 確定 ／ F-7）を正とする** | 同上・**§2-6a** |
| OTP保護 | `code_hash` のみ保存（**平文の保存・ログ出力を禁止**）・TTLは数分・`attempt_count` 上限超過で無効化 | DB物理設計.md §3-6 |

### 2-6a. ★ レート制限の確定値（2026-09-22 確定 ／ F-7）

**本節が F-7（レート制限の具体値が未定義）への回答である。** 適用先は 2026-09-05 に確定していたが、
**いくつにするか**が空白のまま残っていた。

> [!danger] パスワードを持たない設計では、試行回数の上限がそのまま乗っ取り耐性になる
> 会員ログインは **6桁のメールOTP＝100万通り**しかない（v13 §5.2.6）。
> パスワード方式なら「長さ・文字種・ハッシュ」が防壁になるが、本アプリは
> **保存すべき秘密を持たないことを選んで**それを捨てている。
> 肩代わりしているのが**試行回数の上限**であり、**値の未定義は乗っ取り耐性の未定義**を意味する。
> 破られた先にあるのは**実名・住所を持つ会員アカウント**（v13 §7）である。

#### ① 日次の送信予算（**これが実効上の天井**）

**Resend 無料枠は 月3,000通・かつ 1日100通。日次キャップが先に効く**（§2-6 の 2026-09-10 注記）。
枯らされると**正規の会員が誰もログインできなくなる**ため、用途ごとに予算を切る。

| 用途 | 日次予算 | 備考 |
| --- | ---: | --- |
| 会員ログインOTP | **30通/日** | Supabase Auth 経由 |
| 公開予約OTP | **20通/日** | 自前実装（`reservation_otps`）。Supabase Auth を経由しない |
| 招待（経路B） | **50通/日** | 対象105名 → **3日に分かれる**。v13 §5.2.6 経路B |
| **合計** | **100通/日** | Resend 無料枠の上限と一致させる |

⚠️ 超過すると送信が失敗する。**日次送信数を記録し、閾値超過を運営へ知らせる**こと（実装は `1-7` の範囲）。

#### ② 会員ログイン（Supabase Auth ／ Authentication > Rate Limits）

> [!warning] **ログインの総当たりを Vercel WAF で守ることはできない**
> `supabase-js` は `https://<ref>.supabase.co/auth/v1/*` へ**ブラウザから直接**発行され、**Vercel を通らない**。
> したがって**前線2（Supabase Auth 側の設定）が本体**である（[[システムアーキテクチャ]]「R2 の妥当性」）。

| 項目 | 確定値 | 根拠 |
| --- | --- | --- |
| OTP の有効期限（TTL） | **10分** | 既定の 3600秒（1時間）は長すぎる。**受信箱に1時間有効なコードを残さない** |
| 同一アドレスへの再送間隔 | **60秒** | 連打による送信枠の浪費を抑える |
| メール送信数 | **20通/時** | ①の日次予算30通に対するバースト上限。⚠️ 経路A（来訪時の登録）で**現場の同時登録が20人/時を超える**運用になったら引き上げる |
| 検証試行（同一IP） | **10回/5分** | 100万通りを 2,880回/日 で試すと**約347日**かかる。実用上破れない |
| 同一コードの失敗上限 | **5回で無効化** | IPを分散されても**1コードあたりの試行を5回に閉じる**。⚠️ Supabase Auth 側で設定できない場合は**アプリ側で実装するか、できないこと自体を本節へ追記する**こと |

### 7-4a. ⚠️ LINE詐称リスクの受容根拠が変わった（2026-09-10）

> [!warning] **「経路が存在しない」という構造的な担保は、もう成立しない**
> 旧根拠は次のとおりだった。
>
> > LINEボット経由では**個人情報に到達できない**。RAG が返すのは `knowledge_{tenant}` の
> > ナレッジチャンクのみで、**会員データを参照する経路が存在しない**（コード実査で確認済み）
>
> **2026-09-03 の #61 決定（アプリのデータをナレッジ空間へ投入する）により、この前提は崩れた。**
> 投入を始めた時点で「会員データ由来のテキストが `knowledge_*` に存在する」状態になるためである。

**2026-09-10 のオーナー決定により、担保手段は次へ差し替わった**（`CONSOLIDATED_DECISIONS.md` §16-3）。

| | 旧（〜2026-09-03） | 新（2026-09-10〜） |
| --- | --- | --- |
| 担保の性質 | **構造的な不到達**（そもそも経路が無い） | **実装とテストで担保する到達制御** |
| 具体手段 | 「その種の情報をナレッジに登録しない」**人手の運用ルール** | 投入時に `pii_flag` を付与し、**LINE Webhook 経路の検索で無条件除外** |
| 詐称に破られないか | 破られない（経路が無いため） | 破られない（**判定軸がロールではなくチャネル**。利用者は LINE から来た事実を詐称できない） |
| 弱点 | 人手のルールは自動パイプラインでは守れない | **PII 検出器の再現率がそのまま防御力になる** |

> [!danger] 実装時の必須条件（ここを外すと受容の前提が崩れる）
> 1. **`target_role` で判定してはならない。** LINE 側ロールは自己申告であり、
>    ロールで出し分けた時点で「詐称を見逃す」決定と併用できなくなる（`QUESTIONS.md` が**非推奨**とした案b）。
>    **判定は LINE Webhook というチャネルそのものに固定する**
> 2. **フィルタは単一のチョークポイントに置く。** 検索関数の内部に埋め込み、呼び出し側の指定に委ねない。
>    **フィルタ無しで検索できる経路を作らない**ことをテストで固定する（`CLAUDE.md` §4.4 の「個人情報」領域＝**テスト必須**）
> 3. **`pii_flag` は再計算可能にし、再スキャンジョブを回す**（検出漏れを後から回収できるようにする）。
>    Cloud Scheduler の定時レーン（`システムアーキテクチャ.md`）に載せられる
> 4. **`find_nearest` への移行を先行させることが望ましい。** 現行の全件スキャン方式ではフィルタが
>    アプリコード頼みになり上記2の逸脱が起きやすい。移行後は equality 事前フィルタとして
>    **DB 層で強制**できる

**再評価時期**: PII 検出器の実装時、および `find_nearest` 移行時。
