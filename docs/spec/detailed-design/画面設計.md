## 1. アクター・デバイスマトリクス（UI_UX設計指針より再掲・2026-08-16修正）

> [!note] 2026-08-16修正：クエスト受注の表現を訂正
> 旧版は「街人・ゲスト」を1行にまとめ「クエスト」を両者共通の特記事項としていたが、これは誤解を招く
> 表現だった。**クエストの受注は原則member（街人）以上のみ**であり、guestは`guest_allowed=true`と
> 明示されたクエストのみ例外的に受注可（それ以外は🔒施錠表示で街人登録へ誘導するだけ、正本§5.10.6・
> A3参照）。既存の`guest_allowed`方式そのものは変更しない（今回の修正は本表の表現のみ）。あわせて
> 「AI質問」の記載は削除（アプリ内AIチャットUIは持たない。案内はLINE＝浮遊街コンシェルジュに一本化、
> v13 §9 #31）。

| アクター | ロール | デバイス | 特記 |
| --- | --- | --- | --- |
| 街人 | `member` | スマートフォン（モバイルファースト） | クエスト受注・オーダー・宿泊確認。街の案内はLINE（浮遊街コンシェルジュ）を利用（アプリ内チャットUIなし） |
| ゲスト | `guest` | スマートフォン（モバイルファースト） | オーダー・宿泊確認。**クエストは`guest_allowed=true`の一部のみ受注可**（他は🔒施錠表示のみで受注不可、街人登録への誘導導線）。街の案内はLINE（浮遊街コンシェルジュ） |
| コアメンバー・ボラスタ | `core_member` | タブレット | 注文管理・代理入力・宿泊者確認。ナレッジ登録は浮遊街コンシェルジュ（line-rag-bot）管理画面で行う |
| 管理者 | `admin` | PC | ダッシュボード・マスタ管理・街人登録承認（会員一括インポートはPhase1では実装不要、C6参照） |

ロール別UI表示制御（DOM非描画＋サーバサイド認可の両方必須）は正本§5.9・WBS §2-3を参照。本書の各画面には
「対象ロール」列を必ず付け、非対象ロールにはDOMごと出さない前提で設計する。

## 3. 画面遷移（概念フロー）

### 3-1. ゲスト初回訪問〜チェックイン
```
[Googleフォーム(外部)] → (自動でpre_registered予約生成) → A1 登録/チェックイン
  → 名寄せ一致: 「おかえりなさい」表示 → A2 ホーム
  → 名寄せなし: ニックネーム・誕生年月入力 → A2 ホーム
```
※フォーム連携の詳細（自動確定／要確認の分岐）はC10と同様、§5.2.3のドラフト状態に依存する部分がある。

### 3-2. クエスト受注〜完了報告〜承認
```
A3 クエスト一覧 → (guest_allowedチェック。falseならA8街人登録導線へ分岐)
  → A3 詳細 → 受注申請 → [運営審査] → B5 実行指示
  → 現場作業 → A4 完了報告(Before/After写真必須)
  → B5 日次承認/差戻し → (承認) → A2 ホーム(獲得XP表示) / A6 マイログ
```

### 3-3. ゲスト→街人アップグレード
```
A3 施錠クエスト(🔒) タップ → A8 街人登録モーダル(入力→確認) → 申請送信
  → C7 街人登録申請一覧(admin) → QR発行・送付 → (ユーザーがQR決済)
  → C7 入金確認 → 承認 → ロール昇格(guest→member) + 特典付与(宿泊券4枚+CB5000)
  → A2 ホーム(街人として再ログイン)
```

### 3-4. 注文〜精算
```
A5 セルフオーダー / B3 代理注文 → 注文確定(未会計計上)
  → (即時決済: その場でQR発行) or (後払い: 未会計のまま蓄積)
  → C2 一括精算QR発行 → ユーザーがQR決済 → 精算完了
  → 遡及修正が必要な場合: C9 顧客管理画面から伝票編集 → 差額算出 → 8-3差額繰越 or 即時精算
```

### 3-5. ナレッジ登録〜検索（2026-08-16再改訂：API連携なし）
```
B9/C5「浮遊街コンシェルジュ管理画面を開く」ボタン → 浮遊街コンシェルジュ（line-rag-bot）Streamlitを別タブで起動
  → [浮遊街アプリの関与はここまで。以降は全て浮遊街コンシェルジュStreamlit上で完結]
  → Streamlit上でナレッジ登録・編集
  → (LINE上でユーザーが質問) → 浮遊街コンシェルジュのWebhookが検索・回答生成
    → (信頼度十分: 回答+出典表示) / (信頼度不足: エスカレーション→運営LINE通知)
  → 未回答一覧の確認・代理回答も浮遊街コンシェルジュStreamlit上で実施（浮遊街アプリ側に一覧表示機能なし）
```
> 検索・回答生成・ナレッジ登録・未回答エスカレーション対応は全て浮遊街コンシェルジュ（line-rag-bot、
> Streamlit＋LINE Webhook）側で完結し、浮遊街アプリは管理画面からのリンク導線のみを担当する
> （アプリ内AIチャットUIは持たない。旧A7画面は削除。API連携ゼロ・2026-08-16オーナー最終判断）。
> 「浮遊街コンシェルジュ」は本アプリにおけるline-rag-botの利用者向け呼称（2026-08-16命名）。
> システム名・リポジトリ名としての`line-rag-bot`自体は変更しない。

### A10. メディアライブラリ（動画・写真の用途別ソート・AIキャプション生成、2026-08-16新設）

> [!success] Phase1へ前倒し（2026-08-16オーナー指示）
> 従来のDB物理設計.md §7では`media_assets`をPhase2送りとしていたが、本機能の新規要望に伴い
> **Phase1スコープへ前倒し**する。詳細テーブル設計はDB物理設計.md §3-7、APIはAPI設計.md §2-10参照。

**コンセプト**：現場で撮影した動画・写真を各自（全ロール）がアップロードし、「何に使いたいか」
（インスタグラム投稿／資料作成 等）を入力するだけで、AIがその用途に合いそうな順に並べ替え、
キャプション案まで自動生成する。

| 領域 | 内容 |
| --- | --- |
| アップロード | カメラロールから複数選択 or その場で撮影。Cloud Storage for Firebase（統一メディア基盤）へ署名付きURL方式で直接アップロード（v13 §5.11.2の既存原則を踏襲、動画も同一基盤） |
| 用途入力 | アップロード直後にモーダルで「用途」を選択・自由入力（プリセット：インスタグラム投稿／ブログ・資料作成／その他自由入力のタグ）。複数用途の同時選択可 |
| AI処理 | Gemini（マルチモーダル、既存の朝会音声処理と同じ基盤）が画像/動画を解析し、①用途ごとの適合度スコア（`ai_purpose_score`）②キャプション案（`ai_caption`）を非同期生成。処理中は「AI解析中…」のプレースホルダー表示 |
| 一覧・ソート | 用途タグで絞り込み、適合度スコア降順でグリッド表示（Instagram風のマソンリーレイアウトを想定）。各サムネイルにAIキャプション案を重ねて表示し、タップで採用/編集/コピー |
| 再解析 | 用途タグを追加・変更した場合は「再解析」ボタンでAI処理を再実行 |
| クエスト連携（任意） | クエスト完了報告（A4）のBefore/After写真からもこのライブラリへ登録できる導線を設ける（`linked_work_log_id`で紐付け） |

> ②動画のサムネイル生成・保存容量の見積り ③生成されたキャプションの著作権・肖像権チェックの要否
