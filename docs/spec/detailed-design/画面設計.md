> **レイアウト領域・構成要素・主要インタラクション**を文章とリストで具体化し、実装者が画面を起こせる
> 粒度を目指す。実コード（.tsx等）は一切書いていない。

## 1. アクター・デバイスマトリクス（UI_UX設計指針より再掲）

| アクター | ロール | デバイス | 特記 |
| --- | --- | --- | --- |
| 街人・ゲスト | `member` / `guest` | スマートフォン（モバイルファースト） | クエスト・オーダー・AI質問・宿泊確認 |
| コアメンバー・ボラスタ | `core_member` | タブレット | 注文管理・代理入力・宿泊者確認・ナレッジ登録 |
| 管理者 | `admin` | PC | ダッシュボード・マスタ管理・RAGメンテ・会員一括インポート・街人登録承認 |

ロール別UI表示制御（DOM非描画＋サーバサイド認可の両方必須）は正本§5.9・WBS §2-3を参照。本書の各画面には
「対象ロール」列を必ず付け、非対象ロールにはDOMごと出さない前提で設計する。

## 3. 画面遷移（概念フロー）

### 3-1. ゲスト初回訪問〜チェックイン
```
[Googleフォーム(外部)] → (自動でpre_registered予約生成) → A1 登録/チェックイン
  → 名寄せ一致: 「おかえりなさい」表示 → A2 ホーム
  → 名寄せなし: ニックネーム・誕生年月入力 → A2 ホーム
```
※フォーム連携の詳細（自動確定／要確認の分岐）はC10と同様、§5.2.3のドラフト状態に依存する部分がある。

### 3-2. クエスト受注〜完了報告〜承認
```
A3 クエスト一覧 → (guest_allowedチェック。falseならA8街人登録導線へ分岐)
  → A3 詳細 → 受注申請 → [運営審査] → B5 実行指示
  → 現場作業 → A4 完了報告(Before/After写真必須)
  → B5 日次承認/差戻し → (承認) → A2 ホーム(獲得XP表示) / A6 マイログ
```

### 3-3. ゲスト→街人アップグレード
```
A3 施錠クエスト(🔒) タップ → A8 街人登録モーダル(入力→確認) → 申請送信
  → C7 街人登録申請一覧(admin) → QR発行・送付 → (ユーザーがQR決済)
  → C7 入金確認 → 承認 → ロール昇格(guest→member) + 特典付与(宿泊券4枚+CB5000)
  → A2 ホーム(街人として再ログイン)
```

### 3-4. 注文〜精算
```
A5 セルフオーダー / B3 代理注文 → 注文確定(未会計計上)
  → (即時決済: その場でQR発行) or (後払い: 未会計のまま蓄積)
  → C2 一括精算QR発行 → ユーザーがQR決済 → 精算完了
  → 遡及修正が必要な場合: C9 顧客管理画面から伝票編集 → 差額算出 → 8-3差額繰越 or 即時精算
```

### 3-5. ナレッジ登録〜検索
```
B9/C5 ナレッジ登録フォーム(4ステップ) → 登録(pgvectorへベクトル化格納)
  → A7 AIコンシェルジュでの質問 → (信頼度十分: 回答+出典表示) / (信頼度不足: エスカレーション→運営LINE通知)
  → C5 未回答一覧からワンタップでB9/C5へ戻り再登録
```

## 4. 主要画面の構成メモ（ワイヤーフレーム相当）

### C9. 顧客管理画面（伝票編集・遡及修正）

既存モックで最も作り込まれている画面（HTMLモック 2026-08-09第3次）。詳細構成：

| 領域 | 内容 |
| --- | --- |
| 顧客サマリーヘッダー | 氏名・会員種別・通算宿泊日数・残チケット・**現在の割当部屋**（§5.2.1）・未会計額（円＋Uii併記） |
| 注文履歴リスト | 伝票ごとに明細・金額・ステータス（未会計/精算済み/取消）。✏️アイコンで伝票エディタ起動 |
| 伝票エディタ（モーダル） | 商品明細の追加/削除/数量変更、単価上書き、注文者付替（チェックイン中限定⇔全顧客切替トグル）、手動調整行（値引き/追加請求）、決済ステータス変更 |
| 差分プレビュー | 保存前に「変更前→変更後」の差分と、算出された差額（追加請求/返金）を表示。**編集理由入力必須** |
| 編集履歴ログ | 誰が・いつ・何を・なぜ変更したかの一覧（監査用） |
| 差額パネル（新規） | `settlement_adjustments`未処理一覧、免除操作ボタン（**免除権限の範囲はQUESTIONS.md未回答のためボタンの表示条件は保留**） |

### A8 / C7. 街人登録アップグレード導線

| 画面 | 内容 |
| --- | --- |
| A8-1（入力） | 申込内容の確認（30,000円・付与内容の表示）。決済情報の入力フィールドは**一切置かない** |
| A8-2（確認） | 「申請する」ボタン押下で`membership_applications`にレコード作成、ステータス`申込中` |
| C7（管理者一覧） | 申込一覧（ステータス別タブ：申込中/QR送付済み/承認済み/却下/保留）。行選択でQR発行モーダル（発行チャネル：LINE/アプリ内/対面を選択） |
| C7（承認操作） | 入金確認チェック→「承認」ボタンでロール昇格・特典付与処理を1操作でトリガー（`membership_applications.approved_at`・`role_upgraded_at`を同時更新） |

### B9 / C5. ナレッジ登録フォーム（4ステップ）

既存モックになし。正本§5.7.2の4ステップを踏襲。

| STEP | UI要素 |
| --- | --- |
| ① 対象者 | ラジオボタン（guest/member/core_member）。STEP2の選択肢に影響（core_member選択時のみ運営系カテゴリを追加表示） |
| ② 格納先カテゴリ | プルダウン（`work_categories`参照） |
| ③ 行動文脈・キーワード | チェックボックス（利用シーン）＋タグ入力（キーワード自由入力） |
| ④ 本文 | タブ切替（FAQ形式 / マニュアル形式）。マニュアル形式は登録後にAIがQ&A候補へ分解 |
| 入力起点 | 画面上部に「未登録論点」カード（未回答ログから質問文プリセット）、朝会議事録からの抽出候補カードを配置 |

> [!note] §5.7.7（タイプ別構造化入力拡張）について
> Q&A/手順/トラブル事例の3タブへの拡張は、v13 §5.7.7として**未コミットの保留中ドラフト**に含まれる
> 内容であり、本書のB9/C5設計は正本で確定済みの4ステップフォーム（FAQ/マニュアルの二択）のみを対象と
> している。3タブ拡張の採否が確定した後、本書を改訂する。

### C10. 宿泊予定カレンダー（ドラフト・参考記述のみ）

v13 §5.2.3自体が未コミットのドラフトのため、確定的な画面設計は行わない。参考として、
`check_ins × room_assignments × rooms` の結合ビューをカレンダー/リスト表示する構成が想定されるが、
表示粒度（月表示か週表示か、施設稼働率の要否）はQUESTIONS.md「宿泊予約フォーム連携の未確定事項5点」
の⑤が確定してから設計する。
