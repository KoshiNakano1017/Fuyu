> 本書は浮遊街アプリ本体と外部システム（line-rag-bot、eumo等）との連携を設計するドキュメントである。
> **line-rag-bot側の実装コードには一切触れていない**（読解のみ）。line-rag-botは別リポジトリ
> （`C:\Users\user\Documents\MyVault\Myvault\Projects\line-rag-bot`）で開発が進む独立システムであり、
> 本書はあくまで浮遊街アプリ側から見た連携インターフェースの設計に限定する。

## 1. ★ 最重要の論点：ナレッジ・RAG基盤の二重化疑義

本書作成のためline-rag-bot側の設計書（`docs/08-浮遊街RAG詳細設計.md`）を精読した結果、
**DB物理設計.md・API設計.mdで設計した「浮遊街アプリ本体のpgvectorベースのナレッジ基盤」と、
「line-rag-bot側の既存Firestoreベースのナレッジ基盤」が、実質的に同じ役割を別々の技術で
二重実装している可能性がある**ことが判明した。これは本サイクルの新規発見であり、
**オーナーの確認が必須の重大な論点**として本書冒頭に記載する。

### 1-1. 判明した事実

| 項目 | 浮遊街アプリ本体（正本v13・RAGシステム仕様が前提とする設計） | line-rag-bot（実際に実装が進んでいる別システム） |
| --- | --- | --- |
| データストア | Supabase（PostgreSQL）＋ pgvector | Firestore（`knowledge_{tenant_id}`等のコレクション） |
| 検索方式 | pgvectorのベクトル類似検索（想定） | 全件取得＋Python側cosine計算（Phase1は意図的にこの方式を維持、§9-1） |
| レシピ・道具・failure_patterns | ER図_概念データモデル.mdで`Recipe`/`Tool`エンティティとして定義 | `recipes_{tenant_id}`/`tools_{tenant_id}`としてFirestoreに**既に実装済み**（2026-08-15〜16時点でブランチ6・7まで完了） |
| エスカレーション | `unanswered_escalations`テーブルを本書DB物理設計.mdで新規提案 | `escalations`コレクションとして**既に実装済み** |
| LINE連携 | v13・RAGシステム仕様は「フロントエンド：LINE Messaging API」と記載し、浮遊街アプリのRAG基盤の一部として位置づけ | line-rag-botが独自にLINE Messaging APIのWebhookを持ち、Firestore上のナレッジで完結した応答を行う（浮遊街アプリ本体を経由しない） |
| ナレッジ登録UI | v13 §5.7・§5.7.7で浮遊街アプリの管理者権限UIとして設計 | line-rag-bot側は現状Streamlit管理画面のみで登録可能。§9-5で「将来的に浮遊街アプリ管理者UIへ統合し、line-rag-bot側にREST APIを切り出す」方針が2026-08-14に決定済みだが**未着手** |

### 1-2. 考えられる解釈（いずれもオーナー確認が必要）

- **解釈A（統合型）**: 浮遊街アプリ本体のAIコンシェルジュ（アプリ内チャット）とLINEチャットボットは**同一のナレッジ基盤を共有すべき**であり、正本の想定どおりline-rag-bot側にREST APIを切り出し（§9-5）、**浮遊街アプリ本体はpgvectorを持たず、line-rag-botのAPIを呼び出すクライアントとして実装する**。この場合、本書DB物理設計.mdで提案した`knowledge_items`/`knowledge_embeddings`（pgvector）テーブルは**不要**になり、代わりにline-rag-bot APIとの連携層のみを実装すればよい。
- **解釈B（並存型）**: アプリ内チャット（浮遊街アプリ本体）とLINEチャットボット（line-rag-bot）は**別のナレッジ基盤を意図的に並存させる**（例: アプリ内は宿泊・会計等の運営系ナレッジ、LINEは来訪者向けFAQ、のように役割分担する）。この場合、本書DB物理設計.mdの提案どおりpgvectorテーブルを維持しつつ、line-rag-botとは別データとして運用する。
- **解釈C（移行型）**: 元々はpgvectorで作る想定だったが、line-rag-botが汎用マルチテナントRAG SaaS的に先行して実装が進んでしまった（line-rag-bot docs/08は「浮遊街」をline-rag-botの1テナントとして扱う設計）ため、**実質的にline-rag-botへ一本化する方向で後から追認する**のが実態に近い。

v13・Master Index・RAGシステム仕様は**いずれもpgvectorを前提に書かれており、line-rag-botの存在・Firestore実装を明示的に位置づけていない**（Master Index §2-Dにline-rag-adminへの言及はあるが、Firestoreベースである点やマルチテナント設計である点には触れていない）。一方、line-rag-bot側は既にPhase1相当の機能（レシピ・道具マスタ、failure_patterns、エスカレーション）を**実装済み**であり、後から作られた本書のDB物理設計（pgvector版）よりも先行している。

> [!success] 確定方針（2026-08-16 オーナー回答）
> **解釈A（統合型）で確定**。line-rag-bot（Firestore）を単一のナレッジ基盤とし、浮遊街アプリ本体は
> 独自のpgvectorナレッジ格納を持たない。さらにオーナーから重要な追加方針が示された：
> **浮遊街アプリ本体はエンドユーザー向けのAIチャットUI（アプリ内コンシェルジュ）自体を持たない**。
> 街人・ゲストへのAI案内（FAQ・レシピ・道具・failure_patterns等）は**LINE（line-rag-bot）経由に一本化**
> する。浮遊街アプリ側が持つのは「ナレッジ登録」（書き込み）UIのみで、管理者権限UIからline-rag-bot側の
> REST API（docs/08 §9-5方針）へ送信する構成とする。DB物理設計.md側の`knowledge_items`/
> `knowledge_embeddings`テーブル提案は不要となったため、同ドキュメント側で参考セクションへ移動済み。
> 詳細は `docs/spec/QUESTIONS.md`（2026-08-16回答）・v13 §9 #31 を参照。
>
> **呼称について（2026-08-16追記）**：本書では技術的な正確性を優先し、システム名・リポジトリ名
> としての`line-rag-bot`表記を維持する。ただし浮遊街アプリの画面設計.md・利用者向け文言では、
> 街人・ゲストがLINEで対話する相手の呼称として**「浮遊街コンシェルジュ」**を用いる（line-rag-bot
> というリポジトリ名・システム名自体は変更しない。ブランド名と技術名の対応関係のみの整理）。

## 3. eumo連携設計（Phase 2スコープ）

Phase 1ではUiiは「円価格換算表示専用」であり、eumoとの直接連携は行わない（v13 §5.5.1、
`Uii経済圏とeumo連携.md`）。Phase2以降に向けた設計メモのみ記載する。

| 項目 | 内容 |
| --- | --- |
| 連携方式 | 非同期の決済ゲートウェイ方式。eumo側を実資金のSSOT（信頼できる唯一の情報源）とし、浮遊街アプリ側は予測残高をキャッシュする「オペレーション帳簿」として振る舞う |
| 同期タイミング | リアルタイム双方向同期は行わない（仕様上困難と判明済み）。非同期同期・自動リトライ・手動同期機能で不整合リスクに対応 |
| データ項目 | 取引ID・送金者ID・受取者ID・金額・有効期限・付与/利用/失効履歴・EUMO同期メタデータ（`uii_transactions.memo`に格納する想定。DB物理設計.md参照） |
| 消費メタデータ | 「何に消費したか」を記録し、地域内経済循環の可視化に利用（Phase2要件） |
| リスク対応 | eumo API制限・不整合時はアプリ側キャッシュ残高を表示しつつ、非同期リトライ。障害はLINE経由で管理者へ即時通知（システムアーキテクチャ.md非機能要件） |

## 5. ★ Googleフォーム連携 ── **不採用（2026-08-23 廃止決定 ／ 正本 §9 #46）**

> [!important] この連携は実装しない。予約は外部フォームを経由しない
> 正本 §5.2.3 は当初「Googleフォームを維持し、送信をトリガーに `POST /api/reservations/webhook` で
> アプリへ連携する（イベント駆動／§9 #3）」と設計していた。**2026-08-23 のオーナー判断により、
> フォーム自体を浮遊街アプリの公開予約ページ `/reserve` へ置き換える**方針へ転換したため、
> **本連携は外部連携として存在しなくなる**。

**転換の理由（2点とも「フォームでは原理的に不可能」という性質のもの）**

| # | 理由 |
| --- | --- |
| 1 | **Googleフォームは残枠を知らない。** 正本 §5.4.2 は「満室時は UI 上で当該宿泊形態を選択不可にする」を要求するが、フォームには在庫を反映する仕組みがなく、**満室でも送信を受け付けてしまう**。Apps Script で選択肢を定期的に書き換える回避策はあるが、反映遅延が残るため「表示上は空いているのに実際は満室」を完全には防げない |
| 2 | **Googleフォームは本人確認手段を持たない。** 正本 §5.8.3 は名寄せの初回紐付けに「招待コードまたはメール／SMSのワンタイム認証」を**必須**としているが、フォームではこれを実装できず、名寄せを常にチェックイン時の対面まで持ち越すしかなかった。公開予約ページなら**予約時点で OTP を通せる**ため、この要件を満たしたうえで名寄せを成立させられる |

**本決定により不要になった設計要素**

| 要素 | 状態 |
| --- | --- |
| `POST /api/reservations/webhook`（フォーム送信 Webhook） | ❌ 廃止（API設計.md §3-4） |
| HMAC-SHA256 署名検証・タイムスタンプによるリプレイ防止 | ❌ 不要 |
| フォーム回答ID をキーとするべき等性制御・upsert | ❌ 不要 |
| Apps Script の改修（`onFormSubmit` からの送信、再送台帳、時間駆動トリガー） | ❌ 不要 |
| 生回答の中間テーブル `reservation_form_submissions` | ❌ 不要（DB物理設計.md §3-6 で撤回） |
| フォームの宿泊場所選択肢を 4種 → 6種へ揃える改修 | ❌ 不要（予約ページが §5.4.2 の6種を直接扱う） |
| Apps Script による自動返信メール（正本 §9 #30-④） | ❌ 停止し、**アプリ発の通知メールへ統合** |

**移行時にのみ発生する作業（連携ではなく切替オペレーション）**

| # | 作業 | 担当 |
| --- | --- | --- |
| 1 | Googleフォームを「回答を受け付けない」設定へ変更し、確認メッセージに新ページURLを掲示 | 運営 |
| 2 | **公式サイトの「Reservation」ボタンのリンクを差し替える** | 運営（⚠️ サイトのCMS種別・管理者が未確認。正本 §9 #46 の残課題） |
| 3 | Apps Script の自動返信トリガーを停止 | 運営 |
| 4 | 過去のフォーム回答を移行するかを判断 | オーナー |

> [!warning] フォームは「削除」しない
> 過去の回答が事実上の宿泊台帳になっている。削除すると復元できないため、**回答受付の停止に留める**。
> なお過去回答を取り込む場合は**実名・連絡先を含む実データ**であり、`CLAUDE.md` §7.1 により
> **本リポジトリへ持ち込んではならない**（投入は開発者のローカル環境でリポジトリ外から行う）。
