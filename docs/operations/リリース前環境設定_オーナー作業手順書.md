これは 2026-09-08 の決定「Supabase を有料プランへ」の**撤回ではなく実施時期の後ろ倒し**である

## 3. 作業手順（無料の範囲 ／ この順で実行する）

> [!warning] Step 1 → Step 2 の順序は変えられない
> Supabase は**カスタム SMTP を保存するまでメールテンプレートの本文（Source）を編集できない**。

### Step 1. カスタム SMTP のパスワードを入れて保存する（3分）

**場所**: `https://supabase.com/dashboard` → dev プロジェクト → Project Settings → Authentication → SMTP Settings

| 項目 | 入れる値 |
| --- | --- |
| Host | `smtp.resend.com` |
| Port | `465` |
| Username | `resend` |
| Password | **Resend の API キー**（`RESEND_API_KEY` と同じ値） |
| Sender email | `no-reply@fuyuugai.com` |
| Sender name | `浮遊街アプリ` |

> [!danger] 保存前に Username が `resend` であることを目視する
> このフォームは**ブラウザのパスワードマネージャが Username / Password を自動入力する**。
> Supabase のログイン情報が入った状態で保存すると、SMTP 認証に失敗するうえ
> **ログインパスワードが SMTP 設定として保存される**。

**確認方法**: 保存後に `/login` から自分のメールアドレスで OTP を送る。
Resend のダッシュボード（Logs）に送信が1件記録され、受信できれば成功。

### Step 2. ログインメールを「6桁コードだけ」にする（3分）

**場所**: Authentication → Emails → **Magic Link**（Magic link or OTP）→ Body を `Source` タブへ

- 本文を **`{{ .Token }}` を含む形にし、`{{ .ConfirmationURL }}`（サインインリンク）を消す**
- 根拠: CONSOLIDATED_DECISIONS §20-1（2026-09-21 決定）。アプリは `verifyOtp({type:"email"})` の
  **リダイレクトを伴わない**方式で、`/auth/callback` はコード上に存在しない

**確認方法**: 再度 OTP を送り、**受信メールに6桁の数字が載っていること**と、
その6桁で `/login` を通過できることを確認する。

> [!note] これが済むと URL Configuration（Site URL / Redirect URLs）の設定は不要になる
> 招待（経路B）も 2026-09-22 にコード方式へ寄せたため（§22-1）、リンクを受ける導線がそもそも無い。

### Step 3. Auth のレート制限を確定値に合わせる（5分）

**場所**: Authentication → Rate Limits

| 項目 | 確定値 |
| --- | --- |
| メール送信 | **20通/時** |
| OTP 有効期限 | **10分** |
| 再送間隔 | **60秒** |
| 検証試行 | **10回/5分/IP** |

出典: `非機能要件詳細.md` §2-6a ②（CONSOLIDATED_DECISIONS §22-5）。
⚠️ **設定しても効いていない報告があるため実測で確認する**（連続送信して 429 が返るか）。

### Step 4. dev Supabase の未適用マイグレーションを流す（10分）

`0027` 以降が当たっていない（§2 #6）。**画面は実装済みでも、メディアと買い物リストは dev では動かない。**

```
# 1. どこまで当たっているかを確認する（DB パスワードの入力を求められる）
npx supabase link --project-ref <dev のプロジェクト ref>
npx supabase migration list

# 2. 足りない分を流す（--include-all が必要。理由は WBS 1-1 の注記と同じ）
npx supabase db push --include-all
```

> [!warning] `0027` が落ちている可能性を先に確認する
> `0021`〜`0026` が当たっていて `0027` 以降が無いのは、**`0027_media_assets.sql` の適用が失敗して
> 以降が止まった**形に見える。`migration list` の出力とエラーメッセージを残してほしい
> （こちら側で原因を追える）。オーナーが Supabase の GitHub 連携を入れた（2026-09-24）ため、
> **連携が既存の未適用分まで遡るのか、連携後に push された分だけを拾うのか**もここで判明する。

**確認方法**:

```
# 表が見えるようになったか（401 = 表は在る ／ 404 PGRST205 = まだ無い）
curl -s -o /dev/null -w '%{http_code}\n' \
  "$NEXT_PUBLIC_SUPABASE_URL/rest/v1/media_assets?select=id&limit=1" \
  -H "apikey: $NEXT_PUBLIC_SUPABASE_ANON_KEY"
```

### Step 6. Vercel の2点を是正する（5分）

| # | やること | 場所 | なぜ |

## 4. 課金しない間、埋まらない穴（受容するリスクと暫定対処）

| # | 穴 | 起きること | 無料のままの暫定対処 |
| --- | --- | --- | --- |
| 1 | **prod プロジェクトが無い**（`1-1b`） | Production も dev DB を指す | **実名370名を投入しない・公開URLを配布しない。**リリース当日に §5 を実施する |

| 6 | **E2E 専用プロジェクトが無い** | E2E が dev を壊す | Preview は dev を指す（09-24 決定A）。**破壊的な E2E を CI で流さない** |

## 5. 課金を決めた日にやること（60〜90分 ／ この順を崩さない）

リリース当日、またはその前日に実施する。**ここを飛ばすと本番が dev DB を使い続ける。**

1. **Supabase を Pro へ切り替える**（どのプロジェクトを本番にするかを先に決める）
2. **prod プロジェクトを作成**（WBS `1-1b`）→ `supabase db push --include-all` で**全マイグレーションを適用**
3. **Auth 設定を prod にも入れる** — Step 1〜3 を prod プロジェクトに対してもう一度実施する
   （**設定はプロジェクト単位であり、コピーされない**）
4. **Vercel Production の環境変数を prod の値へ差し替える** —
   `NEXT_PUBLIC_SUPABASE_URL` / `NEXT_PUBLIC_SUPABASE_ANON_KEY` / `SUPABASE_SERVICE_ROLE_KEY`
   （＋ Supabase 統合が作った `SUPABASE_*` / `POSTGRES_*` 一式）
5. **再デプロイし、差し替わったことを実測で確認する**（§6 の SHA-256 比較。**Preview は dev のまま**であること）
6. **日次バックアップが有効になっているか**をダッシュボードで確認（非機能 A4 の充足はここで初めて成立）
7. Vercel を **Pro** にするかを判断する（WAF の R2・商用利用の可否）
8. （任意）E2E 専用プロジェクトを作る

## 7. 既知の落とし穴（いずれも実際に起きたもの）

| # | 落とし穴 | 対処 |
