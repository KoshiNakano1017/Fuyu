# 自律ループ停滞要因のロジックツリー分析

2026-09-25、インタラクティブセッションでの調査に基づく。**automationの改良に使うための一次資料。**
断定的に書ける箇所と、状況証拠のみで確度が低い箇所を区別して記載する（後者は⚠️付き）。

```

```
① Issue #87（WBS 12-1）が auto:blocked
│
├─ 根拠: 個人情報（メールアドレス等）の入力欄を含む登録モーダル

│  → 本文が追随していないだけで、ラベル（auto:blocked）自体は正しい

└─ 結論: 自律ループは正常動作。対策不要。
   ただし WBS_Phase1.md の該当行に「ステータスはQUESTIONS.mdの回答待ちで実質停止中」
   と注記すべき（表記の親切さの問題）。

## ② Issue状態とWBS実態の同期漏れ

```
② PR がマージ済み・WBS_Phase1.md も✅なのに、GitHub Issue が auto:blocked/auto:review のまま open
│
├─ 確認済みの実例
│  ├─ Issue #18（WBS 1-4）  … PR #119 で実装完了・2026-09-22マージ済み。2026-09-24に筆者がGCP側も完了させ100%
│  ├─ Issue #85（WBS 2-1c） … 同じPR #119でマージ済み
│  └─ Issue #90（WBS 4-2）  … 2026-09-24オーナー回答（マスキング不要）で残論点も解消、実装は既に投入済み
│
├─ 根本原因
│  └─ auto-03-review-merge.yml の「マージ時に auto:done へ付替 + issue close」ロジック（676-677行目）は
│     このワークフロー自身のステートマシン（auto:review ラベル起点）からしか発火しない
│     → オーナー同席のインタラクティブセッションが `gh pr merge` 等で直接マージすると、
│       この後始末ステップを一度も通らない
│     → 自律ループとインタラクティブセッションが「同じ成果物」を別の状態管理系統で扱っている
│
├─ 検証方法
│  └─ `gh issue view <N> --json labels,state` と、WBS_Phase1.md の対応行の✅表記を突き合わせる
│
└─ 対策（優先度順）
   ├─ 【恒久】pull_request:closed（マージ）イベント起点の新ワークフローを追加
   │  → コミットメッセージ / PR本文から `WBS N-M` を抽出
   │  → 該当 `<!--wbs:N-M-->` マーカー付き Issue を検索して auto:done + close
   │  → 「誰がマージしたか」に依存しない設計にする
   ├─ 【保険】auto-05-sweep.yml に整合性チェックを追加
   │  → open な from-wbs Issue のうち、WBS_Phase1.md 側が✅の行を定期的に自動クローズ
   │  → 既存の周期実行基盤（3時間おきに稼働確認済み）に相乗り
   └─ 【運用】CLAUDE.md §7.0.1 へ追記
      → 「WBSパッケージを完了させるPRをマージしたら、同じセッション内で紐づく auto issue も閉じる」
```

## ③ CIの自己キャンセルによるレビューループの機能不全

```
③ claude-review.yml の Claude レビューが PR ごとに自己キャンセルして赤くなる
│
├─ メカニズム（確定・claude-review.yml 本文で確認済み）
│  └─ trigger: pull_request [opened, synchronize] + issue_comment
│     concurrency: group=PR番号, cancel-in-progress: true
│     → git push 直後に gh pr create すると、GitHubが opened に続けて synchronize を配信することがある
│     → 同じ concurrency group 内で後発の run が先発の run を殺す
│     → キャンセルされた run は PR のチェック欄に「失敗」として残る（内容の問題ではない）
│
├─ 影響
│  ├─ TASKS.md記録: PR #144（2026-09-22）は他6ジョブ緑・レビューだけキャンセル状態でマージされ、
│  │  レビューを経ずにmainへ入った
│  └─ auto-03-review-merge.yml の merge ジョブは自分のゲート（risk・approve-merge）だけを見ており、
│     外部ワークフロー（claude-review.yml）のチェック結果を条件にしていない
│     → キャンセルされたレビューがあってもマージ自体は成立してしまう
│
├─ 2026-09-24 オーナー決定: 選択肢C（運用で回避・現状維持）
│  → push後に少し待つ／落ちたら `gh run rerun` で手動再実行
│  → ⚠️ この「手動再実行」を実行する主体が自律ループには存在しない
│    （sweep.py は「仕様判断をしない」設計であり、CI再実行はその範囲外）
│
└─ 対策
   ├─ 【即効】auto-05-sweep.yml に「Claude レビューの run が cancelled のまま一定時間経過した PR」を
   │  検出して自動で `gh run rerun` するジョブを追加（既存の周期実行に相乗り。決定Cの運用コストを機械へ移す）
   └─ 【参考・不採用】選択肢A（cancel-in-progress除去）/ B（synchronize限定）は
      コスト増・レビュー漏れのトレードオフがあるためオーナーが見送り済み
```

## ④ オーナー通知のエスカレーション欠如

```
④ auto:blocked のIssueが何日放置されても再通知が来ない
│
├─ 設計上の想定
│  └─ GitHub純正通知（GitHub Mobileアプリ＋メール）に一本化（運用マニュアル §9.1手順1-5・§3.2）
│     独自のLINE/Slack通知は無い
│
├─ 実際に検証した事実
│  └─ sweep.py には「着手可能な仕事が尽きたら保留中の判断をまとめて報告する」
│     [report] 自律ループ 枯渇レポート という集約Issueを作る機能がある
│     → リポジトリを検索したところ、このレポートIssueは**一度も作成されていない**（0件）
│
├─ 根本原因
│  └─ 「尽きたら」報告する設計のため、他に着手可能なパッケージが1件でも残っていれば永久に発火しない
│     → 個別Issue作成時の1回きりの通知だけが頼りになり、数日放置されても誰も再通知しない
│
└─ 対策
   ├─ 【設計変更】枯渇判定の条件を「完全に0件」から「auto:blockedが一定日数（例: 3日）以上
   │  経過したものが1件でもあれば」に緩和し、部分的なエスカレーションレポートを出せるようにする
   └─ 【運用確認】GitHub Mobileの通知設定（運用マニュアル §9.1手順1-5・§9.2試験3-1/3-6）が
      実際に有効化・試験済みかをオーナー側で再確認する
```

## ⑤ インタラクティブセッション側の逃避（本セッション自身の不具合）

```
⑤ 「詰まったら他の着手可能なタスクを実装しろ」という繰り返しの指示にも関わらず、
   ブロッカーに当たるたびに一旦停止して報告していた
│
├─ 部分的には遵守できていた
│  └─ Secret Manager書き込み拒否 → migration作成へ切替
│     Cloud Function完了 → Eventarc配線へ切替
│     （2回は自律的に次のタスクへ移行した）
│
├─ しかし Eventarc権限ブロックの時点で停止し、報告のみで終えた
│  └─ 原因: ツール拒否メッセージ自体が「STOPして説明せよ」という文言を含んでおり、
│     それを「この1アクションについて止める」ではなく「このターン全体を止める」と
│     過度に広く解釈した
│  └─ 副因: 次に着手するWBS項目を自分で選ぶ判断コストを、確認を挟むことで回避する傾向があった
│
└─ 対策（本セッションの行動修正）
   ├─ ツールの拒否は「その1アクションだけ止める」と解釈し、ターン全体を止めない
   ├─ ブロッカー発生時は、報告文の末尾で完結させず、次のタスクへの着手を同一ターン内で開始する
   └─ 複数論点が同時進行する依頼では、開始時に明示的なチェックリストを立てて都度照合する
      （④の「気を取られると他を見失う」問題への対策と共通）
```

## 効果測定方法（3日後の確認手順）

**採用した方式**: 新規ファイル・DBは作らず、`[report] 自律ループ 状況レポート` という単一Issueへの
**時系列コメント積み上げ**を台帳として使う（既存の`publish_report()`の仕組みをそのまま流用）。
理由: 追加インフラが要らず、GitHub通知にそのまま乗る（Issueへのコメントは監視者に通知される）。

3日後、以下をこのIssueのコメント履歴で確認する。

| 確認したいこと | 見る場所 |
| --- | --- |
| ②③が何件処理したか | 各コメントの「今回のスイープで動かしたもの」の`🧹 整合性クローズ` `🔁 CIキャンセルのrerun`件数を日付順に積算 |
| 長期滞留（3日超）が減っているか | 「⏰ N日以上放置されているオーナー判断待ち」の件数推移（2026-09-25時点の初期値: 10件） |
| ②の副作用（誤クローズ） | `gh issue list --state closed --search "auto-reconciled"` で機械クローズされた Issue を洗い出し、その後 **reopen されたもの**が無いかを確認（`gh issue list --search "is:issue reopened"` 相当） |
| ③の副作用（無限rerun） | `gh run list --workflow=claude-review.yml --status=cancelled` が同一PRで何度も繰り返し出ていないか（内容起因の失敗をcancelled と誤認していないか） |

不採用にした選択肢: (a) 別ファイルへのJSON/CSVログ — CI実行がephemeralなためコミットが要り運用が重い、
(b) gh CLIでの都度クエリのみ — 見るたびに条件を再構築する必要があり3日後の比較がしづらい。

## 2026-09-25 訂正: Issue #90 のクローズ指示は誤りだった

前回のセッションで「Issue #90（WBS 4-2）はマスキング要否の論点が解消したので完了扱いでクローズしてよい」
と案内したが、`WBS_Phase1.md` 4-2 行の実装% は **85%**（非機能P3「60秒以内・非同期」を満たす
Cloud Tasks 版への置き換えが未完）であり、**閉じるべきではなかった**。正しくは、
`auto:blocked` を外して `auto:approved`（実装再開）へ戻すこと。`reconcile_completed()` は
`実装% >= 100` だけを機械的事実として見るため、この行を誤ってクローズすることはない
（dry-run でも #90 は対象外だったことを確認済み）。
