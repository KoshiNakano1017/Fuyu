# 自律開発ループ オーナー操作マニュアル

> [!info] このマニュアルの立ち位置
> **正本は [[Projects/fuyuugai-app/docs/自律開発ループ設計.md|自律開発ループ設計]] です。**
> このマニュアルは、その設計書から**オーナーが手を動かす部分だけ**を抜き出し、作業の順番に並べ替えたものです。
> 新しいルールは1つも足していません。各項目の末尾に設計書の節番号を書いてあるので、**迷ったら設計書を見てください。**
> 設計書と食い違ったら、**設計書が正しい**。

## 0. 最初に読む

### 0.1 このループでのあなたの役割

**あなたがやるのは「決める」ことだけです。** 作るのはループがやります。

| あなたがやること | ループがやること |
| --- | --- |
| 仕様を決める（対話セッション・ループの外） | 確定済みの仕様を動くコードに変換する |
| どのタスクを流すか選ぶ | 調査・実装・テスト・レビュー・修正 |
| ゲートで承認 / 却下する | PR を作り、CI を通し、マージする |
| 止まったときに1文字返す | 止まる。勝手に埋めない |

> [!danger] ループに仕様を考えさせてはいけない（設計 §0）
> 「なぜその仕様を選んだか」はあなたの頭の中にしかありません。
> ループは **[[Projects/fuyuugai-app/docs/spec/浮遊街アプリ 総合要件定義・設計書_v13.md|正本 v13]] に既に書いてあることを実装するだけ**の存在です。
> 仕様が無い・曖昧・矛盾している箇所を見つけたら、ループは実装せず [[Projects/fuyuugai-app/QUESTIONS.md|QUESTIONS.md]] に起票して止まります。**それが正常動作です。**

### 0.2 現況 — 今どこまで本当に動くか（2026-09-13 時点）

> [!warning] ファイルが存在することと、稼働していることは違う
> 設計書 §12.1.6 段7 が未完のため、**新方式で動いているのは計画フェーズだけ**です。
> このマニュアルの操作手順そのものは全フェーズで有効ですが、内部実装は下表のとおり混在しています。

| フェーズ | ワークフロー | 実装 | 操作への影響 |
| --- | --- | --- | --- |
| 計画（ゲート1・2） | `auto-01-plan.yml` | ✅ 新方式（`plan.mjs` / 構造化出力） | なし。リスク判定は JSON Schema 強制で安定 |
| 実装 | `auto-02-implement.yml` | ⚠️ 旧方式のまま（`implement.mjs` は未接続） | なし。ただし内部はコメント文字列で繋がっている |
| レビュー・マージ（ゲート3） | `auto-03-review-merge.yml` | ⚠️ 旧方式のまま（`review.mjs` は未接続） | リトライ計数が `<!--retry-->` の grep 依存。空振りすると高リスク側へ倒れる |

**未実装のため手作業になっているもの:**

| 機能 | 設計 | 現況 | あなたの代替操作 |
| --- | --- | --- | --- |
| `QUESTIONS.md` からの逆流線（導線3） | §10.1.5 | ❌ 未実装 | 回答済みにしても Issue は自動で戻りません。**手でラベルを付け直す**（§3.3） |
| `needs-spec` 起動の仕様ナビ | §10.1.5 導線2 旧仕様 | ❌ 未実装 | 起票支援エージェント（✅ 実装済み）で代替 |

## 1. 全体像 — 1 Issue の一生

```
     [夜] あなた: WBS番号を打つ → Issue 生成 + 起草
              ↓
     [夜] あなた: 起草を読む → auto ラベルを付ける  ← ★承認その0
              ↓
          ループ: PM がタスク定義 → リスク判定
              ↓
     [朝] あなた: ゲート1 を承認                    ← ★承認1（What）
              ↓
          ループ: 調査 → 段取り
              ↓
     [朝] あなた: ゲート2 を承認                    ← ★承認2（How）
              ↓
          ループ: テスト設計 → 実装 → CI → レビュー3種 → 修正
              ↓
     [夕] あなた: ゲート3 を承認                    ← ★承認3（反映）
              ↓
          ループ: マージ → auto:done
```

**1 Issue につきあなたの操作は、起票を入れて4回。それぞれ数分です。**（設計 §10.2）

### 1.1 ラベルが今どこにいるかを示す

ループの状態は **Issue のラベル**だけで表現されています。途中で失敗しても、Issue を見ればどこまで進んだか分かり、**ラベルを戻すだけで再開できます。**（設計 §5）

| ラベル | 意味 | 次に動くもの |
| --- | --- | --- |
| `auto` | ループ対象として起票された | WF1（計画） |
| `auto:planning` | PM / 調査が動作中 | — |
| `auto:approved` | ゲート1・2 を通過した | WF2（実装） |
| `auto:implementing` | コーディング中 | — |
| `auto:review` | PR 作成済み、レビュー / 修正ループ中 | WF3（レビュー・マージ） |
| `auto:blocked` | 仕様未確定 / リトライ超過で停止 | **あなた** |
| `auto:done` | マージ完了 | — |
| `auto:rejected` | ゲートで却下された | **あなた** |

補助ラベル: `needs-spec`（仕様未確定で保留）／ `auto:low-risk`（自動通過中・異議申立て可）／ `security`

### 1.2 承認が何回来るかは、タスクのリスクで変わる

**全部を3回承認させると、文言修正もDBマイグレーションも同じ手間になります。** そこで PM がリスクを3区分に判定し、区分ごとにゲート数を変えます。（設計 §4.1）

| 区分 | 何が該当するか | 承認回数 |
| --- | --- | --- |
| **高** | 認可・ロール判定／金額・Uii・宿泊券の計算／個人情報の入出力／DBマイグレーション／外部連携（LINE・Supabase Auth・決済）／セキュリティ高リスク | **3回**（ゲート1・2・3） |
| **中** | 上記以外の新規機能・既存機能の振る舞い変更 | **2回**（ゲート2・3） |
| **低** | 表示文言の修正／テスト追加のみ／振る舞いが変わらないリファクタ／コメント・型注釈のみ | **0回**（自動通過） |

> [!important] 低リスクには30分の異議申立て窓がある
> **高リスクを「低」と誤判定されるのが唯一の致命的な失敗モードです。**
> そこで PM は**まず区分判定だけを Issue にコメント**し、低と判定した場合は判定理由つきで通知して30分待ちます。
> 違和感があれば **`auto:low-risk` ラベルを外す**だけで中リスクに落ちます（§3.4）。

## 2. 日々の操作

### 2.1 夜（就寝前）— 起票する

**やることは3つだけです。**（設計 §10.1.5 導線1・導線2）

| # | 操作 | 場所 | スマホ |
| --- | --- | --- | --- |
| 1 | WBS の作業パッケージ番号を打つ（例 `2-1`） | Actions タブ → `WBS → Issue 生成` → **Run workflow** | ⚠️ アプリ不可・**モバイルブラウザのPC版表示なら可** |
| 2 | 起草を読む。`⚠️ 要オーナー確認` があれば **A/B/C を1文字コメント** | Issue | ✅ アプリ可 |
| 3 | **`auto` ラベルを付ける ← これが承認** | Issue | ✅ アプリ可 |

**入力欄の意味:**

| 入力 | 既定 | 説明 |
| --- | --- | --- |
| `package` | （必須） | [[Projects/fuyuugai-app/docs/spec/WBS_Phase1.md\|WBS_Phase1.md]] の表の1列目と**完全一致**させる（例 `3-5b` / `1-2` / `14-6`） |
| `draft` | `true` | 起票支援エージェントに完了条件とスコープ外を起草させる。**通常はそのまま** |
| `start_loop` | `false` | `auto` ラベルまで自動で付ける。**起草を読まずに流すことになるので通常は使わない** |

**自動で埋まるもの / 埋まらないもの:**

- 自動で埋まる: 目的・根拠となる仕様・想定サイズ（WBS から転記）
- 起草される: 完了条件・スコープ外（**根拠の節番号が必ず添えられる**）
- 廃止・Phase 2 移送済みのパッケージは**起票を拒否**されます（掘り起こしは操作ミスなので）

> [!danger] 起草がもっともらしく誤っていても、素通りしてしまう（設計 §10.1.5）
> **空欄は目に留まりますが、それらしい嘘は素通りします。**
> だから起草エージェントには「分からないものを埋める」より「**分からないと言う**」ことを要求しています。
> あなたが見るのは「**起草の根拠節が、実際にその内容を書いているか**」です。ここが最頻の事故ポイントです。
>
> 物理的な担保として `automation/settings/draft.json` が `Write` / `Edit` を全面拒否しており、
> 起草エージェントは `docs/spec/` を**1文字も書き換えられません**。

> [!warning] 夜に仕様を考え始めない（設計 §10.1.3）
> 起票の場で仕様を考えると、**翌朝のゲート1で「自分の意図」と照合できなくなります。**
> ゲート1は「PM の解釈が自分の意図とズレていないか」を見る場であって、意図そのものを作る場ではありません。
> 判断がつかない項目は [[Projects/fuyuugai-app/QUESTIONS.md|QUESTIONS.md]] に置いたまま、別の時間（対話セッション）へ回します。

### 2.2 朝5分の固定手順 — 順序を変えない

> [!important] なぜ順序を固定するのか（設計 §10.10.2）
> **疲れている日でも同じ判断ができるようにするためです。**
> 「見てから決める」ではなく「**決まった順で見る**」。

| 順 | やること | 所要 | 判断基準 |
| --- | --- | --- | --- |
| **1** | **`auto:blocked` を先に見る**（Issues をラベルで絞る） | 1〜2分 | 選択肢3つ＋推奨が出ているはず。**A/B/C を1文字返し、続けてラベルを付け直す**（§3.3）。**仕様を考え始めない** |
| **2** | **`auto:low-risk` の異議申立て**（30分窓） | 30秒 | 判定理由を読み、違和感があればラベルを外す。無ければ何もしない |
| **3** | **ゲート1を承認**（§4.1 のチェックリスト） | 1分 | 節番号が実際にその仕様を指しているかだけ確認 |
| **4** | **ゲート2を承認**（§4.2 のチェックリスト） | 2分 | 受入テスト一覧が完了条件を満たしているか |

> [!note] なぜ blocked を最初に置くのか
> blocked は**ループが止まっている**状態で、放置するとその日1日分の処理が丸ごと失われます。
> 承認は待たせても進みが遅れるだけですが、**blocked は進みません。**

> [!warning] 朝に仕様を決めようとしない
> 手順1で「これはどっちだろう」と考え始めたら、**その場では決めずに保留します。**
> 起票と仕様策定は時間を分ける。判断がつかない項目は `QUESTIONS.md` に置いたまま、夜の前処理へ回します。

### 2.3 夕方 — ゲート3

通知でレビュー完了を確認したら、ゲート3（マージ前）を承認します。
**差分を読む必要があるので、ここだけは PC が現実的です。**（設計 §10.10.1）

### 2.4 複数件が並行しているとき

計画フェーズは並列、実装は直列なので、朝の承認待ちが3件同時に来ることがあります。（設計 §10.10.3）

**処理順序は「進んでいる順」。番号順でも重要度順でもありません。**

1. ゲート**3**待ち（マージ直前 ＝ 最も投資済み）
2. ゲート**2**待ち
3. ゲート**1**待ち
4. `auto:blocked`（ただし §2.2 のとおり**確認だけは最初**にする）

> [!important] 1日に承認する上限は3 Issue まで
> **進んでいるものから片付けるのは、仕掛品を減らすためです。**
> 全部を少しずつ進めると、どれも完了せずレビュー対象だけが積み上がります。
> 実装フェーズは直列化されているので、4件目を起票しても待つだけになります（設計 §10.6）。

## 3. 操作カタログ — どこを押すか

### 3.1 承認する（PC）

ゲートで停止すると、Actions の run が**待機状態**になりメールが届きます。（設計 §10.10.1）

1. メール本文のリンク、または **Actions タブ**から該当 run を開く
2. 上部の黄色いバナー **`Review deployments`** を押す
3. モーダルで環境（`gate-task-definition` 等）に**チェック**
4. コメント欄に理由を書く — **承認なら空でもよい。却下は必ず書く**
5. **`Approve and deploy`** を押す

### 3.2 承認する（スマホ）

GitHub モバイルアプリの通知から同じ run を開き、同じ `Review deployments` 導線に入ります。
**朝の2回（ゲート1・2）はスマホで完結する想定です。**

| 操作 | モバイルアプリ |
| --- | --- |
| ゲート1・2 の承認 | ✅ できる |
| ゲート3 の承認 | ⚠️ 技術的には可能だが、差分を読むので PC 推奨 |
| ラベルの付け外し（blocked 復帰など） | ✅ できる |
| Issue へのコメント（A/B/C 返答） | ✅ できる |
| **`WBS → Issue 生成` の起動** | ❌ **アプリは `workflow_dispatch` 非対応**。モバイルブラウザのPC版表示で代替 |

### 3.3 `auto:blocked` から復帰させる

> [!danger] コメントしただけでは再開しません（設計 §8.5・§10.5）
> **Issue へのコメントは、自律ループのどのワークフローも起動しません。**
> 回答のコメントは*エージェントへの入力*にはなりますが、*引き金*にはなりません。
> 引き金になるのは **ラベルが「付いた」こと**だけです。

**正しい手順（2手）:**

1. 回答（A/B/C など）を Issue に**コメント**する
2. **`auto:blocked` を外し、`auto` を付け直す** ← **これが引き金**

> [!warning] `auto` が既に付いている場合は、一度外してから付け直す
> 同じラベルを付け直しても、**既に付いている状態では `labeled` イベントは発生しません。**

**停止理由ごとの対処:**

| 理由 | 見分け方 | 対処 |
| --- | --- | --- |
| **仕様が未確定** | `QUESTIONS.md` に新規項目が起票されている | 該当項目を「回答済み」にし、必要なら `docs/spec/` を更新してから、ラベルを `auto` に戻す |
| **リトライ5回超過** | 「リトライが5回に達した」コメント | 失敗ログを読む。環境不備・仕様の矛盾なら人間が直す。直したら `auto:review` に戻す |
| **基盤エラー** | `⛔ 基盤エラーで停止しました` コメント | **リトライしても直りません。** Secrets・PAT 権限・SDK の導入を直してからラベルを付け直す |
| **同一指紋が2回** | `同一のエラー指紋（…）が2回続きました` コメント | 同じ失敗の繰り返し。回数を増やしても解けないので、**人間が原因を取り除く** |

### 3.4 低リスクの自動通過に異議を出す

判定理由のコメントを読んで違和感があれば、**`auto:low-risk` ラベルを外す**だけです。中リスクに落ち、ゲート2・3で止まるようになります。**窓は既定30分。**（設計 §4.1）

なお、低リスクの自動通過には次の**全条件**が課されています。1つでも欠ければ自動的に中リスクへ繰り上がります。

- CI が全ジョブ緑 ／ レビュー3種の **[必須] 指摘がゼロ**
- 変更ファイルが段取りで宣言した範囲内 ／ 新規依存パッケージの追加なし
- `docs/spec/` に差分なし ／ `supabase/migrations/` に差分なし

## 4. ゲートで何を見るか（チェックリスト）

> [!important] 「なんとなくOK」にしない（設計 §10.3）
> 承認をなんとなくで通すと統制が形骸化します。ゲートごとに**見る場所を固定**してください。

### 4.1 ゲート1（タスク定義）— 見るのは「ズレていないか」だけ

- [ ] 目的が**自分の意図と一致**しているか
- [ ] 引用された仕様の節番号が**実際にその仕様を指しているか** ← **ここが最頻の事故ポイント**
- [ ] スコープ外の宣言に、**勝手に広げられた項目**が混ざっていないか
- [ ] `QUESTIONS.md` の未回答項目に抵触していないか（PM が抵触を報告してくる）
- [ ] **リスク区分と判定理由**が妥当か

### 4.2 ゲート2（段取り）— 見るのは「作り方」と「テストの一覧」

- [ ] 変更ファイル一覧に、**触ってほしくないもの**が入っていないか
- [ ] **受入テストの一覧が完了条件を満たしているか** ← ここが実質の受入基準になる
- [ ] 認可・金額計算・個人情報に触るなら、**そのテストがあるか**（CLAUDE.md §4.4）
- [ ] 調査結果に「仕様が曖昧」という報告が混ざっていないか

### 4.3 ゲート3（マージ前）— 見るのは「差分」と「指摘の処理」

- [ ] CI が**全部緑**か
- [ ] レビュー3種の **[必須] 指摘がすべて対応済み**か（未対応なら理由が書かれているか）
- [ ] **5c（個人情報）が「問題なし」と明言**しているか
- [ ] `docs/spec/` に差分が無いか（§8.2 のガードが通っていれば自動的に保証される）

## 5. 却下するとき

Environment の承認画面で **Reject** し、**却下理由を Issue にコメントします。**
**理由が無いと同じ提案が返ってきます。**（設計 §10.4）

> [!danger] 却下理由をモーダルのコメント欄だけに書かない
> **Environment の却下コメントは Issue には流れません。エージェントはそれを読めません。**
> モーダルのコメントは**人間の監査ログ**、Issue のコメントが**エージェントへの入力**です。
> 却下したら**必ず Issue 側にもコメント**してください。

### 5.1 却下の種類と、その後

| 却下の種類 | 書き方の例 | その後 |
| --- | --- | --- |
| スコープがずれている | 「§5.10.2 ではなく §5.10.7 が対象」 | `auto` を付け直して再実行 |
| 仕様が未確定だった | 「これは仕様策定が先。`QUESTIONS.md` に起票済み」 | `auto:blocked` → 仕様を決めてから再投入 |
| 作り方が違う | 「Server Actions ではなく Edge Function で」 | ラベルを `auto:approved` に戻さず **`auto` から再実行** |
| 質問の仕方が悪い | 「選択肢が実質1つしかない」「決定済み事項を聞いている」 | §3.2 のプロンプトを直す。**タスク自体は再実行してよい** |

### 5.2 却下理由にマーカーを付ける（必須）

**人間の却下は、接地した唯一の信号のうち最も価値が高いものです**（設計 §11.6）。
Issue にコメントしただけでは会話に埋もれて再利用されません。**コメントの先頭に機械可読なマーカーを置いてください。**

```markdown
<!--reject phase=gate2 kind=how -->
Server Actions ではなく Edge Function で。理由は RLS を跨ぐ集計が必要だから。
```

- `phase` は `gate1` / `gate2` / `gate3`
- `kind` は `scope` / `spec` / `how` / `question` の4種

週次でこのマーカーを集計します。**3回同じ `kind` で却下されているフェーズは、プロンプトに構造的な欠陥があります。**

## 6. 困ったとき（症状 → 対処）

設計 §10.7 のランブックを操作視点で並べ直したものです。

| 症状 | 原因の第一候補 | 対処 |
| --- | --- | --- |
| **コメントしたのに再開しない** | コメントは引き金にならない（§8.5） | **ラベルを外して付け直す**（§3.3） |
| **同じラベルを付け直しても動かない** | 既に付いている状態では `labeled` が発火しない | **一度外してから**付け直す |
| 承認待ちの run が勝手に消えた | `concurrency` の自己キャンセル（§8.4・修正済み） | 再発するならラベルから再開。3本とも隔離設定済みのはず |
| PR は出来たが CI が走らない | `GITHUB_TOKEN` で PR を作っている（§8.1） | **`AUTOMATION_PAT`** を使う設定になっているか確認 |
| ゲートで承認しても次に進まない | ラベル付け替えを `GITHUB_TOKEN` でやっている | 同上 |
| 承認メールが来ない | Environment の Required reviewers 未設定、または通知設定 | Settings → Environments と Notification settings を確認 |
| `auto:blocked` が頻発する | Issue の「根拠となる仕様」が甘い | **起票基準を締める。** 続くなら仕様側の整備が先（§7.2） |
| レビュー指摘が的外れで修正が空回り | プロンプトが過剰に強い指示になっている | エージェント定義から `CRITICAL` `必ず` 等の強調を減らす |
| run が30日で失敗した | 承認を放置した（§8.3） | ラベルから再開する |

## 7. 週次メンテナンス（5〜10分）

週に一度、次を確認します。（設計 §10.8）

- [ ] [[Projects/fuyuugai-app/LOOP_LOG.md|LOOP_LOG.md]] を読み、想定と違う判断をしていないか
- [ ] [[Projects/fuyuugai-app/QUESTIONS.md|QUESTIONS.md]] の未回答が**増え続けていないか**（増える一方なら仕様策定が追いついていない）
- [ ] `auto:blocked` のまま**放置された Issue** が無いか
- [ ] Actions の実行時間・API 利用量が想定内か
- [ ] **却下が多いゲート**は無いか（多ければそのフェーズのプロンプトを直す）
- [ ] §7.1 の指標を `LOOP_LOG.md` から算出し、前週と比べる
- [ ] `QUESTIONS.md` の回答済み項目を、正本反映・WBS 更新まで進める

### 7.1 見る指標

| # | 指標 | 定義 | なぜ見るか |
| --- | --- | --- | --- |
| 1 | **指摘密度** ★主指標 | `[必須]指摘件数 ÷ 変更行数 × 100` | 生の指摘件数は使わない。**正規化しないと改善が悪化に見える** |
| 2 | 停止率 | `auto:blocked ÷ auto を付けた Issue` | 高いなら**起票3条件が守られていない**（前処理の問題であってループの問題ではない） |
| 3 | 却下率（ゲート別） | `Reject 回数 ÷ 承認判断の回数` | どのフェーズのプロンプトが的外れかを特定する |
| 4 | 手戻り回数 | `修正エージェントの起動回数 ÷ PR 数` | 2を超え続けるなら**テスト設計が完了条件を捉えきれていない** |
| 5 | リードタイム | `auto 付与 → auto:done の経過時間` | 承認待ちの滞留か、処理そのものが遅いのかを分ける |
| 6 | トークン単価 | `1 Issue あたりの総トークン` | コスト方針が機能しているかの検算 |

> [!warning] 1つの指標を目標にした瞬間、それは指標でなくなる（Goodhart の法則）
> **指摘密度（#1）だけを下げにいくと、レビューが甘くなるだけで下がります。**
> #1 は必ず **#4（手戻り回数）と #2（停止率）とセットで見る。**
> 指摘密度が下がり、**かつ**手戻りも停止率も増えていないときに限り、改善したと判断します。

> [!note] 初期値は「悪い」のが正常
> 最初の数週間は停止率が高く出ます。これは**ループの失敗ではなく、仕様の空白がループによって可視化された**ということです。
> ここで指標を良く見せようとして**起票基準を緩めると、設計 §0 が崩れます。**

## 8. やってはいけないこと

| # | 禁止 | なぜ |
| --- | --- | --- |
| 1 | **節番号を書けない Issue に `auto` を付ける** | それは実装タスクではなく**仕様策定タスク**。`needs-spec` を付けて別扱いにする（設計 §10.1） |
| 2 | **起票の場で仕様を考える** | 翌朝のゲート1で「自分の意図」と照合できなくなる（設計 §10.1.3） |
| 3 | **朝のゲートで仕様を決め始める** | 同上。判断がつかないものは `QUESTIONS.md` に置いて夜へ回す |
| 4 | **却下理由をモーダルにだけ書く** | エージェントに届かない。同じ提案が返ってくる（設計 §10.4） |
| 5 | **コメントだけして再開したつもりになる** | Issue は静かに滞留する。ラベルを付け直すまで何も起きない（設計 §8.5） |
| 6 | **1日に4件以上起票する** | 実装フェーズは直列。待つだけになる（設計 §10.6） |
| 7 | **慣らし運転を飛ばして高リスクを初日に流す** | 「設計どおり止まった」のか「壊れて止まった」のか判別できなくなる（§9.4） |
| 8 | **停止率を下げるために起票基準を緩める** | 設計 §0 が崩れる。指標のための運用になる |

## 9. 初期セットアップ（1回だけ）

> [!note] 既に稼働している場合は読み飛ばしてよい
> 本節は設計 §9「導入手順」の要約です。**順序に意味があります。**

### 9.1 セットアップ手順

| フェーズ | 作業 | 完了条件 |
| --- | --- | --- |
| **0-1** | 足場の作成（Next.js 雛形・Supabase スキーマ・Playwright 設定） | `main` で `npm run build` と E2E が通る |
| **0-2** | ブランチ保護 — `main` に「PR 必須」「CI 必須」 | 直接 push が拒否される |
| **1-1** | Environments 3つ（`gate-task-definition` / `gate-task-plan` / `gate-merge`） | それぞれ **Required reviewers にオーナー自身** |
| **1-2** | Secrets 登録 — `ANTHROPIC_API_KEY`・**`AUTOMATION_PAT`** | PAT 権限は §9.3 |
| **1-3** | ラベル作成 — §1.1 の8種 ＋ `needs-spec` ＋ `auto:low-risk` ＋ `security` ＝ **11種** | — |
| **1-4** | Issue テンプレート `.github/ISSUE_TEMPLATE/auto-task.yml` | 5項目が必須フィールド |
| **1-5** | 通知設定 — メール受信を有効化。スマホ承認するならモバイルアプリ | — |
| **2-x** | ループの中身（権限設定6本・エージェント定義12本・オーケストレータ・ワークフロー3本） | ✅ 実装済み。詳細は [[Projects/fuyuugai-app/automation/README.md\|automation/README.md]] |

### 9.2 試運転（飛ばさない）

**いきなり本番タスクを流さない。** 検証したいのは実装品質ではなく**統制が効くか**です。

| # | 試験 | 使う Issue | 期待する結果 |
| --- | --- | --- | --- |
| 3-1 | ゲートが止まるか | 表示文言の修正1件（低リスク） | 「低」と判定され、**判定理由つきで通知**。30分窓が機能する |
| 3-2 | 中リスクで2回止まるか | 既存画面に項目を1つ追加 | ゲート2・3で停止し、承認するまで進まない |
| 3-3 | `docs/spec/` を守るか | 仕様書に差分が出るタスクをわざと投げる | ジョブが失敗する。**settings でも拒否されるか**を両方確認 |
| 3-4 | PR で CI が走るか | 3-2 の PR | `ci.yml` が起動している（しなければ PAT 設定ミス） |
| 3-5 | **止まり方が正しいか** ★最重要 | 節番号をわざと曖昧にした Issue | `auto:blocked` になり、**選択肢3つ＋推奨の形**でコメントされている |
| 3-6 | スマホで承認できるか | 3-1 の再実行 | モバイルアプリの通知から `Review deployments` に到達できる |

> [!important] 3-5 が最も重要
> ここで「矛盾があります」としか言わずに止まったら、**質問の作法（設計 §3.2）が効いていません。**
> 直してから本番に入ってください。

### 9.3 `AUTOMATION_PAT` に必要な権限

fine-grained PAT で次の4つ（設計 §8.1）:

`Contents: Read and write` / `Pull requests: Read and write` / `Issues: Read and write` / `Workflows: Read and write`

> [!warning] なぜ `GITHUB_TOKEN` ではダメか
> GitHub の仕様上、**`GITHUB_TOKEN` で作った PR やラベル変更は、別のワークフローをトリガしません**（無限ループ防止）。
> これを踏まえないと、**CI が走らないまま「CI が赤い PR はマージしない」が検証不能で素通り**します。

### 9.4 立ち上げ期の慣らし運転

| 期間 | 流す量 | 目的 | 次へ進む条件 |
| --- | --- | --- | --- |
| **1日目** | 低リスク1件（表示文言の修正） | 3ゲートの物理操作に慣れる。スマホ承認を確認 | 承認・却下の両方を1回ずつ試した |
| **2〜3日目** | 中リスク1件／日 | 質問形式が機能するか。**わざと曖昧な Issue を混ぜる** | 選択肢3つ＋推奨の形で止まった |
| **4〜7日目** | 2件／日 | 並行時の捌き方（§2.4）に慣れる | §7.1 の指標が算出できた |
| **2週目〜** | 最大3件／日 | 通常運用 | — |

> [!note] 慣らし運転を飛ばすと何が起きるか
> **初日に高リスクのタスクを流すと、統制の検証と実装の検証が混ざります。**
> ゲートで止まったとき、それが「設計どおり止まった」のか「壊れて止まった」のか判別できません。
> 低リスクから始めるのは、**期待する挙動が事前に分かっているタスクで検証するため**です。
